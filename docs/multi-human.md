# 多人协作 · 同一工作目录，各自开自己的门（现在时）

> 顶层合同：**多个物理人**在同一家公司共享盘上协作的**形态、开门配方、边界与迁移清单**。
> 人侧归属与授权面的事实家 = [`company-workspace/kb/owners.md`](../company-workspace/kb/owners.md)；
> 成员侧的协作规矩 = [`company-workspace/AGENTS.md`](../company-workspace/AGENTS.md)。
> 来源与取舍（含输掉的方案）= [proposed/multi-human-role-routing](../notes/implemented/2026-09-26-multi-human-role-routing.md)。
> **不许复杂化**（用户定的）：不搞 client/server、不搞账号体系、**不在 DSH 里造"人"这一层**。

## 0. 先读这条：机制边界（决定一切怎么摆）

**DSH 是单操作者设计**——没有账号体系；客户端身份 = 每进程一个 launch token + 签名 cookie；
**审批与问询的路由键是 `agent`（会话），不是"人"**。由此推出两条实测结论（2026-09-26）：

| 事实 | 证据 |
|---|---|
| **卡按"发起它的那个 agent 的会话"作用域** ⇒ 只有那个会话的 owner 看得到 | 两门实测：让其中一扇门的 agent 发 `request_signoff`，面板只在"请求所属会话"那扇门显示（A=true / B=false） |
| **被委派的成员（含 team teammate）一律拉不到人**——问询在服务层被拒、审批硬编码 `never` | `scripts/member-inquiry-probe.mjs` 逐字报错：`human interaction is unavailable while the calling agent is owned by another live agent`；`user-questions/src/index.ts:101-106` + `child-agent.ts:254` |

⇒ **一场由 CEO 主持的动议里，所有卡都只落到 CEO 那扇门。** 所以：

- **多人的价值在"盘上的分工"（drafts / journal / final），不在"卡的分发"**；
- 要展示"谁该批的事落到谁的门"，得让**那个人在自己的根会话里**触线；
- 手册那条「成员触线一律升级 CEO」**不是礼貌，是机制强制的**（成员自己发 = 白发）。

### ⚠ 但**每扇门都不是成员**——这条最容易搞反

「被委派的成员拉不到人」**不等于**"角色自己拉不到人"。两者的分水岭是 **`parent`（运行时归属）**：

| 谁 | 是不是 root | 能不能拉人 | 该怎么做 |
|---|---|---|---|
| CEO 动议里 spawn 出来的 teammate / 委派 child | ✗（有 `parent`） | ✗ 必被拒 | **升级给 CEO**（手册那条走法） |
| **每人自己开的那扇门**（该角色的**根会话**，他本人就是 owner） | ✓ | ✓ 能 | **自己发起** `request_signoff` / `ask_user_question`——**卡才会落到他自己的门上** |

**所以多人模式下的正确动作是反过来的**：門乙（CFO 的根会话）撞签字线时**由它自己发起**，
**不要**"升级给 CEO"（那会把卡送到甲的门上，恰好演示反了）。
实测依据：`scripts/budget-signoff-probe.mjs` 的正例——CFO 根会话确实会发 `request_signoff`。

（手册「问人两条路」与「审批三档」均已含这条根会话 vs 被委派成员的区分——见两节的 ⚠ 段；
[RFC](../notes/implemented/2026-09-26-multi-human-role-routing.md) 进度表 f 行随之闭合。）

## 1. 形态（已定，可逆）

**每角色一个浏览器 profile**（2026-09-26 自裁）：三扇门互不串味、最接近"3 个登录"、零额外结构。
备选"一个浏览器多标签"被否（"人"的边界最模糊，容易顺手替别人签）。
**可逆**：真演示嫌麻烦就退回多标签——机制上路由仍按会话作用域生效，不受影响。

## 2. 开门配方（runbook）

```sh
cd <仓库根> && source dev/env.sh
CI=true pnpm dsh web -- --port 0 --no-open         # 端口是环境状态；见下方"端口不是仓库事实"
# 启动横幅里会打印带 token 的 URL：http://127.0.0.1:<port>/?token=<token>
```

1. **一个服务**，三个人各自用自己的浏览器（或各自的浏览器 profile）打开**同一个带 token 的 URL**。
   ⚠ **先连工作区**（不连就看不到任何会话——会话列表按【工作目录】过滤）：空态页点主区
   **Choose workspace**（已有工作区时走侧栏 `Workspaces` 旁的 **Add workspace** 图标）→
   **必须先点对话框里的 `Edit path`** 才会出现路径输入框 → 粘贴 `company-workspace` 的**绝对路径**
   → 回车 → `Open`。**这一步最容易漏**（对话框默认是目录浏览器，不点 `Edit path` 看不到粘贴框；
   2026-09-23 实测用户与代理都卡过）。平台 UI 是 vendor 只读、改不了 ⇒ 写进本 runbook 代偿；
   完整版另见 [demo.md](./demo.md) §前置。
2. **每人钉住自己角色的根会话**（**根会话** = 自己在侧栏新建的那个；Agent Teams 的**成员**会话在
   会话头部的 Team 名册里点开，或按标题搜索——但成员会话拉不到人，见 §0）。
   人甲 → CEO 会话；人乙 → CFO 会话；人丙 → COO/VP 会话。
3. **协作全部走共享盘 + 邮箱**：分身之间用 Agent Teams 消息；人对人用文件
   （`drafts/<角色>.md`、`kb/<角色>/journal/`、`final.md` 归 CEO）+ 说一声"我写完了"。
4. **角色一眼可辨（2026-09-26 起 client 面自带）**：侧栏每个公司会话行首有**角色徽标**
   （CEO/CFO/COO/VPE/VPS）；当前会话的**浏览器窗口标题**带【角色】前缀、窗口最顶有一条
   细色带——多窗并排也不会认错门。**开每扇门时记得选对 preset**（默认是 `ceo`，已实测踩坑）。
5. **人该动的时候**：谁的门上出现卡，就由**那个人**答/批。
6. **看进展 = 右栏「在场」页签（在场板）**：成员行带上线状态 + 当前任务 subject，动态流含任务生命周期——**成员进展的唯一面**。**注意力中心只推「需要你」四类**（问询/审批/升级/完成；问询节流是设计哲学，成员进度不进卡面、不是缺陷）。预期行为判据钉 `tests/presence-board.spec.ts`（D-a/D-b）；**ETA 显式不做**（复活触发 = 真人开始问「还要多久」，届时另立推敲）。

**端口不是仓库事实**（环境状态，会被别的实例占用——实测 3080/3081/3082 三个都可能是别人的 DSH）：
被占就换一个空闲端口，或直接 `--port 0`（系统分配，端口与 token 从启动横幅读）。
**脚本一律 `--port 0`**；给人开的窗可**挑一个空闲端口固定用**——好处是浏览器 origin 不变，
工作区连接与面板布局（本地存储按 origin 隔离）能留下来。

**已知边界：卡是实时事件、刷新即丢**——页面加载后**不重建挂起请求**。⇒ 人不在台面前时，
被问的事事后看不到、也答不了；离台期间要的东西必须写进稿件「待人确认」（见公司手册「人机接口」）。

## 3. 交接协议（CEO 怎么把活交给"另一个人的角色会话"）

一场动议由 CEO 主持；但**别的角色的"人"在自己的根会话里干活**——两者之间**没有消息通道**
（成员拉不到人、非团队会话之间也不互发）。所以交接**只能走盘上的文件**，载体用**现成形状**，不新增机制：

| 步 | 谁 | 写/读什么 |
|---|---|---|
| ① 派活 | CEO 的会话 | 把**任务书**落 `deliverables/<slug>/drafts/ceo.md`（**CEO 自己的过程稿 = 任务书**；`drafts/<角色>.md` 是既有形状，`ceo` 也是角色，不新增文件类型） |
| ② 通知 | 人对人 | 出话："CEO 那边派了 `<slug>`，你看一下"（**流程级**，不是机制——机制上只有 CEO 的门会弹卡） |
| ③ 干活 | 那个角色的**人**，在**自己的根会话**里 | 读 `drafts/ceo.md` → 写 `deliverables/<slug>/drafts/<角色>.md` + 自己的 `kb/<角色>/journal/` |
| ④ 回话 | 人对人 | 出话："我写完了" |
| ⑤ 收口 | CEO 的会话 | 读各 `drafts/*`，合稿 `final.md` 并 `present`（**成品只有 CEO 能写**，三态纪律） |

**为什么这样最省**：①③⑤ 全落在**既有三态形状**上（`deliverables-check` 照样能审）；②④ 是人之间
说一句话，不需要任何新结构。**别做的事**：给 `drafts/` 发明新文件名（如 `ceo-brief.md`——
`<角色>.md` 是约定，`ceo-brief` 不是角色）、或为"派活"造消息机制（那要动 client/server，用户已否）。

**已排练验证（2026-09-26）**：两个根会话（ceo + cfo，cwd = 排练场）跑了一遍上述协议——
CEO 门落任务书 `drafts/ceo.md` → CFO 门读它、出 `drafts/cfo.md`、写自己的 journal（文件名用
`日期待核-<slug>.md` 占位，日期口径也守住了）⇒ **PASS**。
**真盘首跑已完成（2026-10-04，firstdeal-v-2026）**：三扇门全链（CEO 派活不 spawn → CFO/COO 各自
根会话出稿 → CFO 半边 `request_signoff` 卡落 CFO 门、人经浏览器应答 allowed-once → CEO 半边卡落
CEO 门、人应答 → final + present）。判据与证据 = [E2E Note](../notes/implemented/2026-10-04-e2e-multihuman-firstdeal.md)。

## 4. 协作前提（多人在同一盘上必须先约定）

1. **slug 唯一性**——共享盘上 slug 就是交付物的键。开动议前先看 `deliverables/` 有没有同名；
   重跑要么换 slug，要么先归档旧产物。（实测撞车：两场动议共用 `renewal-y-2026` ⇒ 产物互相覆盖，
   而三态判据**看不出**；现已加观察项 `slug-collision` 每次提醒。）
2. **写入边界**——各自只写 `drafts/<角色>.md` + 自己的 `kb/<角色>/journal/`；`final.md` 只有 CEO 写。
   三态判据盯着"成品有没有 present 背书"，但**盯不住"是谁写的"** ⇒ 靠手册纪律 + 互审。
3. **同盘并发**——**"一个文件同一时刻一个写者"是本仓的流程政策，不是文件系统的保证**。
   机制实况（2026-09-26 复核；**2026-10-03 E1/E2 实测更新**，证据 =
   `notes/archived/2026-09-26-multi-human-ux-evidence.md` + 推敲卡 E1/E2 结论
   `_backlog/_done/_closed_plans/2026-09-29-collab-mechanism-evidence.md`）：
   - **有**：`fs-local` 的**实例内** per-target 排队锁 + 版本守卫（读过再写时版本变了报 `FS_STALE_VERSION`，
     "一胜一 stale"有官方测试）。**E1 实测（真角色会话 ×4 轮全绿，`scripts/fs-guard-probe.mjs`）**：
     守卫在角色会话真实生效——盲写既有文件被拒（`FS_NOT_OBSERVED`，模型被拒后重读重写）、stale 拒 4/4；
     **新机制事实：守卫管新鲜度不管独占**——并发同文件败者天然先读后合法重写 = 后写者静默胜出
     （机械拒只在败者恰好盲写时出现）；
   - **没有**：**跨进程 / 跨 `$DSH_HOME` / 外部编辑器**的共享租约——**E2 实测（真 fs-local × 2 进程）**：
     同版本守卫写 ×20 轮 20/20 双双成功互踩（守卫检查与发布间无跨进程原子性）⇒ 跨进程互斥的正解 =
     `dsh-atomic-write`（维护者/脚本侧）；**无版本期望的写仍是无条件原子覆盖**。
   ⇒ 产物分工（一角色一稿 / `final.md` 归 CEO / journal 归本人）**缩小了冲突面，但没有消除跨人并发**。
   交接靠"我写完了"的消息 + 文件本身；**"文件已存在"只表示有可读材料，不表示收到、认领、授权或完成**
   ——**唯一例外 = 占位抢注**（下条纪律 5）。

   **五条可核对纪律**（把"责任/版本"从口头变成**写在稿上、机器可查**）：
   1. **单稿负责人**——一稿一人，**写在稿首署名行**；
   2. **出稿回执**——"我写完了"落到自己的 journal（不只口头）；
   3. **CEO 合稿前确认**——用的是**哪一版**、还有谁没回稿（缺席如实写进 final 未决项）；
   4. **返工显式通知 + 新版本号**——改稿要能看出是哪一版，并知会合稿人；
   5. **占位=认领（R0-2，2026-10-03 立）**——要占坑就**开场**先落 `drafts/<角色>.md`，**首行一字不差**
      写「占位=认领，非出稿」（机器可查的抢注登记，`deliverables-check` 观察项 `PLACEHOLDER_CLAIMS` 盯守）。
      守卫的并发创建本就是一次性抢注（重写被拒）——这是原义不是障碍。占位稿仍是过程稿、非成品；
      真正出稿时**换掉占位首行**写正文。

   **署名行形状**（稿首引用行，机器可解析）：
   `出稿：<角色>｜版本 v<N>｜任务书 = deliverables/<slug>/drafts/ceo.md`；
   若稿经他人代笔后由本人复核收回署名，**必须**加一行
   `本稿由 <角色> 根会话复核并署名（首版系 <谁的会话> 代笔）`——
   真实先例：`deliverables/sea-reconcile-2026/drafts/cfo.md`。
   **机器核对** = `scripts/authorship-audit.mjs`（比对署名行与实际写入会话的 preset）。

## 5. 迁移清单（搬共享目录到真实多人环境）

**要搬的**（全是文件，无进程/账号状态）：

| # | 搬什么 | 为什么 |
|---|---|---|
| 1 | `company-workspace/` 整盘——`kb/`（CHARTER + journal + **owners.md** + org.md + motion-ledger.md）、`deliverables/`、`templates/`、`AGENTS.md`（公司手册） | 这是**真正的共享层**；协作全落在它上面 |
| 2 | `packages/company-pack/`（角色 persona/skills + bundle 行 + client 面） | 角色与规矩的来源 |
| 3 | `docs/` + `notes/`（当前合同与开发记忆） | 迁过去的人要能读懂"规矩从哪来" |
| 4 | 环境：DSH 本体（**同一 pin**）+ 各自的 `$DSH_HOME` | home **每台机器自己的**（会话库/凭据是本地的，不共享）。**多 home 三个已核事实（实验 D 配置 B 活体，2026-09-26）**：① 每家要**各自装 pack**（新 home 只有 factory preset，公司角色建不了门）；② 同一共享盘在两家**各落一个日志 bucket** ⇒ 审计（`deliverables-check` / `journal-audit` 按 `$DSH_HOME` 扫）**每家跑一遍**，只跑一家会漏另一家的会话；③ Agent Teams 消息跨 home 无寻址路径（进程内能力 + 双服务互不可见）——跨家协作只剩共享盘 |

**不能搬的**：`$DSH_HOME/sessions/`（会话日志是**运行时残留**、含机器专属路径）。
要留证据就按会话 id 归档到 `snapshots/`，别搬会话库。

**迁移后的第一件事**：把 `kb/owners.md` 的 `人甲/人乙/人丙` 换成**真名**（本仓是本地模拟映射）。

## 6. 边界（诚实说清，不假装是安全隔离）

- **"门"不是"人"**（2026-09-26 复核补）：门 = **承载一个会话上下文、模型工作与实时人机交互的位置**；
  它**不是**身份边界、权限边界，也不是话题本身。"看不到别人的门"≠"没有权限进"，
  "卡在哪扇门"≠"谁拥有授权"（授权唯一看 `owners.md`）。侧栏分组走 **workspace 实体**（`fs.realpath` 归一），
  所以**同一个真盘 = 同一个分组**，用路径别名**造不出**按人隔离。
- "谁该签"是**政策级**约束（写在 `owners.md` + 公司手册里，人和 agent 都照它走），**不是安全级**：
  同一台机器上谁都能按那个按钮。demo 阶段够用；真要多租户/安全隔离 ⇒ 另立条目并提上游 seam。
- **不做**：账号体系、权限模型、多服务、identity 扩展、answerer 路由插件（全部留到 MVP 且需上游 seam）。
- **client 侧"身份过滤"增强**（防"看得到但按不动"）= **红线**（要动 client 数据层），本轮**不做**、只留案；
  demo 期靠"人各守自己的门 + owners.md 纪律"成立。

## 7. 验收（本条目的完成定义）

（`deliverables-check` 0 违规 + journal 各自在场）；迁移清单随本合同交付；`pnpm verify` / `pnpm test` 保持绿。
**已完成（2026-10-04）**：firstdeal-v-2026 三扇门真盘动议——双签两半各落各门均人应答、
根会话归属 ✓×3（cfo/coo/ceo 各自会话写各自稿）、0 spawn、check 违规 0、journal 三在场。
证据 = [E2E Note](../notes/implemented/2026-10-04-e2e-multihuman-firstdeal.md)；快照 =
