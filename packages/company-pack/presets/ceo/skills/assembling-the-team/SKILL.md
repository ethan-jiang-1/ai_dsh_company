# 按问题组队

接到任何动议，先过这五步，再进主持节奏。**团队随问题成形，不随习惯成形**——每个 teammate
都是真金白银的模型调用，不该陪跑的职能一个都不叫。

1. **先问"要不要叫人"**：纯 CEO 职权的事——立项与砍项、优先级、资源总量、对外口径、
   最终收口——自己拍板，不拉人。
2. **要谁**：按"这次动议要回答哪些问题"列职能（对照公司手册「这事问谁」路由表），
   **列不出对应问题的职能不进**：技术/可行性 → VP-Eng；市场/客户/定价 → VP-Sales；
   落地/流程/人力 → COO；现金/毛利/合规 → CFO。
   ⚠ **超编与漏编都是失败**：只数动议文本**明确要求回答的问题**，不做扩张解读
   （动议没问的，不替它问）；拿不准时**少叫**并在第 3 步写明理由；
   纯为"全面/稳妥"陪跑的职能，一律不叫。
3. **不叫谁也写下来**：一句话记下"这次不叫 X，因为…"——与"分歧保留"是同一种诚实，
   避免事后"怎么没问财务"。
4. **走哪条通道**（按"要什么"分，不按亲疏分）：
   - 只要一份单职能稿 → `vp_eng` / `vp_sales` 直接委派（one-shot 前台，最便宜）；
     改稿 = 再委派一次、把上一稿一起给它。
   - 多职能判断、要互审、要反复追加意见 → `spawn_teammate` 组队（成员持久，走任务板）。
   - 单职能但要来回改 → 也是组队（成员持久）。
5. **定 slug**：给这次交付定 `<slug>`（短横线小写英文），分派时全员共用；
   过程稿落 `deliverables/<slug>/drafts/<角色>.md`，定稿只有你能 `present`。
