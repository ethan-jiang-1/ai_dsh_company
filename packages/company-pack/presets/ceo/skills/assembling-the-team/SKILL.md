# 按问题组队

接到任何动议，先过这六步，再进主持节奏。**团队随问题成形，不随习惯成形**——每个 teammate
都是真金白银的模型调用，不该陪跑的职能一个都不叫。

1. **先问"要不要叫人"**：纯 CEO 职权的事——立项与砍项、优先级、资源总量、对外口径、
   最终收口——自己拍板，不拉人。
2. **要谁**：按"这次动议要回答哪些问题"列职能（对照公司手册「这事问谁」路由表），
   **列不出对应问题的职能不进**：技术/可行性 → VP-Eng；市场/客户/定价 → VP-Sales；
   落地/流程/人力 → COO；现金/毛利/合规 → CFO。
   ⚠ **超编与漏编都是失败**：只数动议文本**明确要求回答的问题**，不做扩张解读
   （动议没问的，不替它问）；拿不准时**少叫**并在第 3 步写明理由；
   纯为"全面/稳妥"陪跑的职能，一律不叫。
3. **能力盘点（先于拆活）**：动议里有没有"要读外部网页 / 拿外部事实"的任务？有 ⇒ 先打一发**能力探针**
   （一次 `web_search` + 一次 `web_fetch`）：本部署 fetch 对一切域名被沙箱 DNS 拦截、搜索只回标题 ⇒
   **外部正文取不到 = HITL 事**——探针判死就先向人发补料卡（料落 `deliverables/<slug>/drafts/sources/`），
   依赖外部事实的任务标**「待补料」**、不许标完成，**不许带着"未核实"分解派活**（手册「事实阻塞闸门」）。
4. **不叫谁也写下来**：一句话记下"这次不叫 X，因为…"——与"分歧保留"是同一种诚实，
   避免事后"怎么没问财务"。
5. **走哪条通道**（按"要什么"分，不按亲疏分）：
   - 只要一份单职能稿 → `vp_eng` / `vp_sales` 直接委派（one-shot 前台，最便宜）；
     改稿 = 再委派一次、把上一稿一起给它。
   - 多职能判断、要互审、要反复追加意见 → `spawn_teammate` 组队（成员持久，走任务板）。
   - 单职能但要来回改 → 也是组队（成员持久）。
6. **定 slug**：给这次交付定 `<slug>`（短横线小写英文），分派时全员共用；
   过程稿落 `deliverables/<slug>/drafts/<角色>.md`，定稿只有你能 `present`。

> **边界**：本 skill 是 guidance，不是 checklist——提供稳定入口与判断标准，判断留给执行者；
> 命中本 skill 时**先读全文再执行**，不从 description 摘要猜。可机械核对的部分归仓库的门禁/审计脚本
> （如署名行 = authorship-audit、交付物三态 = deliverables-check），本文只留需要上下文判断的部分。
