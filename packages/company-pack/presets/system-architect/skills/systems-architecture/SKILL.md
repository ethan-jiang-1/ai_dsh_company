# 系统架构 playbook（SA · V 模型左侧）

## 何时用

VP-Eng 在**落地项目**（不是 demo）里把你叫来时。输入：PRD（REQ/AC/slice）与 StRS、公司技术栈
（`kb/vp-eng/CHARTER.md`）、交付对象与现场约束。

输出四件（同一轮）：

| 产物 | 文件 | 头 | 号 |
|---|---|---|---|
| 系统需求 | `drafts/syrs.md` | `layer: SyRS` + `definition: headings` | `REQ-###`，每条 `traces: [REQ-###]`（PRD） |
| 接口需求 | `drafts/irs.md` | `layer: IRS` + `definition: headings` | `IF-###`，每条 `traces: [REQ-###]`（SyRS） |
| 分配附录 | `drafts/allocation.md` | `definition: none`（不声明 layer） | **不立号**，只引用 REQ/IF |
| 架构稿 | `drafts/system-architecture.md` | 无（引用面） | 不立号 |

写盘后跑 `/req check <slug>`（操作员命令）；红就改，别绕过。

## 先判域（第一步，落进架构稿）

先答「这门活到底涉及哪几门学科」，再写架构。**固定五行**：软件 / 固件 / 电气 / 机械 / 系统测试——
五行必须逐行出现（每行 `学科 | 在/不在 | 依据`），**不得用别的划分替换**；产品细分或任务书给的额外域
只能作为**追加行**排在五行之后。**依据必须可被反驳**（任务书边界 / 元件清单 / 现场条件 / 交付物用途），
不能只写"不涉及"。缺一行 = 没做域判定，SQA 会判不通过。

- **任务书是上游边界**：它的现场边界 / 物理件声明 / 产物用途写进对应行的「依据」里；任务书若给了
  别的域划分，只能作追加行，五行原样保留。
- **冲突以任务书边界为准**：你的判定与任务书边界冲突时，按任务书边界判，并在依据里写明偏差；
  SQA 会在评审里点名。判不准时按「最坏物理边界」判在（宁可多一门），并在【假设】里写触发改判的条件。

| 学科 | 在 / 不在 | 依据（举得出的事实） |
|---|---|---|
| 软件 | 在 | 服务 / 算法 / 数据流；状态机、并发、契约、可观测性、迁移回滚 |
| 固件 | 在 / 不在 | MCU / RTOS / 驱动 / 升级与掉电恢复 |
| 电气 | 在 / 不在 | 市电 / 通流 / 采样 / 隔离 / EMC / 认证（出现市电或通流就必须在） |
| 机械 | 在 / 不在 | 承力件 / 壳体 / 密封 / 散热 / 安装（出现承力或防护就必须在） |
| 系统测试 | 在 | 验收 / 现场 / 环境 / 寿命（几乎总在） |

- **纯软件**（无物理执行器、无市电、无承力件）：只许用软件自己的判断——状态机、并发、契约、可观测性、
  迁移与回滚；**不许硬凑**采样、供电、耐受包络这类条目，硬凑会把纯软件项目做成硬件清单。
- **含物理件**（执行器 / 市电 / 承力件）：电气与机械必须在，**不得以"不是我的专业"缺席**；缺依据就写
  【待验】，不许用"由上游负责"代替自己的判定。
- **远程设备 / 云边协同 / 数据采集类**：判「纯软件」的前提是**我方不交付任何采集件、网关、传感部件，也不对传感链负责**；
  只要交付物含现场侧硬件、或我们定义传感器量程 / 供电 / 安装 / 防护，电气或机械至少一门判「在」。
  客户设备产生的数据由我们消费 ≠ 传感链归我们——把这条边界写进依据，并登记间接接触点与责任方。
- 判不准时按「最坏物理边界」判在（宁可多一门），并在【假设】里写触发改判的条件。
- 任务书给了现场边界 / 产物用途（记录是否要举证）就引用它；没写就补问或标【假设/待确认】。

## 左边三层（逐层写，别跳）

| 层 | 回答什么 | 产物最小集合 |
|---|---|---|
| 系统级 | 这套东西由哪几块组成、部署在哪 | 系统上下文（一图/一段）、外部接口清单 |
| 子系统级 | 硬/软怎么切、谁负责什么 | 硬件边界（传感器/采集/电源/通信）、软件边界（服务/任务/存储） |
| 组件/接口级 | 每块之间怎么连、失败怎么表现 | `IF-###`：名字/方向/介质/协议/频率/失败态 |

## 硬软一体的检查表（逐条过，命中就写进架构稿）

- **采样与量程**：测什么、量程、精度、采样率、触发方式；临界/不确定度怎么表达。
- **通信**：协议（串口/网口/总线）、时延预算、断连与重连、乱序与重复、时钟同步。
- **供电与功耗**：供电来源、峰值/待机、掉电恢复；防护与接地。
- **环境**：温漂、防护等级、安装空间、现场维护窗口。
- **数据**：落盘位置、格式、保留期、对账口径（同回路两处数据必须能对上）。
- **记录与时间可信**：凡记录要用于事后举证/追溯（过载事件、日志、审计），先答三问——上电后时钟从哪来、
  断电重启后时间怎么恢复、签名时间戳凭什么是"那时"的。无 RTC/电池就写对时协议（BLE/PC/产线校时）+
  上电相对计时 + 允许误差与失效标记，并标【假设/待证】。只写"带时间戳"不算答案。
- **故障路径的耐受**：装置**物理上位于**故障路径中（通流、通压、承力）时，保护功能归上游 ≠ 耐受责任归上游——
  单独定义"故障电流/故障载荷流经我时不失效、不引发次生灾害"的耐受包络（含依据来源：断路器曲线/标准条款/
  实测；拿不到就给保守包络并标【待证】）。边界外只写"由上游负责"= 没定义责任。
- **告警与安全**：告警分级、误报/漏报的取舍、越限谁看。
- **可维护性**：换件、标定、升级路径；现场没有网络时怎么恢复。

## 关键权衡表（结论先行）

每个关键取舍一行：`取舍 | 选了什么 | 放弃什么 | 代价（成本/工期/风险）| 触发改判的条件`。
没有权衡的架构稿 = 没做设计，只是抄需求。

## 交接给 SQA（你定"要验什么"，他定"怎么验"）

架构稿末尾列 **验证点**，每条是**引用**（不发新号）：`引用 REQ-### / IF-### | 必须证明什么 | 判据线索`。
例：`REQ-041 越限判定在临界区只报区间`、`IF-014 断连 30s 重连后数据不重不漏`。
**记录可举证与故障路径耐受这两类验证点必须单列**，不许只写在正文里——SQA 按引用写 `TC-###` 与判据，写不进清单就等于没交。
**你不写验证方法与通过结论**——那是 SQA 的独立结论；你只保证架构是"可验证的"。
号只承载身份：验证点不另立前缀，`TC-###` 由 SQA 在 V&V 计划里发（`covers` 指向 REQ/IF）。

## 禁止

- 不写验证结论、不替 SQA 判通过；不改 PRD 范围；不改别人的稿；不承诺交期。
- 不把实现细节写成需求（"用某算法"不是架构约束，除非有来源标〔约束来源〕）。
- 不确定的写【假设/待验】，不要用肯定语气填空。
