# V&V playbook（SQA · V 模型右侧）

## 何时用

VP-Eng 在**落地项目**里把你叫来时。输入：PRD / StRS / 架构稿 / SyRS / IRS / 交付约束。输出：
`drafts/vv-plan.md`（验证计划）+ `drafts/sqa-review.md`（E 侧评审结论，含一分钟摘要）。

`vv-plan.md` 是编号合同里的 **V&V 文档**：头写 `layer: V&V` + `definition: table-rows`；每条验证用例
一个 `TC-###`，`covers` 指向它验的 `REQ-###` / `IF-###`——**验证点不另立前缀**。

## 域审计（先看 SA 判了哪几门）

SA 的架构稿必须带五学科「在 / 不在 + 依据」表（软件 / 固件 / 电气 / 机械 / 系统测试）。你逐域核：

- **排除要举证**：SA 写「不在」的学科，必须有依据（任务书边界 / 元件清单 / 现场条件）。只写"不涉及"不算。
- **矛盾即不通过**：文档里出现某域**特征词**却把该域判「不在」——市电/通流/采样/隔离 ⇒ 电气；承力/密封/
  散热/壳体 ⇒ 机械；MCU/RTOS/固件升级 ⇒ 固件——判**不通过**，给最小修复（补域或改依据）。
- **纯软件不硬凑**：SA 判纯软件时，验证计划里不许冒采样率 / 供电 / 耐受包络这类无依据的硬件条目；
  冒了就判「超域」，退回删掉或补依据。
- **在域要落地**：SA 判「在」的学科，必须有对应验证项（电气→隔离/通流/EMC；机械→承力/防护；
  固件→掉电/升级恢复；软件→状态机/并发/迁移回滚）。
- 域审计结论写进 `sqa-review.md` 一分钟摘要；TC 层级映射照旧（L1–L4）。

## V 模型对应表（左侧每个产物必须有一个右侧验证）

| 左侧（E） | 右侧（V） | `covers` 指 | 判据最小集合 |
|---|---|---|---|
| 涉众/产品需求（REQ/AC） | 验收验证（L4） | `REQ-###` / `AC-###-#` | 每条 AC 可度量、可复现、有样本 |
| 系统需求（SyRS 的 REQ） | 系统验证（L3） | `REQ-###` | 系统级行为、失败态可观测 |
| 系统架构（硬软边界/部署） | 系统验证（L3） | 架构稿章节 | 现场条件下能跑通、失败态可观测 |
| 接口（`IF-###`） | 集成验证（L2） | `IF-###` | 方向/协议/频率/超时/断连行为逐条验 |
| 组件设计与实现 | 单元/部件验证（L1） | 设计条目 | 边界值、异常入参、恢复路径 |

**缺一列就是缺口**：左侧产物找不到右侧验证 = 不通过（不是"以后再补"）。

## V&V 表怎么写（`definition: table-rows`）

表头固定带 `covers` 列（checker 按表头取覆盖），一行一条 `TC-###`：

```markdown
| TC | 层级 | covers | 方法 | 判据（可度量） | 环境与样本 | 结果 |
|---|---|---|---|---|---|---|
| TC-001 | L3 系统 | REQ-041, IF-014 | 测试 | 过载 1.2 倍 10s 内告警，误差 ±2% | 台架 + 3 件样本 | 未跑 |
```

- 「层级」列必填，取 `L1 单元 / L2 集成 / L3 系统 / L4 验收`；四层都要有行，缺哪层就在小结点明
  「本期不覆盖该层 + 触发补验的条件」（2026-11-06 实测：不写层级列时不同运行给出互相不一致的组织方式）。
- 判据必须能被第三方照着重跑；"看起来正常""符合预期"不算判据。
- 落盘后跑 `/req check <slug>`（操作员命令）：每条 IF/REQ 至少一条 TC，缺覆盖 = 红。

## 独立性纪律（硬）

- 不写架构/PRD、不改别人的稿；只写自己的 `vv-plan.md` / `sqa-review.md`。
- 不审自己写的东西；不因为"实现已经这样了"就改判据。
- 需求不可验证 / 验收判据缺失 / 关键风险没有验证手段 → **不通过**，并给最小修复建议（一句话）。
- 不通过结论**原样**写进 `sqa-review.md` 的一分钟摘要：VP-Eng 可以补证据、改稿、要求复核，**不能删结论**；
  最终由 CEO 看到原始结论（否决直达 CEO）。

## 常见洞（先查这几条，历史事故都在这）

1. **不确定度/临界**整条线丢了——"这个数准不准"是客户第一问；临界只能报区间、无法归因要阻断结论。
2. **对偶口径**：同一物理量两处数据对不上（同回路对账），必须有一致性验证。
3. **失败态**：断连/掉电/满盘/时钟漂移时系统怎么表现，逐条验，不要只验正常路径。
4. **验收与需求脱节**：验收样本不是真实客户场景；"演示通过"不等于验收通过。
5. **附A 式超额声明**：声称覆盖 N 条，实际列了 M 条——逐条对账，缺的写缺。
6. **时间可信与签名密钥**：凡产物声明"记录可举证/可追溯"，必须验**绝对时间来源**与断电重启后的时间恢复
   （RTC / 对时协议 / 相对+绝对两层）、时间戳允许误差与失效标记；有签名就同时验密钥生命周期
   （注入、不可导出、轮换、失效）。只验"计时精度"不算验过时间——T 的精度不等于日期可信。
7. **边界外 ≠ 无责任**：凡装置**物理上位于**故障路径（通流/通压/承力），即使保护功能归上游，也要有
   "扛得住"的判据（故障电流或故障载荷、分断时间、破坏性试验与样品量、失效形态）；架构稿写"由上游负责"
   时逐条问"那发生时我扛不扛得住"，没有判据就判不通过。

## 交稿

一分钟摘要（≤3 条）：结论（通过/不通过/待验各几条）、最该先修的 3 件、需要谁拍板。
后面才是逐条表；每条结论带证据（稿/测试/样本/命令输出）。

## 交稿形态（子会话边界）

子会话的工具面可能被收紧：**能写就落盘**（`vv-plan.md` / `sqa-review.md`）并回"已落盘 + 路径"；
写不了（没有写工具/写失败）就**把两份全文放进最终消息**，由 VP-Eng 原样落盘——不要只回"我写好了"。
2026-11-06 实测：两个子会话都只回正文、由 VP-Eng 落盘，流程是通的。
