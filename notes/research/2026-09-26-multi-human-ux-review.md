# 2026-09-26 · 多人协作 UX 提案评审与实验建议

状态：**研究结论**。本稿评审 [多人 UX 提案](../implemented/2026-09-26-multi-human-ux.md)，不直接批准其中任何实现方案。DSH 一手机制证据见 [多人 UX 一手机制证据](./2026-09-26-multi-human-ux-evidence.md)；当前多人合同见 [docs/multi-human.md](../../docs/multi-human.md)。

## 一、结论先行

提案最有价值的部分，是把现场反馈拆成 L1“门”、L2“对齐”、L3“并发”三个症状入口，并主动记录了多个真实踩坑：默认 preset 造成错署名、实时卡刷新后不可答、任务书交接没有载体、共享 slug 会混装。这些观察成立，值得保留。

但“三层正交”还不够。提案把**会话容器、物理人、角色、授权、话题、任务、产物、通知、签署和生命周期**压缩成了门/对齐/并发三个问题，因此几处结论会越过证据：

- “侧栏看不到别人的门”不等于身份隔离、权限隔离或“这属于我”。
- “没有某角色的 draft”不等于该角色有待办；“有 draft”也不等于任务完成。
- “一文件一写者”目前是协作政策，不是文件系统自动保证的事实。
- symlink 的日志 bucket 观察不能推出 Web 侧栏按人分组；官方 workspace 实现反而会把同一真盘的 symlink 归一到同一个 workspace。
- “DSH 无锁”表述过宽。DSH 有单个 `fs-local` 实例内的目标文件排队和版本保护，但没有跨进程、跨 home 的共享文件租约。

因此本轮建议：**不采用 L1-C，不把 L2 的扫盘结果直接命名为“我的待办”，不把 L3 写成“无需并发控制”；先做行为实验，再决定是否增加结构化派活字段或上游 seam。**

## 二、先把 DSH 的实际边界说准确

### 1. 门不是人

DSH 没有账号体系；客户端连接、会话和 agent 不是物理人的身份模型。当前合同也明确说“人”这一层不存在，授权主要由本仓 `owners.md` 和手册作为政策执行，而不是安全隔离（[docs/multi-human.md:9-17](../../docs/multi-human.md)、[docs/multi-human.md:124-129](../../docs/multi-human.md)）。

DSH 的 root/child 区分是**运行时所有权**：自己开的根会话可以进入问询路由；被委派的 child，包括 Team teammate，不能直接问人。委派时 approval policy 也会被设置为 `never`。这解释了“自己的根会话”和“CEO 动议里的成员会话”为什么必须分开说，但它仍不是物理人身份或业务授权（[一手机制证据:13-19](./2026-09-26-multi-human-ux-evidence.md)）。

所以，“门”应定义为：**承载一个会话上下文、模型工作和实时人机交互的位置**。它不是“谁的门”、不是权限边界，也不是话题本身。

### 2. 侧栏按 workspace，不按日志 bucket

提案 L1-C 的实测只证明会话日志的持久化路径保留了 cwd 的字面写法。官方 workspace 以 `fs.realpath` 作为唯一规范，同一真盘的 symlink 会复用原 workspace；Web 侧栏再按 workspace 实体的 `workspaceId` 和 `sessionIds` 分组（[一手机制证据:5-11](./2026-09-26-multi-human-ux-evidence.md)）。

这直接反证了“symlink cwd ⇒ 每人一个侧栏分组”。从提案的示例目录出发向上两级，实际只到仓库的 `dev/` 子目录，而不是根目录的共享盘；即使把路径修正，也不能改变 workspace 的 realpath 归一语义。

L1-C 不应再作为当前方案。若未来要测试路径别名，也只能把它称为**视图聚焦实验**，不能称为门隔离、身份隔离或权限隔离，并且必须同时观察日志路径、workspace/UI、沙箱写入和审计扫描四面。

### 3. 卡是实时交互，不是可刷新的收件箱

审批的 `asked/decided` 事件会写入请求 agent 的会话日志，但浏览器可回答的审批和问询卡来自实时 waterfall 事件及客户端内存中的 Pending 对象。持久审计不等于刷新后还能答，也不等于离台后有人收到（[一手机制证据:21-25](./2026-09-26-multi-human-ux-evidence.md)）。

因此提案“不要依赖实时事件、改从盘上状态推导”的动机是对的，但它最多解决**回来以后发现候选工作**，不解决通知送达、已读、认领、时效和升级。候选发现、个人收件箱和签署路由必须分开命名。

### 4. 并发能力有作用域

`fs-local` 对同一实例、同一 canonical target 有进程内排队；带版本期望的 guarded write/edit 在版本变化时会返回 `FS_STALE_VERSION`，官方测试覆盖了“一胜一 stale”。但这个 Promise Map 不跨 DSH 进程、`$DSH_HOME` 或外部编辑器；无期望的写仍是原子覆盖（[一手机制证据:27-31](./2026-09-26-multi-human-ux-evidence.md)）。

所以 L3 的正确说法是：**产物分工可以降低冲突面，但没有消除跨人并发问题。** 这足以支持 demo 期不自造锁，但不足以声明共享写者不存在。

## 三、哪些判断对，哪些需要改

### L1：门的边界

**成立的判断：**用户看到同一 workspace 下所有会话，难以知道自己该停在哪扇门；默认 preset 是 CEO 导致错署名；客户 UI 的“可见”与“可操作”需要分开；当前 demo 不应自行造账号、权限或 client/server 身份层。

**需要撤回或降级的判断：**

- 真实[sea-reconcile 任务书:3、14](../../company-workspace/deliverables/sea-reconcile-2026/drafts/ceo.md)先说明各角色在自己的根会话工作，随后却说“成员不得自行发起 `request_signoff`，升级 CEO”，与[多人合同 §0](../../docs/multi-human.md)规定的根会话由本人发起直接冲突。这不是措辞小误差：它会使 CFO 的签字请求落在 CEO 的门上。提案没有把**请求发起者、业务授权人、实际应答者、双签证据**分开；在解决这组语义前，不应声称“谁该签的卡落到谁的门”或从卡片位置推断双签成立。
- L1-C 的 symlink 分组隔离被官方 workspace/UI 实现反证。
- L1-B 不是“今天可直接迁移而且天然正确”。多 home 更接近真实多机部署，但会带来独立 session store、独立服务和 Team 不能跨进程协调的问题；跨 home Team 不通目前是强机制推断，尚未做双服务活体实验（[一手机制证据:13-20](./2026-09-26-multi-human-ux-evidence.md)）。
- “各人只看到自己的门”即使在某种 UI 过滤下成立，也只能是**注意力视图**，不能让用户推断自己没有权限进入、别人不能代签，或某份稿的作者已被系统核实。
- D 的命名约定有用，但只是检索辅助，不是归属模型。E 才接近长期产品 UX，但目前红线可以保留。

**当前建议：**demo 继续使用一个服务、每个物理人维护自己的根会话和角色命名；把“当前会话 / 角色 / preset / 物理人”同时展示或写入开门检查。不要用 symlink 伪造隔离。若以后要做真实多人部署，单独评估多 home 与外部共享层，不把它当成 L1 的 UI 小技巧。

### L2：话题对齐与待办

**成立的判断：**在没有跨根会话内置消息的前提下，共享盘是当前最现实的交接媒介；从持久文件状态恢复“可能有工作”比依赖刷新即丢的实时卡可靠；真正的上游方向是按角色路由通知或收件人。

**核心问题：**提案把“候选工作重建”直接叫成“我的待办”。真实 `sea-reconcile-2026` 任务书同时包含 T1–T4 首稿和依赖“四稿齐了”后才开始的 T5–T7 互审；现场只有 CEO/CFO/COO 首稿和 final，VP-Sales/VP-Eng 缺稿，但 final 明确记载这是缺席收口、互审未发生（[sea-reconcile final:1-5](../../company-workspace/deliverables/sea-reconcile-2026/final.md)、[sea-reconcile final:52-58](../../company-workspace/deliverables/sea-reconcile-2026/final.md)）。简单规则会同时产生三种错误：

1. 把已关闭动议的历史缺稿报成新待办；
2. 把已完成首稿但仍有依赖的 CFO/COO 报成已完成；
3. 漏掉互审、返工、取消、审批、口头补料和“由他提出意见但不写稿”的任务。

自然语言“点名”还存在否定、条件、引用、旧版任务书、引用他人结论和同一角色多任务等歧义。缺稿扫描不能推出认领、授权、作者、完成或需要立即打断的人。现行交接协议仍明确要求人对人通报（[docs/multi-human.md:76-87](../../docs/multi-human.md)）。

**正确的产品命名：**第一阶段应叫“共享盘中的待核工作候选”或“发现到的可能任务”，而不是“待我处理”。候选项必须带：`slug`、任务书版本、任务编号、原文引用、角色/物理人映射、预期产物、依赖、发现时间和“待核实”标记。它不能自动宣称“已指派”“已接单”“已授权”“已完成”。

**可以尝试的最小结构：**不先造 `ASSIGN.md` 新事实家，可在现有 `drafts/ceo.md` 任务书中加入一小段机器可读的派活行，例如任务编号、责任角色、输出、依赖、状态和任务书版本。先用实验验证这段字段是否真的减少误报，再决定是否需要独立任务载体。关键是把“任务状态”从“文件存在与否”中分离出来。

### L3：并发可见性

**成立的判断：**按角色拆分稿件、限定 CEO 写 `final.md`、让每个人写自己的 journal，能显著减少同一文件的正常冲突；demo 期不应因为一个尚不存在的跨人租约而发明复杂锁机制；mtime/内容可以作为辅助可见性。

**需要改写的判断：**

- `drafts/<角色>.md` 的路径不是作者证明。同一角色可以由多人承担；同一人可以开多根会话；错选 preset 已经造成 CEO 会话代写 CFO 稿；`journal-audit` 检查在场，不检查署名。
- 任务书、`owners.md`、`motion-ledger.md`、同一 slug 的多个交付物和 CEO 合稿仍可能有多个写者。
- mtime 不能证明写完、已读、无冲突或合稿所依据的是最新版本；跨机器时钟还会进一步削弱它。
- git 可以在分支/克隆工作流中暴露冲突，但不会自动成为共享目录上的锁。

**当前建议：**继续不造 `.lock`，但把“一文件一写者”从“形状保证”降为“流程政策”，并补四条可核对纪律：单稿负责人、出稿回执、CEO 合稿前确认版本和未决项、返工时显式通知与新版本号。能使用 DSH 文件工具时，优先保留读后写和版本 guard；不要把它误写成跨人的写入租约。

## 四、需要补上的概念模型

三层可以作为问题入口，但设计时至少要分开以下对象：

| 对象 | UX 要回答的问题 |
|---|---|
| 物理人 | 谁在值守、谁实际点击、谁在当前班次可联系？ |
| 角色与授权 | 这个人代表哪个职能，能答什么、建议什么、批准什么？ |
| 门/会话 | 当前模型工作在哪个上下文，实时卡从哪里发出？ |
| 动议/话题 | 哪些会话、任务和产物属于同一项工作？什么时候关闭、归档或重开？ |
| 任务 | 谁负责什么，依赖、验收、返工和取消条件是什么？ |
| 产物/版本 | 哪个稿件由谁提交，是否被评审、采纳、替代或发布？ |
| 注意力/通知 | 谁需要知道，是否送达、已读、待回应或逾期？ |
| 权限/签署 | 谁可以决定，谁实际签了，决定对应哪个版本？ |
| 并发/生命周期 | 状态怎样跨人、跨会话、跨时间保持一致？ |

尤其要把 `slug` 从“动议唯一运行 ID”中解耦。现在 slug 是 `deliverables/<slug>/` 的文件目录键；同 slug 两场动议已经混装且三态仍通过（[multi-human-role-routing:190-201](../implemented/2026-09-26-multi-human-role-routing.md)）。未来若要把多个会话聚合成“一个话题”，需要一个明确的动议运行身份和生命周期，不能只依赖目录名。

推荐的状态维度也应彼此独立：

- 动议：`proposed → active → blocked/paused → closed → archived/reopened`；
- 任务：`offered → acknowledged → in_progress → submitted → review/rework → accepted/cancelled`；
- 产物：`draft → revised → reviewed → adopted/rejected`；
- 注意力：`unread → seen → answered/deferred/expired`；
- 审批：`pending → approved/rejected/expired`。

这些是 UX 语义模型，不表示现在就要把所有状态做成新文件或新 client 数据层。它们的作用是防止用一个 `final.md`、一次 `present` 或一条实时卡替代所有问题。

## 五、实验顺序与判据

### 实验 A：冷启动可发现性

安排三位物理人分别打开自己的根会话；由一人创建动议，第一轮不口头通报，第二轮加入现行“CEO 那边派了 `<slug>`”通报。分别测：首次发现时间、发现率、能否说出下一步、是否打开了正确 preset、离台后回来是否还能恢复上下文。

**判据：**任何关键审批、取消或截止事项不能因为“扫盘未触发”而静默遗漏；若用户把“列表看不到”理解成“没有权限”，路径分组方案不能进入 demo。

### 实验 B：任务书扫描的精确率与召回率

取 10–20 份真实任务书和人工变体，覆盖：否定、条件、引用、互审、返工、取消、旧版本、同角色多任务、已关闭动议和缺稿但有 final。由人先标注任务级金标准，再比较：纯文件存在规则、结构化派活行、结构化派活行加动议状态。

分别统计任务召回率、精确率、错误“已完成”数、错误“需立即处理”数。**审批、取消、阻塞依赖的漏报零容忍**；没有达到门槛前，扫描只能显示“待核候选”，不能进入个人待办或自动通知。

### 实验 C：签署、署名与版本穿透

覆盖 CEO 任务书、CFO/COO 首稿、互审依赖、CFO 返工、CEO 提前合稿、角色缺席、默认 preset 错选和双签。逐项记录：实际发起 agent、物理人、preset、稿件作者声明、审批者、审批对应的稿件版本、最终 `present` 的会话。

**阻断条件：**任何一次错误签署、把卡所在门当授权判定、把缺稿当完成、或把 CEO 代写误计为角色署名，都会否定“仅靠文件形状即可证明归属”的说法。

### 实验 D：门的心智模型

分别测试普通共享 workspace、路径别名、不同浏览器 profile 和独立 `$DSH_HOME`。同时观察四面：Web 侧栏/workspace、会话日志 bucket、实际沙箱写入、`journal-audit`/`deliverables-check` 扫描。再测试互发链接、刷新、关闭后重连和把别人路径直接粘贴进工作区。

**判据：**任何方案若让用户误以为“看不到 = 没权限”“同一真盘 = 个人私有”“卡在哪扇门 = 谁拥有授权”，就只能作为内部实验，不作为多人 UX 合同。

## 六、建议的决策顺序

1. **立即撤回 L1-C 的隔离结论。** 保留其 bucket/审计漏扫作为技术债观察，不再把它当 UI 方案。
2. **把 L2 改成候选发现实验。** 先验证结构化派活行是否必要；在实验前不自动扫自然语言任务书生成个人待办。
3. **保留当前共享盘交接协议，但明确它是人工交接。** “文件已存在”只表示有可读材料，不表示收到、认领、授权或完成。
4. **把 L3 改写为“冲突面缩小 + 版本纪律”。** 继续不自造跨人锁，同时承认 DSH 进程内锁与跨进程缺口，并验证合稿/返工场景。
5. **将上游 seam 单独记录，不在本仓模拟身份。** 长期真正解法是按角色/授权路由人机请求、持久化可恢复的 attention inbox，以及可配置的 delegated approval policy；当前只保留复活条件。

一句话总结：**当前 DSH + 共享盘可以提供共同上下文和人工交接，也可以在文件上重建“可能有工作”；它还不能提供个人收件箱、授权证明、签署证据或跨进程并发完成语义。** 设计重点应从“怎样把别人的门藏起来”转向“怎样让责任、状态、版本和需要人介入的事项可核对”。
