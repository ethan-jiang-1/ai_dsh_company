# 2026-09-25 · 人机合一：物理人 ↔ 分身（配对、四类接口、不在场策略）

状态：proposed（2026-09-25 用户口述需求登记；**分两批：内容层先做，机制层待升 pin 之后**——2026-09-25 用户排定）

## 问题

Agent ↔ Agent 这一层已经通了：团队成型、汇报线、任务板、在场板、升级中继都在跑，用户判断"Agent 之间
的协作没什么问题"。真正缺的是**物理人 ↔ 分身**这一层。

现状只有两个点 + 一个单人形状：

- **审批闸门**（`request_signoff` → `ctx.approval`）：一次性、轮内有效、**无应答 fail-closed**，事件对
  `approval/asked` + `approval/decided` 入日志，浏览器官方 `ui-approval` 应答，注意力中心跨会话显示
  （[cockpit-human-loop](../implemented/2026-09-24-cockpit-human-loop.md) 切片二）。
- **问人两条路**（手册明文）：动议内成员用 `send_message` 升级 CEO 带【待澄清】前缀、**不直接问用户**；
  独立会话（无动议上下文）直接用 `ask_user_question`。五个 preset 均已挂 `tool-ask-user`。
- **收件人模型 v1 = 单操作者**：条目带 `owner` 字段但全部路由到唯一操作者；多人在数据模型上不堵死，
  但**人这一侧没有被建模**——`kb/org.md` 是 50 人数字编制，"哪个物理人对应哪个角色"没有事实家。

用户要的是**人机合一**：CFO 的数字分身能做部分事，但要能问物理的 CFO"你补充资料 / 给 approval /
给建议"，**尤其规矩不知道的时候**。逐类对照，缺口是四类接口里只做了两类的一半：

| 人机接口 | 现状 | 缺口 |
|---|---|---|
| 要审批（阻塞型） | 有（一条最经营线 + 双签线） | 未分层：哪些必批 / 哪些可事后告知 / 哪些自主，没明文 |
| 问询（阻塞型） | 有（两条路 + 注意力中心四类条目） | 收件人只有"唯一操作者" |
| **要资料**（"你补充资料"） | 无载体 | 人交文件 / 补数据的回路未核实、未约定 |
| **要建议**（"还是听物理的 CFO 给建议"） | 无载体 | 非阻塞、非审批的轻量回路没有家 |
| **规矩不知道** | 无路径 | 手册 / CHARTER 未覆盖时该问谁、裁决如何**回流成规矩**，没有规矩 |

## 分批与依赖（2026-09-25 用户排定）

**为什么分两批**：升 pin 会**重写 preset 声明**（`agent.cordis.yml` 形状）与 **client 数据层**
（`remote.agentTeams` → 投影），而人机合一的机制层恰好要动这两处 ⇒ 机制层若先做，升 pin 时同一批文件
要迁两次。内容层（事实家 + 手册规矩）不依赖新基座，先做，且**机制没到位时以"退化形状"执行**（见下），
不产生返工。

- **内容层（先做）**：A1 人侧建模、A2 规矩落地进手册 / CHARTER / skill。**不动机制、不动 client。**
- **机制层（升 pin 之后做）**：B1 收件人路由、B2 三类接口载体、B3 不在场机制化、B4 证据与回看。
  前置 = [pin-upgrade-0.1.7-rc.2](./2026-09-25-pin-upgrade-0.1.7-rc.2.md) 落地。

## 方案 · 内容层（A，先做）

1. **A1 · 人侧建模**：新增"角色 → 物理人（多对多）+ **授权面**（能批什么 / 能答什么 / 只给建议）"的
   事实家——`kb/owners.md` 新文件或 org.md 增节，实施时按"一处事实一个家"择一。**必须先定授权面**：
   本仓现实是一个物理人养五个角色，只定"归属"会让路由对了、权限还是错的。
2. **A2 · 规矩落地进手册**（把四类接口的**规矩**先钉住，等机制跟上）：
   - **审批三档**明文：**必批**（对齐全仓已生效的两条签字线）/ **可事后告知** / **自主**；避免"要么
     全闸、要么全放"。第一版只把已生效的签字线落进"必批"档，其余先观察再收。
   - **规则缺口路径**：手册 / CHARTER / skill 都没覆盖时 ⇒ 按 A1 的授权面问人 ⇒ 人的裁决**回流**
     （改手册 / CHARTER 或登记磨清单，带取代检查）⇒ journal 留痕。这是组织学习闭环，也是"培养"的
     输入源之一。
   - **不在场纪律**（阻塞/非阻塞分档）：阻塞型（审批 / 裁决）保持 fail-closed，把事项写进稿件未决项；
     非阻塞型（建议 / 补料 / 规矩缺口）允许带**显式默认假设**继续，假设写进稿件与未决项，人不回来
     **不假装已答复**。
   - **退化形状**（机制未到位时怎么执行，必须写明）：补料 = 人写文件进共享盘 + 在会话里说一声；
     建议 = 会话内直接答复（不承诺落稿权）；审批 = 现有 `request_signoff`；路由 = 唯一操作者。

## 方案 · 机制层（B，升 pin 之后）

3. **B1 · 收件人路由**：把"唯一操作者"升级为按 A1 授权面路由，**沿用** cockpit 收件人模型的 `owner`
   字段形状，不推翻 v1。**第一步机制核实**（D15 发现权在代理）：answerer 路由面是否支持多收件人 /
   按会话或按角色指定；不成立则退化为"owner 字段如实显示 + 单人路由"，并在 Note 记证伪。
4. **B2 · 三类接口的机制载体**：**补料**（核实 composer 附件 → `workspaceFiles` 数据面有没有直路；
   不成立就沿用退化形状并写进手册）；**建议**（给非阻塞载体，语义与审批明确区分：建议 = 输入、不授予
   落稿权；审批 = 授权）；**规矩回流**（回流动作的痕迹面，与 A2 的路径对齐）。
5. **B3 · 不在场的机制化**：把 A2 的分档落到注意力中心条目类别与挂起 / 继续语义上——人回来时能一眼
   看出"哪些在等他、哪些是带假设走的"。
6. **B4 · 证据与回看**：审批已有 `approval/asked` + `decided`；补上问询 / 建议 / 补料的记录面；驾驶舱
   注意力中心与经营仪表台账如实显示"哪条是真人拍的板"（谁 / 何时 / 批的什么），回看走 replay / snapshot。

## 输掉的方案

- **内容层也等升 pin 之后再做**：内容层本来不依赖新基座，却把用户最关心的事全押在一个两天级工程后面；
  输给"拆两批、内容先做"。
- **机制层先做（先人机合一、后升 pin）**：preset 声明与 client 数据面要迁两次；输给"基座先行"。
- **现在就建完整多人模型**：无 seam、也无"两个人同时用"的需求证据（不发明纪律）；输给"v1 形状 +
  A1 先建模、B1 后升级路由"。
- **通知走界面外推送**（email / 桌面通知）：缺上游 seam，搁置池 d 判定不变，且当前操作者就在驾驶舱前；
  输给"先做舱内闭环"。本条提供了该搁置项所要的"明确的物理人通知需求"，但部署面仍缺——复活判据按
  搁置池规则复核，不在本条承诺。
- **审批全闸**：毁动议节奏，agent 变事事请示（cockpit RFC 已判）；输给"分层三档"。
- **让人直接编辑 `kb/<role>/CHARTER.md`**：破坏"轮末收敛只由人做 + 原文件随快照归档"的记忆纪律；输给
  "裁决 → 回流 → 由人收敛"。
- **把"规矩不知道"当异常自己猜**：与初衷相反，且猜出来的规矩无法复用；输给"显式规则缺口路径 + 回流"。
- **建议与审批共用一条阻塞管线**：让人"给句意见"也变成闸门，节奏死；输给"建议 = 非阻塞输入"。

## 验收

**内容层（A）**：
- A1：`kb/owners.md`（或 org.md 增节）给出角色 ↔ 物理人 + 授权面；单一事实家、无第二处复述。
- A2：四类接口的规矩在手册 / CHARTER / skill 里有明文，含**退化形状**；`pnpm verify` 绿；动 preset /
  手册时按面补最小真检查（preset-smoke / probe / handbook-smoke）。
- 机制未到位期间：真跑一轮验证退化形状可行（补料走共享盘、建议走会话答复、审批走 `request_signoff`）。

**机制层（B，前置 = 升 pin 落地）**：
- B1：收件人路由 keyless 单测（多 owner fixture）+ 真模型证据：两个角色的请求分别路由到不同 owner
  （单人现实下 = owner 字段如实、路由表形状可扩）。
- B2：三类接口各一条真证据——补料落地且被 agent 读到 / 建议回路不阻塞落稿 / 规矩缺口 → 人裁决 → 回流
  进手册或 CHARTER 的完整一条链。
- B3：真跑或模拟"人不在"——阻塞型挂起且稿件记未决，非阻塞型带显式假设继续；注意力中心如实显示。
- B4：交互记录可回放（replay / snapshot 判据绿）+ 面板如实显示决策来源。

## 风险

- **机制面未核实两处**：answerer 多收件人路由、附件 → 共享盘直路。分别在 B1 / B2 第一步核实，不成立
  即退化并记证伪（不硬闯）。
- **内容层先行的最大风险 = "规矩定了但像没落地"**：靠人肉执行退化形状，容易被读成"没做"。对策 = 退化
  形状与"机制到位判据"都写进手册，验收里明确"机制未到位期间也算通过"。
- **承诺权不因此松动**：人批的是自己职能线内的决定，不是对外口径——只有 CEO 能对外（R3 / D18 维持）。
- **多对多的边界**：一个物理人可能养多个角色（本仓现实是单人养五个），A1 必须先定授权面而非只定归属。
- **规矩回流的维护成本**：裁决回流若不收敛（每次问答都改手册），手册会膨胀且互相矛盾；回流需带"取代
  检查"（dev-loop §12），并在轮末收敛时并入 CHARTER 历史纪要。
- **与人不在场现实的关系**：本 RFC 只定"带假设继续"的纪律，不解决"没人时怎么自动续跑"——那仍受上游
  seam 限制（见 [longrun-goal-shape](./2026-09-25-longrun-goal-shape.md) 与搁置池「自主节律」）。
