# 2026-09-25 · 人机合一：物理人 ↔ 分身（配对、四类接口、不在场策略）

状态：proposed（2026-09-25 用户口述需求登记；建在已毕业的驾驶舱人机协作线之上，不重开其四切片）

## 问题

Agent ↔ Agent 这一层已经通了：团队成型、汇报线、任务板、在场板、升级中继都在跑，用户判断"Agent 之间
的协作没什么问题"。真正缺的是**物理人 ↔ 分身**这一层。

现状只有两个点 + 一个单人形状：

- **审批闸门**（`request_signoff` → `ctx.approval`）：一次性、轮内有效、**无应答 fail-closed**，事件对
  `approval/asked` + `approval/decided` 入日志，浏览器官方 `ui-approval` 应答，注意力中心跨会话显示
  （[cockpit-human-loop](../implemented/2026-09-24-cockpit-human-loop.md) 切片二）。
- **问人两条路**（手册明文）：动议内成员用 `send_message` 升级 CEO 带【待澄清】前缀、**不直接问用户**；
  独立会话（无动议上下文）直接用 `ask_user_question`。五个 preset 均已挂 `tool-ask-user`。
- **收件人模型 v1 = 单操作者**：条目带 `owner` 字段但全部路由到唯一操作者；多人在数据模型上不堵死，
  但**人这一侧没有被建模**——`kb/org.md` 是 50 人数字编制，"哪个物理人对应哪个角色"没有事实家。

用户要的是**人机合一**：CFO 的数字分身能做部分事，但要能问物理的 CFO"你补充资料 / 给 approval /
给建议"，**尤其规矩不知道的时候**。逐类对照，缺口是四类接口里只做了两类的一半：

| 人机接口 | 现状 | 缺口 |
|---|---|---|
| 要审批（阻塞型） | 有（一条最经营线 + 双签线） | 未分层：哪些必批 / 哪些可事后告知 / 哪些自主，没明文 |
| 问询（阻塞型） | 有（两条路 + 注意力中心四类条目） | 收件人只有"唯一操作者" |
| **要资料**（"你补充资料"） | 无载体 | 人交文件 / 补数据的回路未核实、未约定 |
| **要建议**（"还是听物理的 CFO 给建议"） | 无载体 | 非阻塞、非审批的轻量回路没有家 |
| **规矩不知道** | 无路径 | 手册 / CHARTER 未覆盖时该问谁、裁决如何**回流成规矩**，没有规矩 |

## 方案（四切片，按依赖顺序）

1. **切片一 · 人侧建模与收件人路由**：新增"角色 → 物理人（多对多）+ 各自授权面（能批什么 / 能答
   什么 / 只给建议）"的事实家（`kb/owners.md` 新文件，或 org.md 增节——实施时按"一处事实一个家"
   择一）；收件人从"唯一操作者"升级为按该表路由，**沿用** cockpit 收件人模型的 `owner` 字段形状，
   不推翻 v1。**第一步机制核实**（D15 发现权在代理）：answerer 路由面是否支持多收件人 / 按会话或
   按角色指定；不成立则本轮退化为"owner 字段如实显示 + 单人路由"，并在 Note 记证伪。
2. **切片二 · 四类接口补齐**：
   - **要资料**：约定"补料"回路——人交文件 / 补数据 → 落共享盘哪个目录 → agent 读取并在稿件引用。
     **第一步核实**：composer 附件与 `workspaceFiles` 数据面之间有没有直路；不成立则退化为"人写文件
     进共享盘 + 在会话里说一声"（退化的形状也要写进手册，别留口头约定）。
   - **要建议**：给"建议请求"一个非阻塞载体，语义与审批明确区分（建议 = 输入，不授予落稿权；审批 =
     授权）。载体候选：沿用 `ask_user_question` 带 options / 复用审批管线但不阻塞落稿——实施时按机制
     核实择一，并定记录面（进注意力中心哪一类、是否入台账）。
   - **规矩不知道**：定一条**规则缺口路径**——手册 / CHARTER / skill 都没覆盖时 ⇒ 按切片一路由问人
     ⇒ 人的裁决**回流**（改手册 / CHARTER 或登记磨清单）⇒ journal 留痕。这是组织学习闭环，也是
     "培养"的输入源之一。
   - **审批分层**：明文三档（**必批** / **可事后告知** / **自主**），对齐承诺权与签字线；避免"要么
     全闸、要么全放"。第一版只把已生效的两条签字线落进"必批"档，其余先观察再收。
3. **切片三 · 不在场策略**（直接回应"人睡了"的处境，也是长程自主执行的前提）：按**阻塞性**分类——
   阻塞型（审批 / 裁决）保持 fail-closed，把事项写进稿件未决项 + 注意力中心条目；非阻塞型（建议 /
   补料 / 规矩缺口）允许带**显式默认假设**继续，假设写进稿件与未决项，人不回来不假装已答复。
   **目标**：人不在时，agent 知道"哪些必须停、哪些可以带假设走"。
4. **切片四 · 证据与回看**：人机交互全程可审计——审批已有 `approval/asked` + `decided`；补上问询 /
   建议 / 补料的记录面；驾驶舱注意力中心与经营仪表台账如实显示"哪条是真人拍的板"（谁 / 何时 /
   批的什么），回看走 replay / snapshot。

## 输掉的方案

- **现在就建完整多人模型**：无 seam、也无"两个人同时用"的需求证据（不发明纪律）；输给"v1 形状 +
  切片一先建模、后升级路由"。
- **通知走界面外推送**（email / 桌面通知）：缺上游 seam，搁置池 d 判定不变，且当前操作者就坐在驾驶舱
  前；输给"先做舱内闭环，界面外留给搁置池"。注意：本条提供了该搁置项所要的"明确的物理人通知需求"，
  部署面仍缺——复活判据按搁置池规则复核，不在本条承诺。
- **审批全闸**（所有对外文本都要批）：毁动议节奏，agent 变事事请示（cockpit RFC 已判）；输给"分层三档"。
- **让人直接编辑 `kb/<role>/CHARTER.md`**：破坏"轮末收敛只由人做 + 原文件随快照归档"的记忆纪律；输给
  "裁决 → 回流 → 由人收敛"。
- **把"规矩不知道"当异常自己猜**：与人机合一的初衷相反，且猜出来的规矩无法复用；输给"显式规则缺口
  路径 + 回流"。
- **建议与审批共用一条阻塞管线**：会让人"给句意见"也变成闸门，节奏死；输给"建议 = 非阻塞输入"。

## 验收

- 切片一：收件人路由 keyless 单测（多 owner fixture）+ 真模型证据：两个角色的请求分别路由到不同
  owner（单人现实下 = owner 字段如实、路由表形状可扩）。
- 切片二：四类接口各一条真证据——补料落地且被 agent 读到 / 建议回路不阻塞落稿 / 规矩缺口 → 人裁决 →
  回流进手册或 CHARTER 的完整一条链 / 审批三档在 persona 或 skill 里有明文。
- 切片三：模拟或真跑"人不在"——阻塞型挂起且稿件记未决，非阻塞型带显式假设继续；注意力中心如实显示。
- 切片四：交互记录可回放（replay / snapshot 判据绿）+ 面板如实显示决策来源。
- 共同前提：`pnpm verify` + `pnpm test` 绿；动 preset / 手册 / pack 时按面补最小真检查（preset-smoke /
  probe）。

## 风险

- **机制面未核实两处**：answerer 多收件人路由、附件 → 共享盘直路。切片一 / 切片二的第一步先核实，不
  成立即退化并记证伪（不硬闯）。
- **承诺权不因此松动**：人批的是自己职能线内的决定，不是对外口径——只有 CEO 能对外（R3 / D18 维持）。
- **多对多的边界**：一个物理人可能养多个角色（本仓现实是单人养五个），切片一必须先定"授权面"而不是
  只定"归属"，否则路由对了、权限还是错的。
- **规矩回流的维护成本**：裁决回流若不收敛（每次问答都改手册），手册会膨胀且互相矛盾；回流需带
  "取代检查"（dev-loop §12），并在轮末收敛时并入 CHARTER 历史纪要。
- **与人不在场现实的关系**：切片三只定"带假设继续"的纪律，不解决"没人时怎么自动续跑"——那仍受上游
  seam 限制（见 [longrun-goal-shape](./2026-09-25-longrun-goal-shape.md) 与搁置池「自主节律」）。
