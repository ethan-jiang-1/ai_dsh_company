# 2026-09-25 · 长程自主执行的目标形态：交付型 vs 打磨型

状态：proposed（登记 2026-09-25；只解决"goal 怎么写"，不解决"没人时怎么继续"）

## 问题

2026-09-24 晚用户说"底下有将近八个小时"，实际自主段 = 23:12 → 02:02（2 小时 50 分，turn 3–13 共
10 轮，20 个 commit）后自行收口。根因不是故障：goal objective 被写成**固定 8 条队列清单**
（N1 → 驾驶舱①–④ → 记忆收敛+培养轮3 → 新动议×2 → 呈现叙事），第八条完成即 `update_goal complete`
⇒ **队列有界**，不是时间/预算有界；轮次上限（30）根本没用满（只用 11 轮）。

同一晚还有一层错配：用户要的是"自动琢磨打磨、把自己的能力提高"（**打磨型**：输入 = 发现的问题），
实际执行的是**交付型**（输入 = 已排期条目）。两种形态的输入源、停止条件、收尾物都不同，混在一句
"跑 8 小时"里必然走偏。

## 方案

1. **显式区分两种长程 goal 形态**，分别钉写法：
   - **交付型**：objective = "按 ROADMAP §队列逐条执行"，有界性 = 队列空即收口。当晚形态本身没错，
     只是不等于"跑满时长"。
   - **打磨型**：objective = **预算（时间或轮次）+ 输入源 + 停止条件**。输入源 = 磨清单（由
     [记事面治腐化](./2026-09-25-notebook-hygiene.md) 负责给它立家）与执行期审计发现；停止 =
     预算耗尽 / 输入源枯竭 / 真卡住。
2. **停止条件三类各自动作**写进 objective：预算耗尽 → 自评收口；队列或输入源空 → 收口并报告；
   真卡住（机制证伪／验收无法变绿／需人裁决）→ 停并汇报阻塞与证据，不硬闯。
3. **节奏**：每条一个 commit + push，每完成一条向用户简报（当晚已实证有效，固化为默认）。
4. **落点**：[dev-loop §0.5](../../docs/guides/dev-loop.md) 增一小段"长程 goal 的目标写法"，不新增
   流程、不新增工具、不新建 spec。

## 输掉的方案

- **把 8 小时写进 `max_goal_rounds`**：轮次 ≠ 墙钟，cap 只截断不定义"跑满"；当晚 cap=30 只用了 11 轮，
  说明瓶颈不在 cap；输给"objective 写预算 + 到点自评"。
- **goal 永不 complete（无限续跑）**：DSH goal 需要有界终点与可裁决的收尾证据，永久续跑会让"完成定义"
  消失；输给"预算式边界 + 到点自评"。
- **自建调度器／常驻循环实现无人值守**：搁置池已判"缺外部触发 ↔ 会话内自主续跑的 seam"，且 D9/D13 禁
  自建调度器；输给"提 seam + 记录证据"。
- **把打磨型也预排成条目清单**：等于把"发现过程"提前写死，执行中发现的真问题反而进不来；输给
  "预算 + 输入源"。

## 验收

- 下一次长程执行按本形态起 goal：证据 = session 时间线（起止与轮次）+ 每轮 commit + 结项报告；
  打磨型的输入源可追溯到磨清单条目。
- 落盘物 = dev-loop §0.5 的目标写法段（两类形态各一句示例 + 停止条件三类）。

## 风险

- DSH 的 goal 需人类授权、session-start 一律 disarm（搁置池「自主节律」已核实）⇒ **无人值守续跑仍受
  seam 限制**；本条只规范"被授权后那个 goal 怎么写"，不宣称能解决无人续跑。
- 预算式 objective 若写得太松（如只写"跑够 8 小时"）会诱发凑数式工作；写法要求同时给"输入源"与
  "枯竭即收口"，防为跑满而空转。
