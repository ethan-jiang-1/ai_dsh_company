DSH 之上的插件。coding agent 同时阅读插件仓库与 DSH 仓库，两边沿用同一套分类与流程词汇时，开发的
信噪比最高、冲突最少；DSH 自己的分类规则（目录职责、内容的维护形态）与它为插件作者维护的文档 tier，

所以这件事不是"再读一遍文档"，而是**逐条对照 + 二分判定 + 落地**：本仓现状 vs 语料方法 vs 差在哪 vs

## 方案（读 → 判 → 改，三阶段；阶段 1 只记判定、不动仓）

1. **阶段 1 · 对照台账（研究）**：按上节读法过全部 27 篇，每篇产一条判定：**本仓现状 / 语料的方法 /
   差在哪 / 采纳 or 不采纳 + 理由 + 被否方案**。产出落 `notes/research/`（按主题归并，不按篇数）。
   **硬规则：不留"待定"**——判不了就写"本仓不适用 + 为什么"。
2. **阶段 2 · 改（按主题切片，每片独立验收 + 独立 commit）**。候选切片（以阶段 1 判定为准）：
   - **入口与归属面**（对齐 02 / 08）：入口链、docs / notes 归属、负知识的落点。
   - **反馈面**（对齐 05）：按"六层反馈各自证明什么"给本仓 verify / test / 各 smoke 分层标定，
     补缺层；负例证明已有，核对是否每道门禁都带。
   - **参与面**（对齐 04 / 09）：正确路径与参与阶梯；**插件作者入口**逐条核——我们的 README / AGENTS /
     presets 文档是否让一个外部读者能照 09 的定义读懂"我们是什么插件、怎么装、怎么组合"。
   - **运行时可检查性**（对齐 06）：与升 pin 的收割项合并处理，不另立条目。
   - **边界与成本**（对齐 07）：用"三个问题检验一个 Development Harness"给本仓打分，明确**哪些不照搬**，
     并写进 AGENTS.md / index 的"本仓适配"叙述。
   - **prose / 文档标准**（对齐 Reference 05）：与本仓 doc-budget、md-newline、链接门禁合并核对。
3. **阶段 3 · 归位**：把新吸收的规则写成本仓合同（AGENTS.md 纪律表 / dev-loop / verify 门禁），
   更新 [docs/index.md](../../docs/index.md) 的 D 号台账与外部材料登记；每条改动带该面最小真检查；
   新吸收的**机械可查**规则进 `verify`（按纪律带反证）。

## 节奏与红线（小步迭代；用户 2026-09-25 定）

本仓 harness **已接近**语料主张的形态，因此**预期大头是"确认 + 显性化"，不是大改**。按小步迭代走，
碰红线**停下报人**、不自己拍：

| | 判据 | 处置 |
|---|---|---|
| 小步 | 只改措辞 / 加一句纪律 / 补指针 / 补一条门禁反证 | 直接做，收尾报告 |
| **红线** | 改**目录归属**（什么放哪个家）/ 改**门禁语义**（现有门禁管什么）/ 动 **preset 声明或 client 数据层** | 先报人，同意才动 |

**"读完确认无需改动"是合法结局**：某篇对照下来发现已对齐，就记「已对齐 + 证据」，不硬凑改动。
**用途**：给自己开发本项目用优先；数字分身是否共用这套，留待用户后续判断。

**本条目不含收尾清扫**：清扫由**独立的清扫会话**做（中立体，打造的人不扫、扫的人不打造），
处置入口见 [notebook-hygiene](../proposed/2026-09-25-notebook-hygiene.md) 的「收尾清扫」节。

## 输掉的方案

- **按语料全量照搬仓库结构**：语料自己（07）就写了"DSH 的完整结构不适合照搬到所有项目"；输给"逐条判
  采纳 / 不采纳"。
- **只读 Tutorial 就动手改**：Tutorial 为了可读性省略精确条件，"核对事实不能靠教程记忆"（语料 README
  第 42 行）；输给"Reference 逐条核"。
- **把它并进 ③ 打扫卫生**：理念面与自洽面目标不同，混在一起两个都不可验收；输给"独立条目 + 明确分工"。
- **等语料 re-pin 到 rc.2 再对照**：我们借的是**理念**不是版本细节；等它会无限期延后；输给"以语料当前
  钉版为准 + 在台账里显式记录差一个 tag"。
- **当成"读书笔记"交付**：没有"采纳/不采纳"二分的笔记不会改变仓库；输给"台账强制二分 + 每条采纳项必须
  落成切片或明确进搁置池"。

- **平均用力读完 27 篇**：同构的 9+6 篇值得逐条判，其余 12 篇多是已覆盖或本仓不适用；平均用力会把
  力气花在确认上；输给"全量读 + 分层用力"。
- **打造者顺手做收尾清扫**：自己扫自己的产出，盲区会被一起固化；输给"清扫中立体、收尾才扫"。

## 验收

- **阶段 1**：对照台账落盘——每篇一条判定（采纳 / 不采纳 / 本仓不适用 + 理由 + 被否方案），无"待定"悬空。
- **阶段 2**：每条采纳项有落地切片（文件 + 该面最小真检查）；每条不采纳项在台账里有理由；明确的"不照搬"
  清单进 AGENTS.md / index。
- **阶段 3**：`pnpm verify` + `pnpm test` 绿；AGENTS.md / dev-loop / index 台账与外部材料登记同步；新进
  `verify` 的规则带红绿反证。
- **边界**：不改 `vendor/`；不引入语料里的具体工具（除非升 pin 收割项已落地并单独立项）。

## 风险

- **语料基线差一个 tag**（`rc.1` vs 我们升级后的 `rc.2`）：只吸收理念层结论，机制细节一律回 `vendor/dsh/`
  自己复核，引语料时注明其钉版。
- **"读得多、改得少"**：27 篇正文全量读会拖时间并产出笔记；对策 = **分层用力**（9+6 逐条判、其余 12 篇
  只抓没见过的形状）+ 判定强制二分 + "读完无需改动"记为合法结局。
- **边做边扫会互相污染**：打造者顺手打扫会把自己的盲区一起固化；对策 = 清扫中立体、收尾才扫（见队列 ③）。
- **范围膨胀**：本条容易变成"什么都想改"；对策 = 每片独立验收、独立 commit，单片超一轮按 D11 拆。
- **与升 pin 的收割项重叠**：运行时查询类（06）会想两头都做；已明确归本条阶段 2，避免重复立项。
