## 过程中遇到的问题与处置（用户明确要我「自己解决」）

**问题：本轮第一次 `turn/end` 的 reason 是错误，不是完成**——

```
turn/end → {"turn":1,"reason":{"kind":"error","error":{"message":"DeepSeek Messages stream: tool input is invalid JSON","code":"MALFORMED_RESPONSE"}}}
```

会话停在第 67 步、正在收口写 `final` 的中途（最后一句是「对账回合闭合，两造对齐。现在收口 final。」）。**当时的盘面是「写了 final、标了『已采纳』、却没调 `present`」** ⇒ `deliverables-check` 报 `final-not-presented`，看起来像「角色又跳过了 present」（正是上一轮修掉的那个病）。

**处置：不动盘、不替它补 `present`，而是让同一个会话续跑**（告诉它「上一轮被基础设施打断了，不是你的判断问题，请接着收完」）。**结果**：第二次 `turn/end` = `completed`，`present` 已调（1 次），审计 **违规 0 条**。

**结论（这条比动议本身值钱）**：`MALFORMED_RESPONSE` 是**瞬时基础设施故障**，不是行为缺口——**判据红是对的**（它确实还没 present），而**恢复路径干净**（同一会话续跑即可，无需回滚、无需人工补声明）。给后续同类事故的口径：**先看 `turn/end` 的 reason 再判角色**——`kind: error` 的场次不该按「角色没做完」定罪。
