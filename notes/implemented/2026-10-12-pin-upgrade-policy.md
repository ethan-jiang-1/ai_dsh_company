# 2026-10-12 · vendor 升 pin 政策：用户策动制 + 渠道只认 RC/正式版

状态：implemented（2026-10-12 用户点名写死：「一定要写死，就是我们只升级 RC 或者正式版，其他的版本通通不管」＋「不是主动升，是我来策动升，你就其实不用管了」）

## 问题

上游 tag 流当时已进入 0.2.1 段（alpha 两枚在场；本仓钉在 `dsh-v0.2.0-rc.2`），「何时升 pin」存在三类自由裁量：定期盯梢上游、逐 tag 评估、或「等 rc 出现再走程序」（agent 此前的口头建议属第三类）——每一次都要临时判断，且前两类把 agent 变成上游的哨兵。需要一条写死的政策，把升 pin 的触发权与渠道准入一次性定死。

## 决定

- **升 pin = 用户策动制**：agent 不主动盯上游 tag、不评估、不建议、不记录候选——上游出任何新 tag 都是零动作。只有用户明确指示「升」才进 release.md §升 pin 程序。
- **渠道只认 RC 与正式版（stable）**：alpha/beta 及其他预发布 tag 通通不管；即使被点名也不作为升 pin 对象（改渠道须新 Note 翻案）。
- 政策家 = `docs/release.md` §升 pin 程序首段（随本 diff 写入）；升 pin 的其余程序（sync-dsh 簿记、人审 JSON、experimental 行重校、货架过账、release-smoke）不变。

## 输掉的方案

- **agent 定期盯上游 / 逐 tag 评估（含 alpha）**：把 agent 变成上游哨兵，评估成本常态化；alpha 无稳定性承诺，结论几乎总是「不升」——纯耗损。
- **rc 出现即主动升（agent 此前的建议）**：仍是主动升，只是收窄了渠道——用户明确否掉「主动」半边：「不是主动升，是我来策动升」。
- **只跟正式版（不含 RC）**：本仓现行 pin 就是 rc.2（0.2.0 无 stable 时已升）——RC 是本仓的实际采纳渠道；排除 RC 会把升 pin 拖到不必要的晚。
- **不写政策、维持临时判断**：每次出 tag 重新开讼，正是用户要求消灭的状态。

## 后果

- 上游出任何 tag（含 0.2.1-alpha.*）= 零动作：不看 changelog、不评估、不入触发器、不记账。
- 用户说「升」时：先核渠道（RC/正式版），再走 release.md §升 pin 程序全流程。
- 维护者的「前瞻事实」汇报不再包含上游 tag 动态（那是用户策动时要查的，不是 agent 要守的）。
