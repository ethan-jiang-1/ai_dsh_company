## 问题（用户原话还原 + 真盘实测）

1. **门的边界不清**：CEO 起一个话题 = 他的一扇新会话。**CFO 的人看得到 CEO 的会话**，可一打开
   是 CEO 的上下文——"这就不对了"；可自己新建一扇，又**跟 CEO 那个话题对不上话**。
   "CFO 能看到 CEO 的 session 好像也不太 make sense。"
2. **立刻对齐**：物理人针对某话题由 CEO 启动，**CFO / COO 的人怎么立刻对齐到那件事**？
3. **完全靠文件系统的代价**："你咋知道这个文件被锁住了？你不能改。"

**实测踩到的坑（同一场）**：新建会话的 **preset 默认 = `ceo`** ⇒ 用户开第二扇门想当 CFO 的门，
实际开成了**第三扇 CEO 的门** ⇒ CFO 的稿与纪要由 CEO 的会话代笔。
**而 `journal-audit` 查不出来**——它只查"在场"，不查"作者"（查在场 ≠ 查署名）。

## 先分层（三层正交，别混着谈）

| 层 | 问题 | 现状 |
|---|---|---|
| **L1 门** | 侧栏里**哪些会话属于我**？ | 按 workspace 过滤 ⇒ 同一个盘 = 同一个列表 ⇒ 各人看得到彼此的门 |
| **L2 对齐** | 话题 → **我的待办**，怎么自动出现？ | **没有通道**：①-b 实测成员（含 teammate）拉不到人 ⇒ 只能靠人之间说话 |
| **L3 并发** | 同一文件多写者，**我怎么知道能不能写**？ | 无锁；靠口头约定 |

## L1 · 门的边界：三个方案

### A · 共享服务 + 共享会话库（现形态）
- ✓ 零新结构、一个服务、Agent Teams 消息通
- ✗ **各人看得到彼此的门**（用户明确说不对）；要找自己的门；preset 默认坑

### B · 共享盘 + **每人一个 `$DSH_HOME`**（各起各的服务）
- ✓ 侧栏**天然只有自己的门**；与"迁到真实多人"同形（RFC §迁移清单 就是这形态）；零 client 改动
- ✗ Agent Teams 消息**跨 home 不通**；要装多份 pack/home
- ⚠ 这条**在 RFC 里被否过**（"三份会话库 ⇒ 团队态互相看不见，与同一 topic 协作相反"）——
  但用户这次的反馈说明：**"互相看不见"正是想要的**，而"同一 topic 协作"由**共享盘**承载、
  不需要共享会话库。**⇒ 那条否决理由需要重审。**

### ~~C · 共享服务 + 每人一个 symlink workspace~~ —— **❌ 已撤回（2026-09-26，被官方源码反证）**

**我原先的主张**：用 symlink 路径当会话 cwd ⇒ 侧栏按 cwd 分组 ⇒ 每人只看到自己那组。
**实测只证明了前半句的一半**：会话日志的 **bucket 名**确实保留字面 cwd
（`--Users-…-dev-homes-bob-company-workspace--`，`projectKey` 逐字编码、不调 `realpath`）。
**但我从 bucket 名推出了"侧栏分组"，这一步是错的。**

**反证（vendor 只读，逐字）**：
- `vendor/dsh/docs/subsystems/workspace.md:19`：**"`realpathNormalize`（`fs.realpath`；尾斜杠、`..`、symlink 全部解析）
  是唯一性规范 —— workspace 路径按规范化存储，唯一性 = 规范化路径的字符串相等（**a symlink to an owned
  directory collides**）"**；同一句话逐字出现在 `vendor/dsh/packages/workspace/workspace/src/paths.ts:39-56`。
- **侧栏按 workspace 实体分组，不按 bucket**：`vendor/dsh/packages/client/ui-workspace/src/client/tree.ts:327-340`
  的 `groupByWorkspace` 用 `workspace.workspaceId` + 该实体的 `sessionIds`。
- ⇒ **同一个真盘的 symlink 会碰撞成同一个 workspace** ⇒ **造不出"每人一组"**。

**仍成立的那半句（留作技术债观察）**：本仓审计按 `resolve()` 后的真盘路径拼**一个** bucket
（`scripts/deliverables-check.mjs:80`）⇒ 若会话真以别的字面 cwd 落盘，**会漏扫**。
这是**审计面的隐患**，与"能不能隔离侧栏"无关。

**教训（值得留档）**：我把"持久化路径的字面性"当成了"UI 分组语义"的证据——**测对了现象，推错了层**。
以后凡从 A 层观察推 B 层行为，先读 B 层实现。

### D · **命名约定代偿**（零结构，不隔离只帮找）
每扇门把会话标题写成 `<角色> · <slug>`，侧栏可搜/可辨。
- ✓ 零结构、零改动、今天就能用
- ✗ **不解决"看得到别人的门"**（只是让它不那么刺眼）；靠人自觉命名

### E · **client 侧"我的门"过滤/收藏**（**红线，只留案**）
在驾驶舱里按角色 pin/过滤会话列表。
- ✓ 这才是真正好用的 UX
- ✗ **要动 client 数据层**（用户 2026-09-25 已裁 demo 期不做）⇒ **本轮不做，只登记**

## L2 · 对齐：**候选工作重建**（不是"我的待办"）

**为什么不能靠"通知"**（⚠ 措辞已按评审收窄）：被委派的成员（含 team teammate）**拉不到人**——
问询在服务层被拒（`DELEGATED_CALLER`）。**Team 邮箱是活跃 Team/Lead 上的进程内能力**
（发送者须属于本进程准确的 live Team；普通 subagent 消息只发直接父/子）
⇒ 正确的说法是「**独立根会话之间不能借内置 Team 邮箱互发**」，
**不是**"一切通知方式都不存在"（共享盘文件、外部集成另论）。

**所以对齐只能靠"状态可推"**：把盘上的状态变成"我那扇门一打开就能看见的**候选工作**"。

**做法（零新机制）**：每扇门的**开工动作**（已有先例：读 CHARTER + journal + org.md）加一步——
扫 `deliverables/*/drafts/ceo.md`，列出「任务书提到我这个角色、而我还没有 `drafts/<角色>.md`」的。

**★ 但"缺稿"≠"待办"——评审用本场真事给了三种误报**（`sea-reconcile-2026` 的任务书含 T1–T4 首稿 +
依赖"四稿齐了"才启动的 T5–T7 互审；现场只有 CEO/CFO/COO 首稿 + final，VP-Sales/VP-Eng 缺稿，
而 final 明确记为**缺席收口、互审未发生**）：

| # | 误报 | 为什么 |
|---|---|---|
| 1 | 把**已关闭动议**的历史缺稿报成新待办 | 只看"文件在不在"，不看动议状态 |
| 2 | 把**已出首稿但仍有依赖**的角色报成已完成 | 出稿 ≠ 任务完成（互审/返工还在后面） |
| 3 | **漏掉**互审、返工、取消、审批、口头补料、"提意见但不写稿" | 这些任务**不产生 `drafts/<角色>.md`** |

自然语言"点名"还有否定、条件、引用、旧版任务书、同角色多任务等歧义。
⇒ **产物命名必须诚实**：第一阶段叫「**共享盘中的待核工作候选**」，
候选项要带 `slug` / 任务书版本 / 任务编号 / 原文引用 / 角色↔物理人映射 / 预期产物 / 依赖 /
发现时间 / **「待核实」标记**；**它不能自动宣称"已指派""已接单""已授权""已完成"**。

**最小结构（评审建议，待实验）**：不先造 `ASSIGN.md` 新事实家，而在现有任务书里加**一小段机器可读的
派活行**（任务编号 / 责任角色 / 输出 / 依赖 / 状态 / 任务书版本）。**先用实验验证它是否真降误报**
（见 §评审与修正 的实验 B），再决定要不要独立任务载体。
**关键是：把"任务状态"从"文件存在与否"里分离出来。**

**其他方案（列出以证空间完整）**：
- **F · 显式派活单**：CEO 写 `deliverables/<slug>/ASSIGN.md`（谁 / 做什么 / 状态）。
  ✗ 比"扫盘推"多一个**新文件类型**（`drafts/<角色>.md` 已是既有形状，任务书用它就够）——
  多一个事实家就多一处会漂。**除非**评审认为"任务书兼派活单"在语义上太挤。
- **G · 靠 CEO 的动议会话 spawn 成员，人的门只读**：✗ 机制上成员**拉不到人**（①-b 实测）⇒
  人就成了旁观者，"各自开门"失去意义。
- **H · 上游 seam：按角色路由通知**（搁置池）：✓ 才是真解；✗ 需上游能力，**不自建**。
- **I · 驾驶舱"动议"页签**（按 slug 聚合各角色稿状态）：✓ **那才是真正的 UX**；
  ✗ 要动 client 数据层 = **红线，只留案**。

## L3 · 并发：**缩小冲突面 + 版本纪律**（不是"消掉锁需求"）

⚠ **我原先写的"DSH 无锁"过宽，且"真正的共享写者不存在"只能当目标、不能当机制事实**（评审修正，
证据 = `notes/research/2026-09-26-multi-human-ux-evidence.md`）。机制实况：

| | 有 / 没有 | 证据 |
|---|---|---|
| **实例内** per-target 排队锁（`locks = Map<targetKey, Promise>`，串行化"读→守卫→写"窗口） | **有** | `vendor/dsh/packages/fs/fs-local/src/index.ts:101-112` |
| 版本守卫（读过再写、版本变了报 `FS_STALE_VERSION`；官方测试"一胜一 stale"） | **有** | 同上 `:216-218`；`packages/fs/fs-local/tests/filesystem.spec.ts` |
| **跨进程 / 跨 `$DSH_HOME` / 外部编辑器**的共享租约 | **没有** | 该锁只是实例内 Promise Map |
| 无版本期望的写 | **仍是无条件原子覆盖** | 同上 |
| `read-before-write` | **是可选插件的按会话观察**，不是"正在写"状态 | `packages/fs/fs-observation-policy/src/index.ts` |

**产物分工仍然有用**（这是本仓的**流程政策**，不是文件系统保证）：

| 文件 | 政策上的写者 | 政策挡不住的 |
|---|---|---|
| `drafts/<角色>.md` | 本人 | 同角色多人、一人开多根会话、**错选 preset**（已实测：CEO 会话代写 CFO 稿） |
| `kb/<角色>/journal/` | 本人 | 同上；且 `journal-audit` **查在场、不查署名** |
| `final.md` | CEO | 提前合稿（稿没齐就合） |
| `drafts/ceo.md`（任务书） | CEO | 版本漂移（谁手上是哪版） |
| `kb/motion-ledger.md` | 维护者 | — |

⇒ **正确说法**：**产物分工降低冲突面，但没有消除跨人并发问题**。这足以支持"demo 期不自造跨人锁"，
**不足以声明"共享写者不存在"**。补四条可核对纪律：
1. **单稿负责人**（一稿一人，写进稿首）；
2. **出稿回执**（"我写完了"要落到 journal，不只口头）；
3. **CEO 合稿前确认版本与未决项**（哪一版、哪些还没回）；
4. **返工显式通知 + 新版本号**（改稿要能看出改的是哪一版）。
能用 DSH 文件工具时**优先保留读后写 + 版本 guard**，但**别把它误写成跨人的写入租约**。

**其他方案（列出以证空间完整）**：
- **J · append-only 活动流**（谁在写什么，如 `kb/<slug>/ACTIVITY.md`）：✓ 有可见性；
  ✗ 造新事实家 + 需要"什么时候写"的纪律；且 **mtime 不能证明写完/已读/无冲突/合稿用的是最新版**
  （跨机器时钟更弱）⇒ 收益不抵成本，先靠上面四条纪律。
- **K · 文件级租约**（`.lock` sidecar）：✗ 造锁机制 = 发明（D13）；且**实例内已有锁**，
  缺的那层（跨进程/跨 home）本仓补不了 ⇒ 不造。
- **L · 用 git 当并发层**（各人 commit/push，冲突显式化）：✓ 这才是多写者的"真答案"；
  ✗ demo 期给每个物理人加 git 仪式太重；**迁到真实多人时可作可选层**（合同 §5 迁移清单可挂）。

### 补上：四个角色别混（评审指出，本场真事踩到）

`sea-reconcile-2026` 的任务书里写着"成员不得自行发起 `request_signoff`，升级 CEO"，
**与合同 §0（根会话由本人发起）直接冲突**——这不是措辞小误差：它会让 CFO 的签字请求落到 CEO 的门上。
根因是**这四个角色被混成了一个"谁该签"**：

| 角色 | 是什么 | 事实家 |
|---|---|---|
| **请求发起者** | 哪个 agent/会话发出 `request_signoff` | 会话日志的 `agent` 字段（机制） |
| **业务授权人** | 谁**有资格**决定（毛利线归 CFO、对外口径归 CEO…） | `kb/owners.md`（政策） |
| **实际应答者** | 哪个物理人按了按钮 | 审批事件 + 人（**机制只记 agent，不记人**） |
| **双签证据** | 两次签署各自对应**哪一版稿** | 目前**没有**载体 ⇒ 见下 |

⇒ **在解决这组语义前，不应声称"谁该签的卡落到谁的门"，也不能从卡片位置推断双签成立。**

## ★ 结论（2026-09-26，四线证据齐后；本节 = 实验线的最终回答）

证据索引：B = 打分腿确认值（R1 40%/44%、R2 60%/60%、R3 60%/100% 严格 67%、零容忍 19）；
C = 署名 0 违规 + 版本穿透活体；A = 冷启动零信号 + 指引失败活体；D = 配置 A 红线触发 + 方向感勉强能 + 配置 B 四观察。
细节全在 [实验记录](../research/2026-09-26-experiment-b-labels-and-d-mechanical.md) 与 [C 记录](../research/2026-09-26-experiment-c-quote-z.md)。

**问一：要不要结构化派活字段？——要，两条前置纪律【已采纳 2026-09-26】**（代理拍板、单 commit 可逆；
手册「机器可读派活行」规矩 + CEO skill 两动作 + 扫描器双源核对 stale 标记 + 打分复跑同 diff 落地）
- 纯文件存在规则**不可用**（精确 44%，把有稿当完成 ×4，否定句/关闭动议全误报）；
- 结构化派活行显著更准，但有两个实测失败模式：**自然语言任务书饿死它**（4 个真待办全漏）、
  **状态行不回写就漂**（quote-z 关闭后三条过期待办被报成候选）。
- ⇒ 结论：**采「结构化派活行 + 状态回写纪律」**（出稿/完成/取消时同步改派活行；扫描侧双源核对——
  状态行 × 盘面文件矛盾即标「待核实」，quote-z 真语料 #2 同结论"要么回写要么双源核对"）。
  落点 = CEO 任务书模板 + 各角色收工回写（手册/skill 变更）+ candidate-scan 打分复跑。
  **审批 / 取消 / 无稿任务（意见类）三类不进扫描**——结构性全盲是机制事实，需要显式通道（人工或上游 seam），
  扫描永不背书；扫描产物永远只叫「待核候选」。

**问二：哪些上游 seam 值得提？——两条证据最硬，先行成文；其余附录**
1. **审批载荷带稿件版本/哈希**（最硬：双半审批钉 v2、签字轮推 v3 的活体穿透 + `approval/asked`/`decided`
   无结构化版本字段的源码核实）；
2. **分类色板令牌（每角色一色）**（用户活体：方向感"勉强能"、同色黑药丸区分全靠读字；平台 182 令牌无分类色板，
   本包禁写字面色）。
附录（复活条件已在搁置池）：按角色/授权路由人机请求 + 可配置 delegated approval policy；
持久可恢复 attention inbox（刷新即丢边界）；自主节律（外部触发 ↔ 会话内续跑）。

**配置裁决（实验 D）**：配置 A 红线触发（第一眼"看不到=没权限"，后想通）⇒ **现形态不能作为多人 UX 合同**，
demo 期继续 A+D 但按缓解方向走（色板 seam、开门时把"你是谁/该看哪扇门"备到一眼可决）；
配置 B 机制面更干净（会话库隔离坐实）但 Team 不通 + 每家装 pack + 审计须每家跑 ⇒ **真实多人部署时单独评估**，不作 L1 技巧。

## 输掉的方案（先记，免得重复讨论）

- **造通知/推送通道**：机制上不存在（成员拉不到人），自建要动 client/server（用户已否）。
- **给会话加"话题"字段 / 派生各角色的门**：派生出来的是**子会话**，而子会话拉不到人
  （`DELEGATED_CALLER`）⇒ 人的门**必须是根会话**，不能派生。
- **按角色藏内容**：同一话题一个真相是这家公司的卖点；藏内容 = 拆掉协作（RFC 已裁）。
- **造文件锁**：锁要解决的问题已被"一文件一写者"的形状消掉；造锁 = 发明（D13）。
