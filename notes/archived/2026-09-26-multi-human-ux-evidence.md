核查对象：[提案](../implemented/2026-09-26-multi-human-ux.md)、[当前合同](../../docs/multi-human.md)、[既有记录](../implemented/2026-09-26-multi-human-role-routing.md)。依据为钉住的 `vendor/dsh` 源码、官方 docs 和官方测试。**本轮只做静态核查，没有启动多 home、浏览器或 symlink cwd 探针。**“已证实”指可由所引源码直接支持，“推断”指机制给出强依据但缺本场运行验证。

## 会话分组与 symlink

- **已证实：会话日志 bucket 可保留 cwd 字面拼法，不等于侧栏分组。** `projectKey` 逐字编码 cwd，没有调用 `realpath`；`projectDir` 用该键作为日志路径（[format.ts:216–256](../../vendor/dsh/packages/session/session-persistence-jsonl/src/format.ts)）。本仓审计仅按 `resolve()` 的真盘绝对路径拼一个 bucket（[deliverables-check.mjs:39–40](../../scripts/deliverables-check.mjs)、[deliverables-check.mjs:75–85](../../scripts/deliverables-check.mjs)）；若会话确以不同字面 symlink cwd 写入，就会漏扫。bucket 名本身**不能证明** GUI 分组隔离。
- **已证实、反证提案 C：workspace 身份用 `fs.realpath`，同一真盘的 symlink 会复用原 workspace。** 官方合同明确 symlink 指向已注册目录会碰撞（[workspace.md:19](../../vendor/dsh/docs/subsystems/workspace.md)）；实现也明定 `realpath` 唯一规范（[paths.ts:39–56](../../vendor/dsh/packages/workspace/workspace/src/paths.ts)），`create`/`resolveByPath` 均使用它（[index.ts:222–241](../../vendor/dsh/packages/workspace/workspace/src/index.ts)、[index.ts:494–510](../../vendor/dsh/packages/workspace/workspace/src/index.ts)）。vendor 测试断言通过 symlink 创建会返回原实体（[workspace.spec.ts:381–395](../../vendor/dsh/packages/workspace/workspace/tests/workspace.spec.ts)）。
- **已证实：Web 侧栏按 workspace 实体而非 bucket 分组。** `groupByWorkspace` 以 `workspace.workspaceId` 和该实体的 `sessionIds` 构造各组（[tree.ts:327–375](../../vendor/dsh/packages/client/ui-workspace/src/client/tree.ts)）；Session header 的 cwd 在建索引和 attach 时同样被 realpath 归一（[index.ts:800–821](../../vendor/dsh/packages/workspace/workspace/src/index.ts)、[entity.ts:101–145](../../vendor/dsh/packages/workspace/workspace/src/entity.ts)）。`session/create` 用 `workspaceId` 时以已归一的 workspace path 作 cwd；直接指定字面 `cwd` 则不触发该分支的 `attachSession`（[commands.ts:105–143](../../vendor/dsh/packages/api/session-controller/src/commands.ts)）。未归属的 session 可进入 Ungrouped，不会自动形成“每人一组 symlink workspace”。因此提案 [L1-C](../implemented/2026-09-26-multi-human-ux.md) 从日志 bucket 反推侧栏隔离是**错误推断**；改脚本扫多个 bucket 也不会改变 GUI 的 workspace 身份。
- **部分已证实、运行未证实：symlink cwd 指向真盘的写入。** `sandbox-policy` 保留 cwd 的绝对路径字面拼法，执行 provider 负责身份归一（[sandbox-policy/index.ts:35–39](../../vendor/dsh/packages/sandbox/sandbox-policy/src/index.ts)）；Seatbelt/FS fence 共用的 writable roots 以 `realpathSync.native` 归一（[sandbox/roots.ts:20–54](../../vendor/dsh/packages/sandbox/sandbox/src/roots.ts)）。`fs-local` 声明 symlink 文件写入更新目标而非链接（[fs-local/index.ts:1–4](../../vendor/dsh/packages/fs/fs-local/src/index.ts)）。这支持“真实目标落在可写根内时可写”的静态预期，但不是所有工具和当前 Web 会话写入都已实测。提案所说“相对路径落在 symlink 前缀内所以放行”不是源码采用的统一判据。
- **已证实：journal 审计只做字面后缀过滤。** header cwd 要 `endsWith('company-workspace')`；显式 `--cwd` 则比较 `resolve()` 字面路径，而非 realpath（[journal-audit.mjs:73–80](../../scripts/journal-audit.mjs)）。

## Root、child、Team 与跨 home

- **已证实：root 是运行时所有权，不是 Session fork lineage。** 建 Agent 时 `parentAgent` 可省略以表示 root（[agent/index.ts:63–85](../../vendor/dsh/packages/core/agent/src/index.ts)）；`roots()` 筛 `owner === undefined`，文档说明恢复的 fork 仍可能是 root（[agent/index.ts:590–600](../../vendor/dsh/packages/core/agent/src/index.ts)）。Team `spawn` 把 `parent: root` 传给 `startContinuable`（[roster.ts:280–291](../../vendor/dsh/packages/experimental/agent-team/src/roster.ts)）；其 teammate 不是另一个物理人的根会话。Team 成员资格还须匹配 Lead 的 roster，普通 child 不自动是 teammate（[roster.ts:92–115](../../vendor/dsh/packages/experimental/agent-team/src/roster.ts)）。
- **已证实：被委派 child（含 Team teammate）不能直接问人；独立根会话可以进入问询路由。** `userQuestions.ask` 验证准确的 live Agent，再对非 `roots()` 成员抛 `DELEGATED_CALLER`；root 可继续进入 scoped answerer waterfall（[user-questions/index.ts:70–105](../../vendor/dsh/packages/interaction/user-questions/src/index.ts)、[user-questions/index.ts:129–143](../../vendor/dsh/packages/interaction/user-questions/src/index.ts)）。这支持 [合同 §0 的区分](../../docs/multi-human.md)，不支持“角色会话一律不能问人”。
- **已证实：委派时审批策略被设为 `never`（当审批服务存在），该策略在服务内拒绝请求。** 捕获后写进 child 日志（[child-agent.ts:221–255](../../vendor/dsh/packages/subagent/subagent/src/child-agent.ts)、[child-agent.ts:258–279](../../vendor/dsh/packages/subagent/subagent/src/child-agent.ts)）；`decide` 遇 `never` 在 dispatch 前返回 `rejected`（[user-approval/index.ts:267–284](../../vendor/dsh/packages/interaction/user-approval/src/index.ts)）。请求携带发起的 `agent`、按其 scoped UI answerer 路由并在该 Session 记审计，而非按本仓 `owners.md` 的业务授权角色自动路由（[user-approval/index.ts:107–117](../../vendor/dsh/packages/interaction/user-approval/src/index.ts)、[user-approval/index.ts:215–233](../../vendor/dsh/packages/interaction/user-approval/src/index.ts)）。不能将这条具体委派策略扩大成“所有非 root 在所有配置下永远不可审批”。
- **已证实：Team 邮箱是活跃 Team/Lead 上的进程内能力，不是任意两个根会话间消息。** 发送者须属于本进程准确的 live Team，目标在 Lead roster 内解析，消息写入 Lead Session 再由本进程 `ctx.agents`/`ctx.subagents` 递送（[roster.ts:75–103](../../vendor/dsh/packages/experimental/agent-team/src/roster.ts)、[mailbox.ts:109–150](../../vendor/dsh/packages/experimental/agent-team/src/mailbox.ts)、[mailbox.ts:234–267](../../vendor/dsh/packages/experimental/agent-team/src/mailbox.ts)）。普通 subagent 消息只发给直接父/子（[subagent/index.ts:265–285](../../vendor/dsh/packages/subagent/subagent/src/index.ts)）。
- **强机制推断、未做双实例实测：方案 B 各自 `$DSH_HOME` 的内置 Team 消息不能跨 home 使用。** 默认 Session 后端路径是 `dshHomePath('sessions')`（[base/cordis.patch.yml:130–133](../../vendor/dsh/packages/bundle/base/cordis.patch.yml)）；官方 Team README 明确“不支持多个进程协调一个 Team”，定义进程内所有权（[agent-team/README.md:28–32](../../vendor/dsh/packages/experimental/agent-team/README.md)、[agent-team/README.md:101–108](../../vendor/dsh/packages/experimental/agent-team/README.md)）。该结论限于**独立 home/服务的原生 Team 通道**；共享盘文件或自建外部集成另论。提案 [“跨门通知通道不存在”](../implemented/2026-09-26-multi-human-ux.md) 应限定为“独立根会话不能借内置 Team 邮箱互发”，而非一切通知方式都不存在。

## 持久事件与刷新

- **已证实：Session 日志可持久，但创建本身并非即刻落盘。** JSONL backend 说明首次 append/flush 才写盘，之前崩溃则可能没有会话记录（[persistence-jsonl/index.ts:239–245](../../vendor/dsh/packages/session/session-persistence-jsonl/src/index.ts)）。Team 的 `message/queued` 先 append+flush 后才尝试发送，离线成员可延后投递（[mailbox.ts:117–150](../../vendor/dsh/packages/experimental/agent-team/src/mailbox.ts)、[agent-team/README.md:67–71](../../vendor/dsh/packages/experimental/agent-team/README.md)）。**Team 持久邮箱不等于可刷新的审批/问询卡。**
- **已证实：可回答的卡是实时 waterfall + 客户端 Pending 对象。** Host→Client 的 `approval/request` 和 `user-questions/request` 都声明为 `waterfall`（[remote-events.ts:16–23](../../vendor/dsh/packages/api/remotes/src/remote-events.ts)、[remote-events.ts:45–48](../../vendor/dsh/packages/api/remotes/src/remote-events.ts)）；收到事件时 Client 新建内存 `PendingApproval`/`PendingQuestion`，等待答复并在结束后移除（[ui-approval/index.ts:34–69](../../vendor/dsh/packages/client/ui-approval/src/client/index.ts)、[ui-user-questions/index.ts:60–79](../../vendor/dsh/packages/client/ui-user-questions/src/client/index.ts)）。`uiSession` 从活动 domain 投影待交互状态，domain 卸载释放并委托未决请求（[ui-session/index.ts:384–409](../../vendor/dsh/packages/client/ui-session/src/client/index.ts)、[ui-session/index.ts:461–481](../../vendor/dsh/packages/client/ui-session/src/client/index.ts)）。未见新页面从 Session log 恢复可答卡的路径；[合同“刷新即丢”](../../docs/multi-human.md) 得到机制支持，但连接断开时每种请求的最终结算未逐项运行验证。
- **已证实：审批审计持久事件不等于可重答 inbox。** `approval/asked` 和 `approval/decided` 记在请求 Agent 的 Session（[user-approval/index.ts:197–233](../../vendor/dsh/packages/interaction/user-approval/src/index.ts)）；问询依赖实时 scoped waterfall 等答（[user-questions/index.ts:129–150](../../vendor/dsh/packages/interaction/user-questions/src/index.ts)）。L2“扫盘推待办”避开实时卡是合理的**设计推断**，但不是 vendor 已实现的待办功能；任务书自然语言识别漏/误率仍未证实。

## 文件并发语义

- **已证实、修正“DSH 无锁”：`fs-local` 存在实例内 per-target 排队锁。** `withLock` 串行化同一 `targetKey` 的本实例变更；带版本期望的 write/edit 在版本变化时报 `FS_STALE_VERSION`，无期望的 write 仍是无条件原子覆盖（[fs-local/index.ts:101–130](../../vendor/dsh/packages/fs/fs-local/src/index.ts)、[fs-local/index.ts:202–255](../../vendor/dsh/packages/fs/fs-local/src/index.ts)、[fs-local/index.ts:257–280](../../vendor/dsh/packages/fs/fs-local/src/index.ts)）。官方测试证明同一实例并发 guarded writes 一胜一 stale（[filesystem.spec.ts:641–653](../../vendor/dsh/packages/fs/fs-local/tests/filesystem.spec.ts)）。该锁只是实例内 Promise Map，**不是跨服务/跨 home 的文件租约**；shell 和外部编辑器不共享它。
- **已证实：read-before-write 是可选插件的按会话观察与版本校验，不是“正在写”状态。** `fs-observation-policy` 以 Agent Session 作 owner、目标 `targetKey` 作键；未读的 write 采用 `createIfAbsent`，读过采用观测版本 `replaceIfVersion`，未读的 edit 拒绝（[fs-observation-policy/index.ts:17–40](../../vendor/dsh/packages/fs/fs-observation-policy/src/index.ts)、[fs-observation-policy/index.ts:61–94](../../vendor/dsh/packages/fs/fs-observation-policy/src/index.ts)）。`tool-fs` 将 intent 交给 provider；若未装插件则默认 `undefined`，无条件写入（[tool-fs/write.ts:106–125](../../vendor/dsh/packages/fs/tool-fs/src/write.ts)）。不同进程不共享内存锁，即使均用版本检测，检测和随后文件发布之间仍有跨进程竞态（[fs-local/index.ts:214–243](../../vendor/dsh/packages/fs/fs-local/src/index.ts)、[fs-local/fsio.ts:620–650](../../vendor/dsh/packages/fs/fs-local/src/fsio.ts)）。
- **已证实：单次文件覆盖以临时文件+link/rename 原子发布，不提供多人合并或在写提示。** [fsio.ts:595–650](../../vendor/dsh/packages/fs/fs-local/src/fsio.ts)。Team task 的文件 hint 也只警告重叠而不阻断（[agent-team/README.md:73–79](../../vendor/dsh/packages/experimental/agent-team/README.md)）。一角色一稿、CEO 写 final 是[本仓合同的协作政策](../../docs/multi-human.md)，不是目录结构自动强制的写者身份校验；两个同角色根会话、误选 preset 或同 slug 仍可冲突。已有[撞 slug 记录](../implemented/2026-09-26-multi-human-role-routing.md)表明三态判据不能识别不同动议产物混合。提案 [L3“真正共享写者不存在”](../implemented/2026-09-26-multi-human-ux.md) 只能视为遵守约定时的目标，不能作为机制事实。

## 未证实与下一步

- 未运行本仓 Web 的两浏览器侧栏实验、symlink cwd 实际写入、跨 home Team 消息实测；C 的关键隔离前提已被官方源码/测试反证，不应继续把日志 bucket 观察作侧栏证明。
- 未运行刷新期间挂起请求的逐种结算实验、双进程同文件写入结果、mtime 观察或自然语言任务书扫盘误差测试；不能声称这些用户体验已验证。
- “默认 `ceo` 导致错署名而 journal-audit 查不出”是[本仓现有观测](../implemented/2026-09-26-multi-human-role-routing.md)，不应表述成 vendor 有作者授权检查。建议决策时明确区分独立根会话、Team child、持久会话日志和可答的实时卡。
