# _backlog · 把问题想清楚

这里记录尚未确定的问题，收集依据，形成结论，再交接或关闭。做什么由用户本轮请求决定；没有点名，不从卡片清单里自行开工。

**backlog 和 notes 是前后两段。** backlog 负责问题、依据、结论和交接材料；[notes](../notes/README.md) 是裁决后 RFC/Note 的住所，不是收件箱。notes 的准入规则决定材料以 RFC 还是 Note 落档；是否实施由用户裁决。不是每张 issue 都成为 Note。结论已确认、申请已记录后，卡可以按关闭条件结束，不等待下游实施或验收。

## 一件事怎么走

1. **记录问题。** 先找已有的 [问题卡](issues/README.md)，没有合适的再新建。写清触发、期望结果、怎么算完成、目前不知道什么。已经确认是缺陷但这次不修的，记在 [缺陷卡](bugs/README.md)；当场修掉的不建卡，其同类横切排查一句话记在该轮轮次回执①行（有 Note 随 Note）。
2. **弄清问题。** 缺事实就查资料、读代码或试原型；缺人的选择就说明依据、建议和要确认的问题。短结论回卡片，长依据进 [调研](research/README.md)。按当前缺口查 [方法导航](methods/README.md)，不必跑完整套。
3. **形成结论。** 回答做不做、什么时候做、先做什么、哪些不做。决定做的先写清 [验收标准](methods/validation-design.md)；延后或不做的，写清条件或理由。
4. **申请下游处理；满足关闭条件后离场。** 完整申请留在卡上，默认在本轮回复中附卡片链接向用户提出；用户指定接收会话或去处时按指定去处提交。记录日期、接收方、申请类型和去向。[notes 入口](../notes/README.md) 是准入规则，不是收件箱；批准后的落点（`notes/proposed` RFC / `notes/implemented` Note）与记录格式见 [交接说明](methods/issue-to-note.md)。不需要后续处理的，留下结论或已有决定的引用。

卡上的状态、方案、建议和交接都不授予实施权限。**限定例外（2026-10-12 立）**：`修复就绪` 的缺陷卡自带修复授权——该翻转即门票且授权（见「缺陷的通道」），P0 或严重/变向情形除外。已由用户授权的工作按原授权继续，不重复请求批准；任务与实施入口见 [开发环 §0.5/§1](../docs/guides/dev-loop.md)。

## 关闭条件

问题已有明确结论，所需确认已得到，需要的下游申请已提交并记录去向，才可关闭。**所需确认 = 结论所需的用户确认；下游申请的受理不是关闭条件**——未受理的请求记 `去向=用户（日期）`，由用户持有。已有结论足以回答的，留下引用即可。按结论检查：

| 结论 | 关闭前留下什么 |
|---|---|
| 做 | 问题、结果、范围与排除项、方案、实际比较过的选择及理由、可执行验收标准，以及申请去向（`rfc`/`note`/`implementation`/`pending`/`none` 之一） |
| 以后做 | 理由、什么时候再看、到时观察什么；需下游保留或处理的提交申请。条件到场新开卡引用旧卡 |
| 不做 | 原因与适用范围；需下游保留或处理的提交申请 |
| 结论已在别处 | 指向已有决定或当前合同，说明它回答了什么问题；agent 指认并引用，不需要用户新裁决（不确定是否足够时先问人）；若卡已在 `等人拍板`，由用户答复（程序性答复，不是新裁决）：答复为关闭时 agent 按答复写卡顶块并 `git mv`，答复为继续时回 `推敲中` |

有结论的卡用 `git mv` 进 [已关闭问题](_archive/settled_issues/README.md)，保留文件名和讨论正文，frontmatter 的 `status` 改为 `已结`，卡顶补 `> **结论/去向**` 块（状态行只做镜像），修相对链接并更新两边清单（活跃 = `issues/README.md`；归档 = `_archive/README.md`）。以后出现新问题，新开卡引用旧卡。

用户明确叫停、尚无结论的，进 [叫停问题](_archive/suspended_issues/README.md)，`status` 改为 `叫停`；重启须用户明确的新决定。事实或答复尚缺的留活跃区，写清缺口与下一步；“决定延后”不是“问题尚未解决”。

旧卡若已经承担实现后的终验，保留其原有未完成要求到验收完成，分别写清技术缺口与用户待确认项。这不是新卡等待下游实施才关闭的理由；“已实现”也不等于“已验收”。

缺陷按 [缺陷规则](bugs/README.md) 处理：修好进 [已修缺陷](_archive/fixed_bugs/README.md)，查明未修进 [待修缺陷](_archive/suspended_bugs/README.md)。研究在最后一张使用它的活卡离开时随迁 [研究归档](_archive/research/README.md)。

## 双轨状态生命周期（2026-10-12 立）

双轨共用一张处理门票：**把问题说清 + 给出验收手段，由格式承载**——问题轨在毕业时是 `## 验收标准`，缺陷轨在修复就绪时是 `## 已修判定`。

分工（一处事实一个家）：frontmatter `status` 是**当前阶段的唯一家**（一值，只经下表带守卫的翻转；活跃值 = 问题轨 `推敲中`/`等人拍板`，缺陷轨 `调查中`/`修复就绪`/`修复已落地`/`等人拍板`，出口值 = `已结`/`叫停`/`已修`/`待修`）；状态行是**镜像 + 历史**（`状态：` 词与 frontmatter 一致，门禁互查；裁定追加；离场补卡顶 `结论/去向` 块，状态行不承载去向）；目录持粗位置（活跃区 vs 归档池）。问题卡状态行带 `毕业：` 字段，封闭头 `未定｜做｜以后做｜不做｜消化`（`消化` = 上方关闭条件表的「结论已在别处」，不是 Note 的「已消化」状态词；四结论映射见上），后接自由散文——它是倾向，不是状态；未确认时可以保持 `做`，状态仍由 frontmatter 决定。

问题轨翻转表：

| 从 | 守卫 | 到 | 谁 | 记录 |
|---|---|---|---|---|
| （立卡） | 分诊后——卡只在路由后存在 | 推敲中 | agent | 立卡时 frontmatter |
| 推敲中 | 下一步是用户选择 | 等人拍板 | agent | 「下一步」点名确切问题；仅用户可判时状态行加 🔒 |
| 等人拍板 | 用户明确答复 | 推敲中，或离场 | 仅用户 | 状态行追加答复；离场时另写卡顶块 + git mv |
| 推敲中 | 判断落地＋申请已提交 | 已结（归档同改） | agent | 卡顶 `结论/去向` + git mv |
| 任意活跃值 | 用户叫停、无结论 | 叫停（归档） | 仅用户 | git mv |
| 叫停 | 用户明确重启决定 | 推敲中 | 仅用户 | 状态行追加 |
| 已结 | 永不重开——复发是新卡引用旧卡 | — | — | 写回 |

缺陷轨翻转表（`活跃` 已于 2026-10-12 改名 `调查中`——与目录「活跃清单」撞词；现无活跃缺陷卡，改名免费）：

| 从 | 守卫 | 到 | 谁 | 记录 |
|---|---|---|---|---|
| （立卡） | 分诊后 | 调查中 | agent | frontmatter |
| 调查中 | 根因有证据确认＋修法选定＋`## 已修判定` 写好；修复为 P1/P2 修复型 | 修复就绪 | agent | 翻转即门票**且**授权（铁律例外） |
| 调查中 | 同就绪，但 P0 或触碰章程/常设指令/docs 合同/company-pack 公开行为/已记录决定 | 等人拍板 | agent | 通道问题本身 |
| 修复就绪 | 修复已落树 | 修复已落地 | agent | 状态行追加 |
| 修复已落地 | 已修判定满足、证据记录 | 已修（归档同改） | agent | 结论追加 + git mv |
| 调查中/修复就绪/修复已落地 | 下一步是用户选择 | 等人拍板 | agent | 仅用户可判时 🔒 |
| 等人拍板 | 用户明确答复 | 等待前状态，或离场 | 仅用户 | 状态行追加 |
| 修复就绪/修复已落地 | 根因或修法被证伪——验收失败或新证据 | 调查中（回翻） | agent | 撤回的假设留在卡上 |
| 任意活跃值 | 用户叫停或已判定延后修复 | 待修（归档） | 仅用户 | git mv；状态行写清是哪种；判定延后按 [触发索引](triggers.md) 记触发句 |
| 待修 | 用户明确重启 | 调查中 | 仅用户 | 状态行追加 |
| 已修 | 永不重开——回归/复发是新卡引用旧卡 | — | — | 写回 |

共享翻转律：**沉默不翻转**（用户未答复不推进，平台 goal pause/resume 同款 owner-gated 先例）；**每次翻转是带守卫与记录的动作**；**出口值只在归档同改翻转**；`可关闭：是` 是出场守卫旗，与迁档同改（门禁已强制）。回翻带守卫合法；**根因纪律：假设→确认须证据**（bundle、git 历史或对照实验），被证伪撤回的假设留在卡上，不抹掉。

## 缺陷的通道与修复授权（2026-10-12 立）

缺陷卡的生命：分诊 → `调查中` →（根因有证据确认 + 修法选定 + `## 已修判定` 写好）→ `修复就绪` → 修复落树 → `修复已落地` → 已修判定满足、证据记录 → 归档已修。`## 已修判定` 写「修成什么算修好」，并可点名其验证搭载的工作（搭载依赖成字段，不成即兴句）。

**修复授权边界**：`修复就绪` 的翻转即门票**且**授权，限 P1/P2 修复型；**P0，或修复触碰以下任一项——章程/常设指令、docs 合同、company-pack 公开行为、已记录决定（notes/implemented 状态行）——不自授权**，需用户明确指示和/或走问题 RFC（通道问题本身把卡翻到 `等人拍板`）。严重级定义见 [bugs](bugs/README.md)——这是 severity 的消费者。

## 文件与维护

问题与研究文件用 `YYYY-MM-DD-<slug>.md`，缺陷用 `BUG-<NNN>-<slug>.md`。新问题/缺陷第一项 frontmatter 为 `status`，新研究第一项为 `topic`，具体模板见各目录 README；历史归档不批量回填字段。

清单与目录保持一致，机械形状由 `pnpm verify` 检查（含状态行↔frontmatter 镜像互查与 `毕业：` 封闭头）；检查通过不证明问题结论正确或方法有效。章程只写制度，现值和条目进各目录清单。状态行带 🔒 的卡仅用户可判定触发，agent 只报告与建议。本区门牌 = [AGENTS.md](AGENTS.md)（薄：定位、走法、门票与枚举，随第一方文件操作自动注入；规则唯一家仍是本章程与各 README，门牌不复述事实）。

本制度整体借自 `ai_dsh_assitant/_backlog` 工作树；取舍、适配与验证见 [落地 Note](../notes/implemented/2026-10-09-backlog-issue-lifecycle.md)。2026-10-12 制度显性化（缺陷通道、双轨状态生命周期、agent 门牌）借自 `ai_dsh_loop_advisor/_backlog` 同日同名评审卡（机器本地路径，刻意不链接），落地记录见 [显性化 Note](../notes/implemented/2026-10-12-backlog-process-made-explicit.md)。[退役历史池](_archive/legacy/README.md) 保持历史性质，不收新件，也不是任务源。
