# 编号 × OpenSpec 接缝：候选与未定问题（2026-11-07 第二轮）

## 前提（已定，不再讨论）

1. **多层需求文档是要的**：MRD → StRS → PRD → SyRS → IRS（用户 2026-11-07：这不是问题，是前提）。
2. **SW 与 FW 已经在用 OpenSpec 作为实践**（用户 2026-11-07）。
3. **OpenSpec 能承载我们的编号**：它开放、可自定义；它的强项是**加工流程与次序**，不是字段封闭
   （用户 2026-11-07，直接否掉"要不要查它撑不撑得住"这条）。

> 因此本轮不再讨论"要不要编号/要不要多层文档/OpenSpec 行不行"，只摊开**接缝关系、落法与集合**。

## 接缝的候选关系（未选）

> 谁当主键、谁当外键，是一个候选选择，不是已定事实。下面三种都还开着。

| 候选 | 主键 | 引用方向 | 可能的买点 | 可能的代价 | 待验证 |
|---|---|---|---|---|---|
| **A** | 我们的需求文档（StRS/SyRS/IRS） | OpenSpec 的 requirement 里写 `Traces:` 指回我们的 ID | 编号随需求走；`rg` 双向可查；不依赖外部表 | 依赖团队愿意加这一行；`openspec validate` 不管它 | 真实 OpenSpec 树里加 `Traces:` 的成本（V13） |
| **B** | OpenSpec 的 `(capability, requirement)` | 我们的文档引用 capability/requirement 标题 | 贴合 SW/FW 现状；OpenSpec 是唯一真相 | 标题会改；供应商/实验室没有 capability 概念 | 标题变更频率；跨组织可读性（V13/V8） |
| **C** | 中间注册表 | 两边都引用注册表键 | 解耦；可跨世界 | 多一个真相源；维护成本 | 注册表由谁生成、怎么防腐（V5/V13） |

**用标题当键的风险（对 B/C 都适用）**：OpenSpec 的身份是 `(capability, requirement 标题)`，标题会改；我们的编号不会；硬软一体的另一端（供应商 BOM、实验室报告）根本没有 capability 概念。这是"反对标题键"的证据，不是"已选定 A"的结论。反过来，A 也有代价：要维护 `Traces:` 行、`openspec validate` 不管它、团队可能不加；B/C 也有好处：贴合现状、少改 OpenSpec 树。下面表里的"好处/代价"都是待验证判断，不是结论。

## 三种落法（待选）

| 落法 | 做法 | 可能的买点 | 可能的代价 |
|---|---|---|---|
| **A. 需求体内带 `Traces:` 行** | OpenSpec 每个 `### Requirement:` 下加一行 `Traces: SYR-014, IFR-003` | 编号随需求走，`rg` 双向可查；不依赖外部表 | 依赖团队愿意加这一行；`openspec validate` 不管它（要我们自己的检查补） |
| **B. 附录映射表** | `allocation`/`trace` 表里写 `SYR-014 ↔ capability/requirement 标题` | 一处集中，好审 | 标题一改就静默失效；表会腐化 |
| **C. `openspec/project.md` 约定** | 在 OpenSpec 的项目约定文件里写"每条需求必须带 Traces 行" | 变成团队公约，AI 会照做 | 仍是约定，没有机械强制 |

## 前缀集合：两条路线（未选）

| | 方案一：6 套 | 方案二：3 套 + 文档号 |
|---|---|---|
| 编号 | `MR / STR / REQ / SYR / IFR / TC` | 全原子编号，仅保留少数层（如 `SYR / IFR / TC`）；上游文档用**文档号 + 章节号**（`PRD-3.2`） |
| 谁有原子编号 | 所有层 | 只有"要跨组织、要进 OpenSpec、要被验证"的层（系统/接口/验证） |
| 上游追溯怎么表达 | `SYR → STR-001` | `SYR → PRD-3.2（PRD 的 3.2 节）` |
| 可能的买点 | 每层都能被独立引用；覆盖表精确到条 | 前缀少一半；上游文档保持"文档"而不是"条目库" |
| 可能的代价 | 6 个空间，模型要在其中选；上游（MRD/StRS）实际很少被单独引用 | 上游追溯粒度粗（到节，不到条）；改章节号会断 |
| 与 OpenSpec | 无差别（OpenSpec 只关心下游引用） | 无差别 |

**要在这两条之间选，需要什么证据**（现在都没有）：

- **外部引用频率**：真正跨出文档体系的条目有多少？（供应商/实验室/客户）
- **模型第一眼**：`SYR/IFR` 与 `REQ/IF` 的盲测结果（V1）
- **迁移成本**：旧产物里 `STR/SYR/IFR` 的引用量（V7）
- **AC 父号耦合**：单 REQ 空间下 AC 号是否还唯一（V2）
- **跨组织样本**：供应商 Excel/实验室报告能否解析（V8）

## 还没定的问题

1. **接缝方向**：A（我们主键）/ B（OpenSpec 主键）/ C（注册表）。
2. **落法组合**：A / A+C / A+B / B / C。
3. **前缀路线**：6 套 / 3 套 / 其它。
4. **标题键的替代**：注册表 / 稳定锚点 / 只靠 ID。
5. **NFR 怎么保证不漏**：`kind` 字段 + 清单，还是接受漏。
6. **检查器**：要不要有"编号与追溯检查"？放在哪一层（我们的文档/OpenSpec 侧/两边各一）？
   注意：硬软一体有两套世界；若要有检查器，它需要同时读 OpenSpec 树和非 OpenSpec 文档，才能覆盖两套世界。
7. **范围**：只用于"落地项目"，还是所有动议（含 demo）。

## 已知边界（先写清，免得实施时才发现）

- OpenSpec 的 `openspec validate` **不会校验我们的编号**，加多少自定义字段都由它的 schema 说了算；
  目前看不到 OpenSpec 内部校验我们编号的路径，外部检查是候选路径。
- 供应商与实验室不读 OpenSpec ⇒ 给他们的文件里，编号必须是**纯文本可读**，不能依赖链接/工具。
- 用标题当键在 OpenSpec 内可行，但跨出 OpenSpec 就失效；这是 B/C 的共同边界。
