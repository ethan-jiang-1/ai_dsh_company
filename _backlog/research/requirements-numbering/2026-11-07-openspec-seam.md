# 编号 × OpenSpec 接缝（2026-11-07 第二轮推敲）

## 前提（已定，不再讨论）

1. **多层需求文档是要的**：MRD → StRS → PRD → SyRS → IRS（用户 2026-11-07：这不是问题，是前提）。
2. **SW 与 FW 已经在用 OpenSpec 作为实践**（用户 2026-11-07）。
3. **OpenSpec 能承载我们的编号**：它开放、可自定义；它的强项是**加工流程与次序**，不是字段封闭
   （用户 2026-11-07，直接否掉"要不要查它撑不撑得住"这条）。

> 因此本轮不再讨论"要不要编号/要不要多层文档/OpenSpec 行不行"，只讨论**接缝与集合**。

## 接缝：谁是主键，谁是外键

| 侧 | 身份 | 生命周期 |
|---|---|---|
| 我们的需求文档（StRS/SyRS/IRS） | **主键**：`SYR-014` / `IFR-003` | 跨动议长期存在；供应商/实验室/客户引用它 |
| OpenSpec（SW/FW） | **外键**：`specs/<capability>/spec.md` 里 `### Requirement:` + `#### Scenario:` | 随迭代演进；capability 长期存在，标题可能改 |

**方向**：引用写在**下游**——OpenSpec 的 requirement 里带一行上游编号（如 `Traces: SYR-014, IFR-003`），
我们的需求文档**不回引** capability。理由：
- 需求冻结后不该因为代码侧新增 capability 而回改（"已 present 的件不回改"）；
- 上游文档在写的时候，下游 capability 可能还不存在。

**为什么不能反过来用标题当键**：OpenSpec 的身份是 `(capability, requirement 标题)`，标题会改；
我们的编号不会。硬软一体的另一端（供应商 BOM、实验室报告）根本没有 capability 概念。

## 三种接缝落法（待选）

| 落法 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 需求体内带 `Traces:` 行** | OpenSpec 每个 `### Requirement:` 下加一行 `Traces: SYR-014, IFR-003` | 编号随需求走，`rg` 双向可查；不依赖外部表 | 依赖团队愿意加这一行；`openspec validate` 不管它（要我们自己的检查补） |
| **B. 附录映射表** | `allocation`/`trace` 表里写 `SYR-014 ↔ capability/requirement 标题` | 一处集中，好审 | 标题一改就静默失效；表会腐化 |
| **C. `openspec/project.md` 约定** | 在 OpenSpec 的项目约定文件里写死"每条需求必须带 Traces 行" | 变成团队公约，AI 会照做 | 仍是约定，没有机械强制 |

**建议 A + C 组合**：约定写进 `project.md`（让 AI 照做），编号写进需求体（让 grep 可查）；
B 只在跨组织（供应商）时才用，因为供应商不看我们的 OpenSpec。

## 前缀集合：两种方案（这是真正要你拍的）

| | 方案一：6 套 | 方案二：3 套 + 文档号 |
|---|---|---|
| 编号 | `MR / STR / REQ / SYR / IFR / TC` | `SYR / IFR / TC` 三套原子编号；上游文档用**文档号 + 章节号**（`PRD-3.2`） |
| 谁有原子编号 | 所有层 | 只有"要跨组织、要进 OpenSpec、要被验证"的层（系统/接口/验证） |
| 上游追溯怎么表达 | `SYR → STR-001` | `SYR → PRD-3.2（PRD 的 3.2 节）` |
| 优点 | 每层都能被独立引用；覆盖表精确到条 | 前缀少一半；上游文档保持"文档"而不是"条目库" |
| 缺点 | 6 个空间，模型要在其中选；上游（MRD/StRS）实际很少被单独引用 | 上游追溯粒度粗（到节，不到条）；改章节号会断 |
| 与 OpenSpec | 无差别（OpenSpec 只关心下游引用） | 无差别 |

**我的倾向**：**方案二**。理由：真正要跨出我们文档体系的只有三样东西——系统需求（给供应商/研发）、
接口（硬软那条缝）、验证（实验室/供应商/客户）。MRD/StRS/PRD 是**我们自己内部的对话**，
用文档 + 章节就够；给它们编号的收益（跨组织引用）几乎为零，成本（每层一套号 + 模型选择）却是实的。
但这条要你拍，因为它决定"六套还是三套"。

## 还没定的问题（缩减到 4 条）

1. **前缀集合走方案一还是方案二**（6 套 vs 3 套）。
2. **NFR 怎么保证不漏**：`kind` 字段 + "安全/法规类为 0 ⇒ 报警"，还是接受漏（BUG-034/035 就是这么漏的）。
3. **检查器**：要不要有"编号与追溯检查"？放在哪一层（我们的文档/OpenSpec 侧/两边各一）？
   注意：硬软一体有两套世界，检查器必须**同时读 OpenSpec 树和非 OpenSpec 文档**。
4. **范围**：只用于"落地项目"，还是所有动议（含 demo）。

## 已知边界（先写清，免得实施时才发现）

- OpenSpec 的 `openspec validate` **不会校验我们的编号**，加多少自定义字段都由它的 schema 说了算；
  我们若要强约束，必须自己在外面加检查（读它的树）。
- 供应商与实验室不读 OpenSpec ⇒ 给他们的文件里，编号必须是**纯文本可读**，不能依赖链接/工具。
