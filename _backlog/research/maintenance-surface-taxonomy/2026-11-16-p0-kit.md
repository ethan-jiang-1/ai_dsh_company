# P0 包：三仓先装同一份合同（零搬家）

> P0 只做三件事：**放一页合同、在根布局与目录 README 写面声明、登记例外**。不搬文件、不改名、不动预算。三仓各自 `verify` 绿即完成。
> 为什么先做 P0：P1/P2 的搬家要改引用、撞预算；而"人和 fresh agent 不糊涂"这件事，**靠面声明就能拿到八成**，不必等目录动完。

## 1. 合同 v1（三仓同文，可直接落 `docs/`）

```text
维护面合同 v1（2026-11-16）

面 = 入口层的一个动词。三面：judge / show / operate。
- judge   红了会拦下变更或退回返工    目录：checks/
- show    红了只是让人来看现场        目录：probes/
- operate 红了意味着活没干成          目录：tools/（dev 只作 tools/dev 组）

两层
- oracle：由 pnpm test 的 runner 跑（vitest / node:test）→ tests/，不是面。
- entry ：要自己起命令/进程/浏览器 → 上面三面。

判定（按顺序）
1. 由 pnpm test 跑？→ tests/。
2. 红了谁动？拦人=judge；看现场=show；重做活=operate。
3. 守卫：双模件按主产物；runner/reporter/fixture/lib 跟消费者；混合件按终端产物。
4. 仍冲突：失败语义 > 产物形态 > 名字。

非面：tests lib drivers fixtures runners reporters snapshots runtime run-config 台账/文档。
新增：默认随目录的面；破例登记一行理由 + 失败类；搬家不占预算，新增才占。
纯度：某面里动词一致的条目 / 该面条目总数；<80% 记"待收敛"，先观察不设硬门。

目录名：checks/ = judge，probes/ = show，tools/ = operate（dev 只作 tools/dev 组，scripts 退役）。
```

## 5. 每仓 P0 验收（不改目录）

1. `pnpm verify` 绿（新文档被索引、链接可解析、预算不超）。
2. 根布局块与三个目录 README 的第一屏都能一眼看到面声明。
3. 例外表里的每一条都能在盘上找到；非面条目没有被写进资产清单。
4. 不出现第二个"面"的清单：合同只此一份，README 只链接。

## 6. P0 不做 / 已知不完美

- 不搬 `tools/observe`、不改 `scripts`/`dev` 名、不拆 release/run-ops；这些是 P1/P2。
- P0 期间 `bsimulation` 的 `checks` 与 `deep_research` 的 `scripts` 仍是混装，合同里必须如实写"待拆"，不许写成已收敛。
- 面声明与目录冲突时，**以合同例外表为准**，不以目录名为准；这条要写进三份 README 的第一行，防止 fresh agent 按名字猜。

## 7. 建议应用顺序

1. company（8 个例外、已有三面名，改动最小）——先证明合同形状可行。
2. `bsimulation`（组级例外 5 条，无需改名）——验证"混装组"能被合同容纳。
3. `deep_research`（两种"面"术语冲突）——验证合同能在术语冲突的仓里活下来。

三仓都过 P0 后，再决定 P1 改名是否值得；不改名也能获得八成清晰度。
