# DSH 测试策略：把「让绿有意义」拆成可借鉴的机制，而不是再抄一轮规则

> 问题：DSH 的测试策略（55 行宪法 + 2,150 个 spec + 六面防漏与复盘回路 + 5 步决策 + 9 个必需 CI job）到底是什么形状？
> 哪些部分能落到本仓、怎么落、先落哪几件？为什么 2026-10-04 已经吸收过一轮，五周后还在"调整测试资产"？
> 消费者：用户 2026-11-13 点名研究（承 2026-11-13 git 复盘：近 200 个 commit 里碰测试面的 112 个、碰源码面的 70 个）。
> 产出的卡：[2026-11-13 测试资产自校正系统（B → C → A）](../../issues/2026-11-13-test-asset-loop.md)
> 初步判断：差距不在"读没读过 DSH"，而在**吸收只到了散文层**——层表、证据纪律、命名语法都写进了宪法，
> 但选中（后缀→lane）、下限（覆盖率门）、必跑（真入口 lane）、账本（显式未覆盖）四类**机器**一件没建，
> 所以修的都是症状。
> 结论：借环路不借规模，按 B（环外必跑回路）→ C（执行下限与账本）→ A（盘子与出生登记）三件落地；
> 约 5 个工作日、全部可逆、每件可单独停。用户 2026-11-13 已定性并转卡。

## 一句话结论

> 借 DSH 的**机器**（选中、下限、必跑、账本），不借它的**规模**（2.7 万用例、9 个 CI job、per-file 100%）；
> 每条规则出生时就定载体（gate / skill / Note / 作废），并把"故意不做"写进 Note——
