## 3. 失败证据（这些是推敲的事实基础，不是假设）

1. **编号漂移三例**：同一件事实测出现 `IF-###` 与 `IFR-###` 并存；验证项出现 `V-01…V-30`、`V-001…V-040`、
   `VP-###` 三种写法（v1/v4/v5 三轮 E2E）。
2. **声称与实际不符**：v5 的收口稿写"21 条接口"，而架构稿实有 **23** 条 `IF-###`。
3. **漏需求的代价**：本轮评审找出两条真缺陷（BUG-034 无绝对时间源、BUG-035 无短路耐受），
   本质都是"某条非功能需求根本没被写出来"——**没有任何机制会发现"少写了一条"**。
4. **加角色的面数**：0.9.0 加 CMO 用了 9 个提交、97 个文件——这类体系改动成本高（事实）；这对流程意味着什么，待讨论。

## 4. 外部实践（AI 编码时代，2025–2026）

| 工具 | 编号做法 | 结构 | 强制机制 |
|---|---|---|---|
| **Kiro（AWS）** | **零前缀**：`Requirements 1`，验收条目 `1.1 / 1.2`；任务里写 `_Requirements: 1.1, 1.5_` | `requirements.md` / `design.md` / `tasks.md`，一层 | 约定 + 评审 |
| **Spec Kit（GitHub 生态）** | 少量前缀 `FR-001` / `NFR-001` / `AC-001` | 单份 `spec.md` → `plan.md` → `tasks.md` | 约定；CLI 校验质量 |
| **OpenSpec** | **无编号**：身份 = capability 目录 + 需求标题；deltas `ADDED/MODIFIED/REMOVED`；每条需求必须 ≥1 `#### Scenario:` | `specs/`（现状真相）+ `changes/`（提案） | `openspec validate --strict` |

来源：
- Kiro spec 格式（社区镜像的 steering 文档）：<https://raw.githubusercontent.com/cremich/promptz.lib/main/steering/kiro-specs.md>；
  官方页 <https://kiro.dev/docs/specs/feature-specs/requirements-first/>（抓取只得到导航）
- Spec Kit 的 `FR-/NFR-/AC-` 写法取自第三方 skill 模板 <https://skillmd.ai/pt/skills/spec-kit-integration/SKILL.md>；
  **官方 `templates/spec-template.md` 多次抓取只得到导航，正文未取到**——此条为二手证据，用前需复核
- OpenSpec 指令全文：<https://raw.githubusercontent.com/asiaostrich/universal-dev-standards/a8112c5f730d3a5236a8f46991168a6033b26a8c/integrations/openspec/AGENTS.md>

**可能可迁移的三点（待验证）**：① delta 语义（改需求写 ADDED/MODIFIED，不重写全文，天然满足"已 present 不回改"）；
② 一个观察：OpenSpec 强制每条需求至少一个场景——这是否是"纪律"的关键，待验证；③ 一个观察：OpenSpec 不编号、
靠 capability + 标题；编号在跨文档引用时是否必要，待验证。

**可能不可迁移的两点（待验证）**：① 它们都假设**单一空间**（一个仓/一份 spec），硬软一体的需求分散在供应商 BOM、
外包固件、实验室报告里；② 它们都没有"层"的概念（按 capability 分，不按责任层分）。

## 5. 硬软一体带来的四条硬约束

1. **ID 必须能单独读懂**：`IFR-014` 贴进供应商 Excel、邮件、CAD 注释、试验报告，必须指着同一件事。
   ⇒ 跨项目并行时可能要在编号前加项目键（`POD1-IFR-014`），避免撞号。
2. **验证是分家的**：自测 / 供应商 FAT/SAT / 第三方实验室 / 客户现场。谁验不写清 = "都以为对方验了"。
   ⇒ 候选方案：每条需求带 `verifier`。
3. **接口是硬软那条缝**：`IFR` 的两端必须各有一个 owner，缺一端就没人负责。
4. **专业域跨越多方**：壳体散热 = ME+HW、采样时序 = FW+HW ⇒ 专业域只能作**附录**（派工视图），
   不能进编号（会逼出两个号），也不宜逐条必填（复杂度爆炸）。

## 6. 待推敲的开放问题（本阶段要答的）

1. **层数**：MRD→StRS→PRD→SyRS→IRS 五层是否都必要？StRS 与 PRD 是否可并？SyRS 与 IRS 是否可并？
   （用户已拍"StRS 在 PRD 之前、SyRS/IRS 归 SA"，但**层数本身**没定过。）
2. **前缀集合**：是否就是 `MR / STR / REQ / SYR / IFR / TC`？`MR` 是否算需求（它是选项账本）？
   `REQ` 是泛称，将来加层会不会歧义？
3. **非功能需求**：NFR（安全/法规/环境/可靠性）要不要独立编号，还是靠 `kind` 字段 + "NFR 数为 0 ⇒ 报警"？
   （BUG-034/035 都出在这里。）
4. **校验器**：要不要有编号校验器（此前试写的 requirements-check）？如果要有，判据是哪几条（R1–R6 哪些是必须的）？
   它是"门禁"还是"操作员工具"？（角色不能在会话里跑脚本。）
5. **追溯矩阵**：粒度到"每条需求一行"还是"每层一张汇总表"？谁维护、谁审？
6. **附录 vs 字段**：专业域附录（`allocation.md`）是否够用？是否需要"待认领"栏？
7. **适用范围**：这套只用于"落地项目"，还是所有动议（含 demo）都要走？
