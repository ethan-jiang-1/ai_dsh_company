## 3. 证据审计：事实、反转与两套并存

> 方法：只读盘面，grep + 读文件；每条给路径与行号。`company-workspace/` 与 `runtime/` 是 gitignored 运行态，路径用行内代码标注，不作为仓库链接。

### 3.1 反转：v5 的 "23 条接口" 是建议新增，不是已定义

**事实（当前盘面）**

- v5 SA 稿的接口清单标题写 "21 条"（`company-workspace/.dsh-company/deliverables/2026-11-06-portable-overload-detection-v5/drafts/sa-architecture.md:364`）；文末自检写 "IF-001~IF-021 共 21 条"（同文件 `:589`）；"21 条连续不跳号"（`:597`）。
- v5 final 写 "21 条接口（IF-001~IF-021）"（`.../v5/final.md:8`）。
- `IF-022` / `IF-023` 只出现在 SQA 稿的 "B-05 最小修复方向：①补 2 条 IF"（`.../v5/drafts/sqa-vv.md:109`）；SQA 同一稿 `:196` 写 "覆盖 21/21 齐全"。
- 研究材料把它写成 "final 说 21，文档实有 23"（[artifact-review.md:66](../../sa-sqa-product-review/2026-11-06-artifact-review.md)、[numbering-deliberation.md:41](../history/2026-11-07-numbering-deliberation.md)）。

**这暴露的问题（不是结论，是失败模式）**

- "定义 / 引用 / 建议新增" 三种 ID 在文本里形状相同；Agent 看到 `IF-022` 无法判断它是哪一种。
- 误读发生在评审者身上，不在作者身上；作者写 21 是对的，SQA 写 21/21 也是对的。**观察：编号唯一并没有阻止这次误读；"定义点是否可机械识别"是一个待验证的变量。**
- 质量审计 Q6 的判据是 "final 声称 vs SA 稿实有"，21=21 应当 PASS；研究材料把 "Q6 抓到 23" 当成事实，与当前盘面不符。
- 若评审后文件被改过，则需重核；但 SQA 的 21/21 与 final 的 21 互相印证，当前盘面自洽。

### 3.2 两套规则同时活着：回滚残留 + 另一套 lab

**事实**

- 主 workspace 的 v1–v5 产物里，`IFR` / `SYR` / `STR` 一次都没出现（grep 全目录）。
- `company-workspace/.dsh-company/kb/process-docs.md` 仍然存在，且仍写 `STR-### / SYR-### / IFR-###`（`:6`、`:16`、`:35`）。它是回滚前 bootstrap 种下的状态，`git reset` 只回了源码，没有回滚 workspace 里的种子文件。
- `runtime/lifecycle-lab/real-ws` 另有一套真实跑过的五层产物：`2026-11-06-portable-overload-requirements/drafts/{str,syr,irs}.md`，16 STR / 33 SYR / 22 IFR。
- pack 的 preset 说 `IF-###`（SA）与 `VP-###`（SA/SQA）；workspace 的 `process-docs.md` 说 `STR/SYR/IFR`。

**这暴露的问题**

- "IF 与 IFR 并存"不是同一份文档里的漂移，而是 **两套规则同时活着**：一套在 pack，一套在 workspace 的 kb。Agent 换一个 workspace 就换一套语法，而且不知道哪套权威。
- 回滚不完整本身就是一个可能的糊涂源：源码回了，状态没回。后续若恢复/再实施，"种子状态是否随源码回滚/刷新"是一个待处理的问题。

### 3.3 缺上游时，Agent 会自造编号空间

**事实**

- v4 SQA 稿在 `drafts/` 无 PRD 时，发明了 `VR-01…VR-15`，并明写"本文件临时编号，PRD 出具后须一一回填"（`company-workspace/.dsh-company/deliverables/2026-11-06-portable-overload-detection-v4/drafts/sqa-vv.md:32-34`、`:268`）。
- v5 仍然没有 `mrd.md` / `prd.md`，于是这套"临时编号"从未被回填，变成了事实上的常驻编号。

**这暴露的问题**

- 缺上游不是"空着"，Agent 会填一个看起来合法的本地空间。如果要有强制机制，"缺上游/缺层是否应判红"是一个待探索的问题——现状允许临时编号绕过。
- `VR` 这种 token 没有先验，回填也无从校验；它正是"临时措施永久化"的样本。

### 3.4 与角色名撞的 prefix 不会被可靠采纳

**事实**

- SQA 的 skill 明写验证点用 `VP-###`（[vv-playbook:25](../../../../packages/company-pack/presets/system-qa/skills/vv-playbook/SKILL.md)）。
- v5 SQA 实际写的是 `V-001~V-046`（`company-workspace/.dsh-company/deliverables/2026-11-06-portable-overload-detection-v5/drafts/sqa-vv.md:9`、`:269`），同一张表里还出现 `VP-Eng`（如 `:223`）。
- SA 的 skill 也把 `VP-###` 当验证点；v5 SA 写 `VP-01~VP-14`，SQA 写 `V-###`，同一个概念两个 token。

**这暴露的问题**

- `VP` 的强先验是 "Vice President"，而本仓上下文里真有 `VP-Eng` / `VP-Sales`。先验撞车时，instruction 也未必救得回来。
- 一个待验证的变量是：同上下文里的角色名/领域词，是否会让 token 产生更强的错误解释。这不是"Agent 不听话"的问题。

### 3.5 收口检查会"空过"

**事实**

- 收口审计的 10 条判据只查接线与产物在场：CEO depth、VP-Eng 成员、SA/SQA 独立会话、final 存在且点名 SQA、SQA 稿含否决、SA 稿含 IF（[sa-sqa-closeout-audit.mjs](../../../../probes/team/sa-sqa-closeout-audit.mjs)）。
- 这套判据不要求 `mrd.md` / `prd.md`；v5 的 `drafts/` 只有 `ceo.md`、`sa-architecture.md`、`sqa-vv.md`、`vp-eng.md`，没有 MRD/PRD，收口仍可 10/10 PASS。
- `/prd check` 是**人命令**，只读固定路径 `{mrd,prd}.md`（[prd-command.ts](../../../../packages/company-pack/src/host/prd-command.ts)）；缺文件会报错，但没人跑它。

**这暴露的问题**

- "有检查"不等于"检查覆盖了对象"。检查器只看它看得见的东西；对象缺失时，它可能空过。
- 一个待探索的问题是：强制点是否应放在"有后果的时刻"（present/收口），以及缺件是否应判红，而不是"跳过/不适用"。

### 3.6 lab 五层：内部自洽，但 PRD→SyR 边缺失

**事实**

- lab 的 16 STR / 33 SYR / 22 IFR 内部自洽：16/16 STR 被至少一条 SYR 覆盖；33 条 SYR 全部有 STR 追溯；22 条 IFR 全部有 SYR 追溯（逐节解析核过）。
- 但 33 条 SYR 的 `追溯` 只列 STR，没有任何一条列 REQ；`prd.md` 里 0 个 STR 引用。
- StRS 是后补的上游：它引用的是**前一个动议** PRD 的 AC（如 `AC-001-4`），而 PRD 不知道 StRS 存在。

**这暴露的问题**

- "五层链条第一次跑通"是超额声明：文档齐了，**PRD→SyR 这条边没闭合**。这提示"手写追溯矩阵"可能不可靠——空列没人填就没人发现（待验证）。
- 追溯矩阵：生成还是手写、粒度如何、谁审，是待探索项（见 §4-H、§6-H）。

### 3.7 跨动议裸 ID 与 near-miss

**事实**

- lab 的 StRS 里 `AC-001-4` 指另一个动议的 PRD（`runtime/lifecycle-lab/real-ws/.dsh-company/deliverables/2026-11-06-portable-overload-requirements/drafts/str.md:37`）。
- 同一份 StRS 里 `AC-008` 不是合法的 AC 号（合法形 = `AC-###-#`），却被当作"PRD 的 AC-008 组"使用（`str.md:67`、`:83`）。
- `syr.md` 里 `AC-001`（REQ 级引用）与 `AC-001-1`（AC 级）混用；`AC-001` 不匹配 `/prd check` 的 AC 文法。

**这暴露的问题**

- 裸 ID 不是跨动议自足的；"裸 ID = 本动议，跨动议 = 项目键 + ID"只是候选规则之一，不是已定规则。
- near-miss 形状（`AC-###` 少了第三段）是否必须判红，取决于最终文法；但它是现实存在的歧义源。

### 3.8 `/prd check` 的能力与边界（现有唯一机械检查器）

**它已经做的**（[prd-check.ts](../../../../packages/company-pack/src/lib/prd-check.ts)）：

- `MR-###` / `REQ-###` / `AC-###-#` 文法与重号；
- REQ 的 `source` 指向存在的 MR；no-go 不得进 PRD；defer 不得进 P0；
- slice 存在且列出该 REQ；`dependsOn` 存在且无环；
- AC 的父号与 REQ 号一致；状态机与 changeLog；每条 REQ 至少一条 AC。

**它没做的**：

- 跨层需求文档（StRS/SyRS/IRS）不在扫描面；
- NFR/约束覆盖、count 声称、提案 token、near-miss、正文 vs JSON 一致性、跨动议；
- 不做文件存在性以外的"层完整性"判断；
- 没有任何自动触发点（人命令）。

**这暴露的问题**

- 它的形状（纯逻辑、keyless 可测、命令 + 测试）是候选先例；但它的**覆盖面与触发点**是否够，是待探索项。
