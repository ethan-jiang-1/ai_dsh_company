# GPT-6.1-terra 的第一直觉与推荐

> **文档性质**：这是 GPT-6.1-terra 基于当前研究材料形成的独立判断，不是用户已拍结论，不是 RFC，也不是实施授权。
>
> **研究边界**：本文件只记录判断和推荐；不修改 pack、tools、tests、workspace 或运行态，不替代本题已有的候选与验证材料。

## 1. 我读到的核心问题

我的第一直觉是：这不是一个单纯的“挑前缀”问题，而是一个**让 Agent 无法把不同语义混在一起的标识与语法问题**。

当前研究已经暴露出至少五类容易混淆的对象：

1. 已经定义的条目，例如 `IF-021`。
2. 对已定义条目的引用，例如在另一份文档中提到 `IF-021`。
3. 建议新增但尚未定义的条目，例如 `IF-022` / `IF-023`。
4. 不同动议中的同形编号，以及缺少项目上下文的裸 ID。
5. OpenSpec 内的 requirement 与 OpenSpec 外的 MRD、PRD、StRS、SyRS、IRS 条目之间的追溯关系。

如果这五类对象仍然使用同一种文本形状，仅仅把 `STR` 改成 `SYR`、把 `IFR` 改成 `IF`，并不能让 Agent 稳定判断。当前证据已经显示：

- `IF-022` / `IF-023` 的建议新增语境与已定义条目形状相同，导致定义、引用、建议新增难以区分。[证据审计 §3.1](research_topic/2026-11-07-evidence.md)
- pack 与 workspace 同时存在 `IF/VP` 和 `STR/SYR/IFR` 两套规则，Agent 换上下文后可能换一套语法。[证据审计 §3.2](research_topic/2026-11-07-evidence.md)
- 上游缺失时，Agent 会自行创建 `VR` 临时编号空间，临时规则可能变成事实上的常驻规则。[证据审计 §3.3](research_topic/2026-11-07-evidence.md)
- `VP` 在当前上下文中还会被理解为 Vice President，说明前缀可能和角色名称发生先验冲突。[证据审计 §3.4](research_topic/2026-11-07-evidence.md)
- 文档和数量检查可能在对象缺失时空过；有检查器不等于检查覆盖了正确对象。[证据审计 §3.5](research_topic/2026-11-07-evidence.md)
- lab 样本的 PRD→SyRS 追溯边缺失，说明编号正确不等于追溯闭合。[证据审计 §3.6](research_topic/2026-11-07-evidence.md)

因此，我不会把“选择一个模型看起来熟悉的前缀”当作完整方案。前缀只能负责传递一小部分第一眼语义；定义语法、提案语法、层级边界、跨动议上下文和机器检查必须一起设计。

## 2. 已知约束对推荐的影响

我把研究材料中的已拍前提视为硬约束，而不是推荐项：

- 必须编号。
- 一件东西保持一个稳定编号，不因为跨层或跨 discipline 就重复起号。
- discipline 不进入前缀，只能作为附录、派工或视图信息。
- 不继续增加前缀族。
- MRD→PRD→StRS→SyRS→IRS 是既定文档链。
- SW/FW 已经使用 OpenSpec，且 OpenSpec 可以承载自定义编号。
- 外部供应商、实验室和客户需要能在 Excel、邮件、CAD 注记或试验报告中看到并理解编号。

这些约束使纯 UUID、纯数字、只靠章节号、只靠 OpenSpec capability 标题等方向不适合作为单独答案。它们可以作为机器内部键或派生视图的局部手段，但不能单独承担跨组织可读的需求识别。

## 3. 候选方向

### 3.1 方向 A：按条目种类编号，层级由文档身份表达

示例：

```text
REQ-001       需求条目
IF-001        接口条目
TC-001        测试用例
AC-001-1      REQ-001 下的验收标准
```

MRD、PRD、StRS、SyRS、IRS 是文档层身份，不再为同一个需求因为所在层不同而各起一个层前缀。文档自身通过标题、文件名或机器可读的文档元数据声明层级。

在这个方向里：

- `REQ` 表示条目种类是 requirement，不表示它属于哪一层。
- `IF` 表示接口条目；接口的两端 owner、verifier 和关联 discipline 放在条目字段或 allocation 附录。
- `TC` 表示 test case，不把验证机构或 discipline 编进 ID。
- NFR 更适合先作为 requirement 的 `kind` 或覆盖清单，而不是再创建一套 NFR 编号空间；这需要 V9 验证，不能直接视为定论。
- `AC-001-1` 只有在验收标准被视为独立可引用对象时才使用；它不应被误解为给同一个 REQ 再起第二个编号。

**我认为它的主要优点**：

- `REQ`、`IF`、`TC` 是常见工程语义，较可能满足“第一眼知道是什么”的要求；但 V1 盲测尚未运行，这只是先验判断。
- 前缀数量不随文档层数增长，符合“前缀不要再加”。
- 同一条需求不会因为从 StRS 分解到 SyRS、再进入 OpenSpec 就被迫产生多个层级编号。
- OpenSpec 可以在 requirement 内写 `Traces: REQ-001` 或 `Traces: IF-001`，保持我们的稳定 ID 作为跨世界锚点。
- discipline、owner、verifier、状态、变更和追溯关系可以显式表达，而不污染 ID 的核心语义。

**我认为它的主要风险**：

- 裸 `REQ-001` 在跨动议或跨项目场景中可能不够自足，需要项目键、文档上下文或明确的跨动议引用语法。
- 层级不在 ID 中，Agent 必须能可靠读取文档身份；这要求文档头、目录结构或注册信息是机器可解析且唯一权威的。
- `REQ` 跨 MRD、PRD、StRS、SyRS 使用时，必须明确“条目种类”和“文档层”是两个不同轴，避免 Agent 重新把 `REQ` 当成某一层专属编号。
- `AC` 的父号关系、需求全局性和并发分配规则仍要通过 V2/V7 验证。

### 3.2 方向 B：文档限定的条目编号

示例：

```text
PRD-REQ-001
SyRS-REQ-001
IRS-IF-001
```

这里把文档层和条目种类都放进编号，定义点在 ID 中更显眼。

**可能的优点**：

- 跨文档引用时，条目来自哪一层更容易直接看见。
- 每份文档可以有自己的局部序列，不一定需要一开始就建立全局分配机制。
- 对外导出时，文档身份和条目类型都在文本里，外部读者不必先打开原文。

**主要风险**：

- 编号变长，前缀和文档码叠加后会增加 Agent 和人的判断负担。
- 文档改名、层级调整或文档合并会把文档身份变化传导到大量 ID，增加迁移成本。
- 容易把“同一件东西在不同文档中的表示”误做成多个编号，和“一件东西一个编号”产生张力。
- `PRD`、`SyRS` 等文档码的语义更像文件/文档，而不是条目种类，第一眼未必能区分“这是文档号还是条目号”。

## 4. 我的偏向

我偏向**方向 A：种类优先、层级由文档身份表达**。

更准确地说，我推荐的是下面这个组合，而不是只推荐一组孤立的前缀：

1. **Canonical ID**：使用稳定、少量、通用的条目种类前缀，例如 `REQ`、`IF`、`TC`、必要时的 `AC`。
2. **Document layer**：由文档头或机器可读元数据声明 `MRD`、`PRD`、`StRS`、`SyRS`、`IRS`，不把层级重复编码进同一条需求的 ID。
3. **Definition grammar**：正式定义必须出现在明确的标题、表格首列或结构化账本中，不能只凭正文中出现一个像 ID 的字符串来判定“已定义”。
4. **Proposal grammar**：建议新增必须使用独立的提案形状，例如 `NEW` / `TBD` 或显式 `proposal:`，不能直接写成正式 `IF-022`。
5. **Trace grammar**：跨文档和 OpenSpec 引用使用稳定 ID；下游写 `Traces:`，并由检查器验证目标存在、方向正确和必要的边闭合。
6. **Context grammar**：同一动议内可使用短 ID；跨动议、跨项目或外部导出时必须带项目/动议上下文，不能假设裸 ID 永远唯一。
7. **Allocation view**：HW、ME、FW、SW 等 discipline 只进入 allocation/派工附录或视图，不进入每条 ID，也不逼同一需求产生多个编号。
8. **Machine checks**：检查器必须同时覆盖定义、引用、提案、near-miss、跨动议、追溯、owner、verifier、NFR 覆盖和数量声明，不能只检查正则和重号。

这里的关键判断是：**让 ID 表示“这是什么类型的可引用对象”，让文档上下文表示“它处在哪一层”，让结构化语法表示“它现在是什么状态以及如何被引用”。** 这样比让一个前缀同时承担种类、层级、专业域、状态和来源更容易让 Agent 正确解析。

## 5. 为什么不是只选一个“看起来最像层名”的前缀

我不偏向 `STR`、`SYR`、`IFR` 作为主要识别轴，不是因为层级不重要，而是因为当前材料已经指出它们的第一先验不够稳定：

- `STR` 可能被读成 string。
- `SYR` 缺少稳定的工程第一先验。
- `IFR` 在已有语境中可能被读成 instrument flight rules。

这仍然不是 V1 的实测结论。真正的决策必须跑盲测。但从当前证据和 Agent 优先的目标看，让自造的层级缩写承担最重要的第一眼语义，风险高于使用通用的条目种类词。

同样，我不偏向 `VP`、`V`、`VR` 作为验证主前缀，因为已有盘面已经显示它们会与 Vice President、voltage/version、virtual reality 或不同历史规则产生强烈冲突。验证对象最好使用稳定的通用条目类型，例如 `TC`，而验证组织、验证方式和证据由字段表达。

## 6. 不能靠编号单独解决的问题

即使采用方向 A，下面的问题仍然必须单独解决：

| 问题 | 不能只靠什么解决 | 必须补的机制 |
|---|---|---|
| `IF-022` 是正式定义还是建议新增 | 换成另一个接口前缀 | 独立提案语法 + 定义点规则 |
| 两套规则同时存在 | 选一个更漂亮的前缀 | 单一权威词表 + 旧规则迁移/冻结策略 |
| 缺上游时 Agent 自造 `VR` | 让 `VR` 看起来更正式 | 缺失上游判红 + 禁止临时编号空间 |
| PRD→SyRS 追溯断边 | 给 SyRS 换前缀 | 下游 traces + 生成/校验的追溯图 |
| 跨动议裸 ID 歧义 | 把序号加长 | 项目/动议限定的引用语法 |
| NFR 漏写 | 增加 `NFR` 前缀 | 文档级 NFR/constraint 覆盖清单，缺失或 `n/a` 必须有理由 |
| IRS 空过 | 把 `IF` 改成 `IFR` | 明确 IRS gate 的 owner、verifier、trace、失败态判据 |
| OpenSpec 与非 OpenSpec 脱节 | 依赖 `openspec validate` | 双世界检查器，或明确的外部 trace 校验 |

## 7. 当前推荐的最小样子

以下只是用于后续验证的纸面草案，不是最终格式：

```markdown
---
layer: SyRS
---

### REQ-014 设备必须在规定时间内提供稳定采样时钟
kind: NFR
status: defined
owner: system-architecture
verifier: third-party-lab
traces: [REQ-007]
discipline: [FW, EE]
```

接口示例：

```markdown
### IF-006 采样时钟接口
status: defined
owners: [firmware, electronics]
verifier: third-party-lab
traces: [REQ-014]
discipline: [FW, EE]
```

OpenSpec 侧只需要把稳定 ID 作为追溯锚点，例如：

```text
Traces: REQ-014, IF-006
```

建议新增不能写成正式定义：

```text
proposal: NEW-IF — 增加断电恢复后的采样时钟接口失败态
```

这个样子还没有回答所有字段、注册分配、外部导出和变更规则；它的用途只是让 V3、V4、V5、V11、V13 能有一个可比较的最小原型。

## 8. 需要优先验证的事项

我的推荐仍然需要证据推翻或确认，优先级建议如下：

1. **V1**：对 `REQ`、`IF`、`TC`、`STR`、`SYR`、`IFR`、`PRD-REQ` 等 token 做无上下文盲测，记录第一反应和错误解释。
2. **V2**：用真实 16 STR、33 SYR、22 IFR 样本重键，验证方向 A 是否真的避免同一对象多号，并检查 AC 父号关系。
3. **V3/V4**：验证正式定义、引用、提案和 near-miss 是否能被 Agent 与机器可靠区分。
4. **V5/V13**：验证 `Traces:` 是否能覆盖 OpenSpec 内外，并能发现 PRD→SyRS 空边。
5. **V8/V16**：验证项目键、英文 ID 和中文文档在供应商/实验室/客户导出中是否够用。
6. **V9/V11**：验证 NFR 清单和 IRS 检查点是否能阻止真实漏项，而不是只让编号看起来整齐。
7. **V7/V15**：验证旧规则迁移、作废、变更和影响分析成本。

在这些验证前，我建议把“方向 A”称为**我的偏向假设**，不要写成用户已选方案，也不要据此恢复此前已回滚的实现。

## 9. 一句话结论

我的第一直觉和当前推荐是：**用少量、通用、按条目种类的 ID 作为稳定锚点，让 MRD/PRD/StRS/SyRS/IRS 承担层身份，让定义/提案/引用/追溯各自拥有可判定语法；在两个候选方向中，我偏向 `REQ/IF/TC` 这一类“种类优先、层级外置”的方案。**

这只是 GPT-6.1-terra 的推荐，最终取舍仍由用户在验证证据基础上决定。
