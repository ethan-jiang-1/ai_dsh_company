# 需求识别与编号：共识

> **这份文件是什么**：本研究题（硬软一体、多 discipline 场景下的多层需求文档）的结论。只读这一份，就能知道为什么研究（§1）、盘面出了什么事（§2）、怎么推的（§3）、结论是什么（§4）、和已拍约束对不对得上（§5）、还差什么（§6–§7）。
> **证据分层**：§1–§2 是事实（可复核，见 [evidence](research_topic/2026-11-07-evidence.md)）；§3–§4 是研究结论（三份独立判断 + 盘面收敛）；§5 是用户已拍硬约束与本结论的对照；§6 是未定参数。**结论不授予实施。**
> **一句话**：ID 只承载身份——「它是什么种类 + 第几号」；层归文档、状态归条目、专业域与验证方归字段。

## 0. 三十秒版

| 问题 | 答案 |
|---|---|
| ID 里编什么 | 只编种类：`MR` 市场需求、`REQ` 需求（任一层）、`IF` 接口、`TC` 验证；`AC` 从属父 REQ |
| 层放哪 | 文档。一份文档一层；文档头声明「层」与「定义形态」。层不进号 |
| 建议新增怎么标 | 状态，不是号形。ID 不变，条目状态写「草案」；不新增任何前缀 |
| 追溯怎么来 | 作者写（下游 `Traces:`）→ 索引派生矩阵 → 检查器判红。不从正文「聚集」 |
| 机器怎么判红 | 悬空号、重复定义、缺层缺件、退役词出现、计数与索引不符 |
| 最大代价 | ID 不再自解释层与状态 → **「每个号必须解到一行」成为承重规则** |
| 还没验证 | 词表盲测（V1）没跑；状态位落点、层数层序、IRS 闸口径未拍 |

## 1. 背景

### 1.1 场景

硬软一体产品，不是纯软件。SW / FW / EE / ME / 系统测试在同一产品里并存；一条需求常跨多个 discipline（例：壳体散热 = ME + EE）；验证是分家的（自测 / 供应商 FAT-SAT / 第三方实验室 / 客户现场）；接口两端必须各有 owner。

### 1.2 两套世界

SW/FW 已用 **OpenSpec**（capability / requirement，没有编号，也没有这套层名）；EE/ME/系统测试/供应商/实验室活在**文档世界**（Markdown / Excel / 邮件，没有工具）。两套世界之间需要一个稳定的锚，否则跨世界引用只能靠人记。

### 1.3 要补的文档链

`MRD → PRD → StRS → SyRS → IRS`（市场需求 → 产品需求 → 利益相关方需求 → 系统需求 → 接口需求），各有 owner：CMO（市场）、VP-Eng（工程）、SA（系统架构）、SQA（系统质量 / 验证）。

人审需要文档；**IRS 是候选检查点**——它是硬软那条缝，EE/ME/FW/SW/系统测试在同一张接口表上碰头，且天然是 OpenSpec `Traces:` 的落点。

本文用「**动议**」指一次交付（一个 deliverables 目录，如 `2026-11-06-portable-overload-detection`）。跨动议 = 跨一次交付。

### 1.4 为什么「编号」成了问题

用户把**第一消费者定为 Agent**，判据不是「人读得懂」，而是三条：

1. **Agent 不可能读错** → 同一语形只能有一个意思；
2. **没有判断题** → 「这里是定义吗」不能靠猜；
3. **机器能判红** → 缺件、悬空、重号要能自动报错。

这三条把「选个好看的缩写」换成了「设计一套可判定的语法」。本研究的结论就是这套语法。

## 2. 盘面：八次真实失败，没有一次是「词不认识」

| # | 失败 | 事实（可复核） | 性质 |
|---|---|---|---|
| 1 | 21 vs 23 | SA 稿写「21 条（IF-001~IF-021）」；SQA 稿在同一动议里写「补 2 条 IF：IF-022、IF-023」。评审把提案读成已定义，报「文档 23 条、声称 21 条」——两边其实都没写错 | 同形三义 |
| 2 | 两套词表 | pack 的 preset 说 `IF/VP`，workspace 的 kb 种子说 `STR/SYR/IFR`；Agent 换个 workspace 就换一套语法 | 词表未关门 |
| 3 | 自造编号 | v4 没有 PRD，SQA 自造 `VR-01~VR-15` 并注「临时编号，PRD 出具后回填」；PRD 一直没出，从未回填 | 缺件不红 |
| 4 | 撞角色名 | skill 明写 `VP-###`，SQA 实际写 `V-001~V-046`，同一张表里还有 `VP-Eng`——instruction 没救回来 | 先验冲突 |
| 5 | 收口空过 | 收口审计 10/10 PASS，而 `drafts/` 里根本没有 MRD/PRD | 检查未覆盖对象 |
| 6 | 断边 | lab 五层齐全：33 条 SyR 全部有 STR 追溯，**0 条**有 REQ 追溯；PRD 里 **0 个** STR 引用 | 追溯靠手写 |
| 7 | near-miss | `AC-008`（少一段）、`AC-001` 与 `AC-001-1` 混用 | 文法不封闭 |
| 8 | 计数无复算 | lab 的 SyR v2 声称「55 条 AC 逐组处置」，实际只列 35；v3 自己认账 | 计数不派生 |

> 复核路径与命令见 [evidence](research_topic/2026-11-07-evidence.md)。「性质」列是分类，不是事实。

**共同点**：八次里没有一次是「Agent 不认识 `IF` 这个词」。失败集中在三处：

- **同一语形承载三种语义**：定义 / 引用 / 建议新增（#1、#7）；
- **词表不唯一**：第二套语法同时活着（#2、#4）；
- **缺件与断边不判红**：空列没人填、空过没人发现（#3、#5、#6、#8）。

## 3. 思考

### 3.1 先把五根轴分开

编号天然可能承载五种信息。先问「每种信息该住哪」，再问「用哪些字母」。

| 轴 | 进 ID？ | 住哪 | 理由 |
|---|---|---|---|
| 种类（需求 / 接口 / 验证） | **进** | ID 本体 | 外部读者第一眼要判「这是接口还是需求」；这是 ID 唯一该承载的语义 |
| 层（MRD…IRS） | 不进 | 文档身份 + 文档头声明 | 层序本身未定；同一物跨层会起两个号；文档已经能承载 |
| 状态（草案 / 生效 / 作废） | 不进 | 条目状态位 | 状态会变，ID 不能变；否则「一件东西一个号」破 |
| 专业域（HW/ME/FW/SW） | 不进 | 附录 / 派工视图 | 已拍；一条需求跨两个 discipline，作前缀必出两个号 |
| 验证方 / 两端 owner | 不进 | 字段 | 验证分家；一个接口两端各一个 owner，号装不下 |

**推论**：ID = 身份（种类 + 序号）；其余全是属性，各有各的家。

### 3.2 为什么「换一组更清楚的前缀」修不了上面任何一条

- #1 双方都用最熟的 `IF`，还是读错——问题不在词。
- #4 `VP` 是熟词，但和 `VP-Eng` 撞车，instruction 没救回来——问题在上下文冲突。
- #2 只要允许第二套词表存在，选哪组字母都会重演——问题在关门。
- #3 / #5 / #6 / #8 与字母无关——问题在缺件判红与派生。

三份独立判断（Claude / GPT / DeepSeek；DeepSeek 明说没读另两份）在这一条上撞到同一个结论：**换前缀修不了其中任何一条**。分歧只剩「用哪组字母」和「提案怎么标」，后者已由用户裁定（§5-8）。

### 3.3 为什么追溯不能靠「后期聚集」

追溯图是**有向、有类型**的边（派生 / 验证 / 分配）；从正文聚集 ID 只能得到**提及图**（无向、无类型）。

- 证据：lab 里写了追溯字段的 33 条 SyR、22 条 IFR 全部自洽——**写了的地方就写了**；缺的是 PRD→SyR，因为没人负责写那条边。
- 更糟：真去聚集，StRS 里的 `AC-001-4` 会解析到**另一个动议**的 PRD——得到一条像真的错边，比空边更难发现。
- 所以：边由作者写（下游 `Traces:`），矩阵由索引派生，检查器判红。三者缺一，链就断。

### 3.4 为什么层不进号，但文档必须声明

「层归文档」是方向，但文档身份不是自动机器可读的：文件名可被改、被复制；而 lab 的追溯矩阵把 ID 放在表格首格——若「首格 = 定义」，矩阵会被误认成定义点。

所以文档头要声明两件事：**我是哪层**、**我的定义长什么样**（小节标题 / 表行 / JSON 账本）。机器只认声明后的形态。

### 3.5 为什么状态不能写成前缀

`TBD-` / `???` / `proposal:` 三种写法都会让状态变成标号语法的一部分：ID 随状态变形，状态一改就要重键；而且家族数真的会增加，违反「前缀别再加」。

状态属于条目：ID 恒为 `IF-022`，状态位写「草案」（即用户说的 **TBD**）。

**代价**：词法层再也分不出「定义」和「提案」。所以必须补一条硬规则——**每个号都要解到一行**：

- 解到定义行 → 该号存在（再看状态是草案还是生效）；
- 解不到 → 悬空 → 红。

悬空号判红因此从「可选项」变成承重规则。

### 3.6 被排除的方案族（范围与排除）

| 方案 | 不选的原因 |
|---|---|
| UUID / 纯数字 | 外部读者判不出类型，违反「第一眼」；贴不进 Excel / 邮件 / CAD |
| 层码（`SYS-REQ-001`） | 双号入口；把未定的层序固化进每个号；等于再加前缀族 |
| 文档码（`PRD-REQ-001`） | 文档改名 / 合层会传导到 ID；像文档号不像条目号 |
| 章节号（`1.1 / 2.3`） | 插入即重排，号不稳定 |
| 单独 NFR 前缀 | 增加家族；NFR 用 kind + 覆盖清单更合适 |
| OpenSpec capability 标题当 ID | 只覆盖 SW/FW，跨不到 EE/ME/供应商 |

## 4. 结论（推荐）

### 4.1 一句话

**ID 只承载身份：`<种类>-<序号>`；层归文档（并声明），状态归条目，专业域与验证方归字段；追溯由作者写边、索引派生、检查判红。**

### 4.2 规则

| # | 规则 | 形态 |
|---|---|---|
| R1 | **身份** | `<KIND>-<NNN>`，`KIND ∈ {MR, REQ, IF, TC}`；四种各自一条 append-only 序列，动议内全局唯一；号只在 owner 登记条目时分配（索引取 max+1），提案方不预先发号 |
| R2 | **从属** | `AC-<REQ号>-<n>`；父号必须是存在的 REQ |
| R3 | **层** | 不进 ID；一份文档一层；文档头声明「层」与「定义形态」 |
| R4 | **定义** | 只在声明的形态里成立（小节标题 / 表行 / JSON 账本）；正文出现 = 引用；一个号只能有一个定义点 |
| R5 | **状态** | 不进 ID；定义点上带状态（草案 / 生效 / 作废）。「建议新增」= 草案，ID 不变；作废留号，不复用 |
| R6 | **引用** | 本文档内裸 ID；跨动议 `<动议键>:<ID>`（键格式未定，§6-4） |
| R7 | **追溯** | 下游写 `Traces:`；矩阵由索引派生，不手写；缺上游、缺层 = 红 |
| R8 | **计数** | 由索引派生；作者不写死「N 条」；禁用「IF-001~IF-021 共 21 条」式区间断言 |
| R9 | **词表** | 唯一权威；`STR/SYR/IFR/VP/V/VR` 退役，出现即红；`NFR` 不作 token |
| R10 | **强制点** | host 命令 / 操作员 / 钩子；角色不能在会话里自查（硬约束） |

### 4.3 一份文档长什么样

```markdown
---
layer: SyRS
definition: 小节标题
---

### REQ-041 试点零新增固定资产
kind: NFR
status: 生效
owner: system-architecture
verifier: 第三方实验室
traces: [REQ-003]
```

```markdown
### IF-014 采样时钟接口
status: 草案                 ← 「建议新增」就是这个状态，ID 不因草案而变形
owners: [firmware, electronics]
traces: [REQ-041]

### TC-006 注入过载信号，测告警延迟
covers: [IF-014, REQ-041]
```

OpenSpec 侧只挂锚：`Traces: REQ-041, IF-014`。

**读法**：`### IF-014` 在声明了「小节标题」的文档里 = 定义点；正文里出现的 `IF-014` = 引用；`status: 草案` = 未生效，不计入「生效条数」；`layer: SyRS` = 这一层的身份。

### 4.4 每条规则消掉哪个失败（自洽性检查）

| 失败 | 被哪条规则消掉 |
|---|---|
| #1 21 vs 23 | R4（定义形态）+ R5（状态）+ R8（计数） |
| #2 两套词表 | R9 |
| #3 自造 VR | R7（缺上游红）+ R9 |
| #4 VP/V | R9（退役）+ R1（唯一序列） |
| #5 收口空过 | R7 + R10 |
| #6 断边 | R7 |
| #7 near-miss | R2（AC 文法）+ R4（定义 / 引用之别） |
| #8 计数 | R8 |

反过来看：**没有一条规则不指向某个失败**——不指向的规则就是加戏，先不加。

## 5. 与已拍约束的关系

| # | 约束（用户已拍） | 本结论如何满足 |
|---|---|---|
| 1 | 编号必须有 | R1 |
| 2 | 一件东西一个号 | 层 / 状态 / 专业域都不进号；跨层不换号；一个号两个定义点 = 红（R4） |
| 3 | 专业域不作前缀 | 只在附录 / 派工视图 |
| 4 | 前缀别再加 | 家族数不变：现 pack 是 `MR/REQ/AC/IF/VP` 5 族，结论是 `MR/REQ/AC/IF/TC` 5 族——`TC` **替换**撞角色名的 `VP`，不是新增 |
| 5 | 多层文档是前提 | 一份文档一层；层数 / 层序未定（§6-2） |
| 6 | SW/FW 已用 OpenSpec | ID 作跨世界锚；OpenSpec 内写 `Traces:` |
| 7 | ID 可单独读懂 / 验证分家 / 两端 owner | 种类进号；verifier、两端 owner 是字段 |
| 8 | TBD 属状态、不是前缀、不进 ID | R5；提案靠状态位，正文里不出现任何状态标记 |

> 1–7 来自前两轮（出处见 [current-brief §2](research_topic/2026-11-07-current-brief.md)）；8 是 2026-11-07 对话裁定。

## 6. 未定（参数级，不影响上面的结构）

| # | 未定 | 影响什么 | 倾向 |
|---|---|---|---|
| 1 | 状态位落在哪 | 散文里的提案怎么表达 | 表列 / 条目字段 / 文档头；散文里裸号解不到行就红 |
| 2 | 层数与层序 | 五层是否都必要、StRS/PRD 能否并 | 先不冻结——层不进号的好处就是可以晚定 |
| 3 | IRS 检查点 gate 什么 | 文档闸 / 评审闸 / 编号闸 / 追溯闸 | 据 §1.3 的四条候选证 |
| 4 | 跨动议键格式 | 供应商 / 实验室导出 | 动议键 vs 项目键；裸 ID 只在动议内有效 |
| 5 | NFR 防漏 | 漏项能不能被发现 | kind + 覆盖清单（每类 `n/a` 要理由） |
| 6 | 号分配并发 | 两个会话同时写会撞号 | 索引取 max+1；撞号 = 红；是否加锁另议 |
| 7 | 词表字母 | `MR/REQ/IF/TC` 是否第一眼就对 | **V1 盲测没跑**；只影响选词，不影响「种类轴」这个结构结论 |
| 8 | 范围 / 豁免 | demo / 决策类动议要不要编号 | 豁免必须显式声明并留痕，不能静默空过 |
| 9 | VP→TC 迁移面 | 落点与文案 | 2 份 skill（SA、SQA）里的 `VP-###` + 手册；角色名 `VP-Eng` 不动 |
