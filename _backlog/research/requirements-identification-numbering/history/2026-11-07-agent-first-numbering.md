## 0.5 五分钟版（给下一个 Agent 的 orientation）

**一句话问题**：在硬软一体、多 discipline（SW/FW/EE/ME/系统测试）的研发体系里，SW/FW 已用 OpenSpec，需求文档规范原本缺失；现在要补 MRD→PRD→StRS→SyRS→IRS 的文档链，需要给人 review 的文档（IRS 是候选检查点）；并要求一套需求识别/编号机制（前缀只是候选形态之一），让**人和 Agent 都能第一眼正确理解、跨文档/跨组织可解析**，且 **Agent 不困惑**。

**研究目标**：把决策空间整理到**可拍板**的程度——目的/约束/候选/证据；**本阶段不选**。完成判据 = 没参与讨论的人/Agent 能复述问题、复现候选、指出缺什么证据。

**已知**：

- 编号必须有；一件东西一个编号；discipline 不作前缀；前缀别再加（用户已拍）。
- 多 discipline、OpenSpec 内外两套世界、人的 review、IRS 检查点、验证分家、接口两端 owner（场景/硬约束）。
- 真实失败：定义/引用/建议新增不可区分（21 vs 23 误读）、两套规则并存、缺上游自造 `VR`、`VP` 与 `V` 混用、收口空过、lab 链缺 PRD→SyR 边。

**未知/待探索**：

- 编号到底服务哪几个目的（§4.A）还没排序。
- 编码轴、词表、定义语法、提案语法、层表示、追溯、NFR、强制点、注册分配、范围、跨动议、视图、迁移、治理（§4.B–§4.P）。
- 8 个方案族（§6.0 S1–S8）+ 8 个假说（H1–H8）；12 个场景用例（§4.Q U1–U12）；16 个验证（§9 V1–V16）。
- 用户未说但场景必然要回答的 14 项（§8.5）——先确认或标假设。

**现在不要做**：不要选前缀、不要写 RFC、不要改 pack。先按 §1.6 自检理解，再补空间，再生成多个候选方案族，最后用 §6.5 的评估维度把 trade-off 摆出来。

## 1. 本轮新增的前提（用户 2026-11-07）

1. **第一消费者是 Agent，不是人。** 判据 = Agent 不可能读错、没有判断题、机器能判红；"人读得懂"是第二位的。
2. **prefix 必须第一眼就对。** LLM 看到 prefix 应立刻、深度地理解其语义；不允许"看到一个陌生术语之后还要去揣测"。
3. **只在现状与约束空间内找答案。** 不新增前缀族、不加逐条必填字段、不发明新机制；能少不多。
4. **research 未完成前不动任何东西。** 只在 `_backlog/research/requirements-identification-numbering/` 里推敲。
5. **不要急着下结论。** 先把空间探索完；现在任何"倾向"都只是待验证假设。

> 这五条改变了前两轮的提问方式：前两轮问"编几套前缀"；本轮先问"Agent 看到这个 token 的第一反应是什么"，再问"编号到底要服务哪几个目的"。

## 1.5 场景与问题（用户 2026-11-07 口述 capture）

> 本节只 capture，不分析；分析散在 §4–§8。用户原话见 §1.5.6。

### 1.5.1 研发场景：硬软一体、多 discipline

- **不是纯软件开发**：软件（SW）、固件（FW）、电子（EE）、结构（ME）、系统测试等 discipline 在同一个产品里并存。
- 同一条需求可能跨多个 discipline（例：壳体散热 = ME + EE；采样时序 = FW + EE；系统测试横跨全部）。
- 已有硬约束（第一轮 §5）：discipline 不能作前缀（会逼出两个号），只能作附录/派工视图；验证是分家的（自测/供应商 FAT-SAT/第三方实验室/客户现场）；接口两端必须各有 owner。

### 1.5.2 现状：SW/FW 已用 OpenSpec，需求文档规范缺失

- 目前研发体系里，**software 和 firmware 已经使用 OpenSpec** 作为实践。
- 原来的研发体系里**没有很清晰的需求文档规范**（需求这一块）。
- 按用户口述，这套 MRD→PRD→StRS→SyRS→IRS 体系是在"补需求文档规范"这个空档上长出来的，不是替换一个已经成熟的规范；这个定位是否准确，需确认。
- 后果：新体系会同时面对两套世界——OpenSpec 内的 SW/FW（capability/requirement，无编号），OpenSpec 外的 EE/ME/系统测试/供应商/实验室（纯文档，无工具）。

### 1.5.3 拟走的文档链

- MRD → PRD → StRS → SyRS → IRS（用户口述；早期任务书里的顺序变体也有人跑过）。
- 每层的 owner、文档形态、编号、追溯仍未定；第一轮已拍"多层文档是前提"，但**层数本身**和**层与层是否可并**仍是开放问题（§8-2）。

### 1.5.4 人的文档：review 需要；IRS 是候选检查点

- **确实需要给人的文档**，因为 **review 需要**——不是所有东西都能只活在 OpenSpec/Agent 里。
- 用户感觉 **IRS（接口需求）是一个挺好的检查点**。
- 为什么可能是好检查点（待验证，不是结论）：
  - IRS 是硬软那条缝：EE/ME/FW/SW/系统测试在同一张接口表上碰头；
  - 每个接口两端都要有 owner，缺一端就没人负责；
  - 供应商、实验室、客户现场都看得懂"接口"这件事；
  - 它天然是 OpenSpec 的 `Traces:` 落点（SW/FW 侧引用上游 IF）。
- 但"检查点"具体指什么还没定：是文档闸门、评审闸门、编号闸门、还是追溯闸门？它 gate 住什么？（§8-18）
- 也可能不是好检查点：接口只是跨边界的一部分；检查点可能更适合放在需求基线/评审流程/测试就绪；IRS 可能太晚或太细。以上两边都待验证。

### 1.5.5 核心问题（用户最关心的）

- **最后在这个体系底下用什么前缀编号，人和 Agent 都容易。**
- **Agent 不能困惑**：今后落地的很多东西靠 Agent；术语/前缀一旦定下来，Agent 如果困惑就很麻烦。
- 这不是"选一个好看的缩写"，而是"选一个第一眼就能被模型正确解释、且机器能判定义的 token 集合"。
- 目前候选池、先验风险、方案族、验证计划见 §4–§9；**本节不选**。

### 3.1 反转：v5 的 "23 条接口" 是建议新增，不是已定义

- 若评审后文件被改过，则需重核；但 SQA 的 21/21 与 final 的 21 互相印证，当前盘面自洽。

### 3.5 收口检查会"空过"

**事实**

- 收口审计的 10 条判据只查接线与产物在场：CEO depth、VP-Eng 成员、SA/SQA 独立会话、final 存在且点名 SQA、SQA 稿含否决、SA 稿含 IF（[sa-sqa-closeout-audit.mjs](../../../../probes/team/sa-sqa-closeout-audit.mjs)）。
- 这套判据不要求 `mrd.md` / `prd.md`；v5 的 `drafts/` 只有 `ceo.md`、`sa-architecture.md`、`sqa-vv.md`、`vp-eng.md`，没有 MRD/PRD，收口仍可 10/10 PASS。
- `/prd check` 是**人命令**，只读固定路径 `{mrd,prd}.md`（[prd-command.ts](../../../../packages/company-pack/src/host/prd-command.ts)）；缺文件会报错，但没人跑它。

**这暴露的问题**

- "有检查"不等于"检查覆盖了对象"。检查器只看它看得见的东西；对象缺失时，它可能空过。
- 一个待探索的问题是：强制点是否应放在"有后果的时刻"（present/收口），以及缺件是否应判红，而不是"跳过/不适用"。

### 3.6 lab 五层：内部自洽，但 PRD→SyR 边缺失

- StRS 是后补的上游：它引用的是**前一个动议** PRD 的 AC（如 `AC-001-4`），而 PRD 不知道 StRS 存在。

**这暴露的问题**

- "五层链条第一次跑通"是超额声明：文档齐了，**PRD→SyR 这条边没闭合**。这提示"手写追溯矩阵"可能不可靠——空列没人填就没人发现（待验证）。
- 追溯矩阵：生成还是手写、粒度如何、谁审，是待探索项（见 §4-H、§6-H）。

### 3.7 跨动议裸 ID 与 near-miss

**事实**

- lab 的 StRS 里 `AC-001-4` 指另一个动议的 PRD（`runtime/lifecycle-lab/real-ws/.dsh-company/deliverables/2026-11-06-portable-overload-requirements/drafts/str.md:37`）。
- 同一份 StRS 里 `AC-008` 不是合法的 AC 号（合法形 = `AC-###-#`），却被当作"PRD 的 AC-008 组"使用（`str.md:67`、`:83`）。
- `syr.md` 里 `AC-001`（REQ 级引用）与 `AC-001-1`（AC 级）混用；`AC-001` 不匹配 `/prd check` 的 AC 文法。

**这暴露的问题**

- 裸 ID 不是跨动议自足的；"裸 ID = 本动议，跨动议 = 项目键 + ID"只是候选规则之一，不是已定规则。
- near-miss 形状（`AC-###` 少了第三段）是否必须判红，取决于最终文法；但它是现实存在的歧义源。

### 3.8 `/prd check` 的能力与边界（现有唯一机械检查器）

**它已经做的**（[prd-check.ts](../../../../packages/company-pack/src/lib/prd-check.ts)）：

- `MR-###` / `REQ-###` / `AC-###-#` 文法与重号；
- REQ 的 `source` 指向存在的 MR；no-go 不得进 PRD；defer 不得进 P0；
- slice 存在且列出该 REQ；`dependsOn` 存在且无环；
- AC 的父号与 REQ 号一致；状态机与 changeLog；每条 REQ 至少一条 AC。

**它没做的**：

- 跨层需求文档（StRS/SyRS/IRS）不在扫描面；
- NFR/约束覆盖、count 声称、提案 token、near-miss、正文 vs JSON 一致性、跨动议；
- 不做文件存在性以外的"层完整性"判断；
- 没有任何自动触发点（人命令）。

**这暴露的问题**

- 它的形状（纯逻辑、keyless 可测、命令 + 测试）是候选先例；但它的**覆盖面与触发点**是否够，是待探索项。

### 4.A 编号的目的（先定目的，才谈形式）

| 目的 | 它对 ID 的要求 | 与其它目的的张力 |
|---|---|---|
| 跨文档引用 | 稳定、唯一、可解析 | 与"类型一眼可见"可兼容，但与"短"冲突 |

| 任务键 | 一 REQ 一任务；标题/依赖可挂 | 与"层/种类"编码可能冲突 |
| 审计/举证键 | 不可变、不复用、可追到签名记录 | 与"重编号/迁移"冲突 |

## 6. 候选假说（并列，不排名）

### 6.0 先看方案族，再看单个 token

> 下面是"族"级别的候选，每族可以再选具体 token；不是排名，不是推荐。H1–H6 对应 S1–S6；H7（上游不编号）与 H8（UUID）是另外两族。

| 族 | 一句话 | 代表 | 可能的好处 | 可能的代价 |
|---|---|---|---|---|
| S1 种类编码 | ID 只说"是需求/接口/验证" | REQ/IF/TC | 先验强、决策少、前缀不随层增长 | 层不可见；需求可能全局分配 |
| S2 层编码 | ID 说"哪一层" | STR/SYR/IFR | 层一眼可见；分配简单 | 先验弱/错；双号诱惑 |
| S3 种类+层 | 两者都编 | SYS-REQ-001 | 层+种类都可见 | 更长；两个判断 |
| S4 文档限定 | ID 带文档码 | PRD-REQ-001 | 定义点明确；无全局分配 | 像文档号；改名成本 |
| S5 层级数字 | 用大纲号 | 1.1/2.3 | 无 token 先验问题；短 | 插入重排；种类不可见 |
| S6 全局序号+字段 | 不透明序号+type 字段 | R-0001 | 分配简单；不复用 | 外部不可读；类型靠字段 |
| S7 双轨 | 人读文档用层名，Agent 用种类号 | 文档标题+REQ/IF/TC | 人机各取所需 | 双真相/映射成本 |
| S8 OpenSpec 中心 | OpenSpec 为主，外部 ID 只做 trace | capability+Traces | 贴合 SW/FW 现状 | EE/ME/供应商没有 OpenSpec |

> 每个假说列"可能的好处/可能的代价/可能推翻它的证据"。没有任何一个被选中。

### H1 只编种类：`REQ / IF / TC`（+ `AC` / `MR` 从属）

- **可能的好处**：token 先验强；每个条目只问"是需求/接口/验证"；层由文档承载；前缀不随层增长。
- **可能的代价**：层不可见；需求可能全局分配；AC 父号耦合；跨动议要项目键。
- **可能推翻它的证据**：V2 重键后追溯不可读；V7 显示全局分配/迁移成本过高；V1 显示 `REQ` 跨层被误读。

### H2 只编层：`STR / SYR / IFR`（+ `REQ/AC` 上游）

- **可能的好处**：层一眼可见；分配简单（每层自己序列）；跨层撞号低。
- **可能的代价**：token 先验弱/错（string/航空）；同一需求两层会起两号；与用户"前缀别加"张力。
- **可能推翻它的证据**：V1 盲测第一反应错误；V4 样本出现同一需求两个号。

### H3 种类+层：如 `SYS-REQ-001`

- **可能的好处**：种类与层都可见；定义点按层明确。
- **可能的代价**：较长；两个判断；表格/Excel 宽度；与"前缀别加"冲突。
- **可能推翻它的证据**：V4 外部文档可读性差；V2 显示写作成本高。

### H4 文档限定：`PRD-REQ-001` / `SyRS-REQ-001`

- **可能的好处**：定义点在 ID 里；无全局分配；跨文档引用明确。
- **可能的代价**：像文档号；文档改名/迁移；长度；AC 子号更长。
- **可能推翻它的证据**：V4 外部读者把 `PRD-001` 当文档号；V7 文档改名成本。

### H5 层级数字：`1.1 / 2.3`（Kiro 式）

- **可能的好处**：无 token 先验问题；自然大纲；短。
- **可能的代价**：插入会重排；种类不可见；跨文档要文档名；AC/TC 怎么编未定。
- **可能推翻它的证据**：V2 编辑样本时出现重排/断引用。

### H6 全局序号+类型字段：`R-0001` + `kind`

- **可能的好处**：分配成本较低；无前缀先验；永不复用。
- **可能的代价**：外部不可读；种类只在字段；供应商 Excel 里无法一眼判。
- **可能推翻它的证据**：V4 外部场景无法解析；V1 第一反应"这是什么"。

### H7 上游不编号，只用文档+章节

- **可能的好处**：空间更少；上游文档保持"文档"。
- **可能的代价**：章节号不稳；上游追溯粒度粗；用户"编号必须有"可能覆盖它。
- **可能推翻它的证据**：V4 上游引用在改章节后断掉；用户否掉。

### H8 不透明 ID + 注册表（UUID/哈希）

- **可能的好处**：零撞号；永不复用；机器友好。
- **可能的代价**：人/外部不可读；与"ID 贴进 Excel/CAD"直接冲突。
- **可能推翻它的证据**：V4 外部可读性；用户约束 1。

## 7. 已知硬约束/边界（不选方案；只记录与哪些选项有张力）

1. **AC 父号耦合**：若保留 `AC-<REQ数字>-<n>`，REQ 号必须动议内唯一且稳定；这会与"每文档从 001 开始"的做法产生张力，除非 AC 解耦。
2. **外部可读**：ID 要能贴进供应商 Excel、邮件、CAD 注释、试验报告；纯 UUID/哈希/纯链接不满足。
3. **验证分家**：每条需求/接口要能带 `verifier`（自测/供应商 FAT-SAT/第三方/客户），否则"都以为对方验了"。
4. **接口两端 owner**：每条 IF 两端都要有 owner，缺一端即无人负责。
5. **专业域只能附录**：HW/ME/FW/SW 不作前缀；这是用户已拍。
6. **角色不能在会话里跑脚本**：强制机制只能放 host/操作员/钩子，不能靠"SQA 自己跑一下"。
7. **手册预算**：`content/AGENTS.md` 现 18.8KB / 32KB；常驻契约有空间，但不是无限。
8. **`/prd check` 先例**：固定路径 `{mrd,prd}.md`、人命令、只读 JSON；它是形状先例，不是覆盖先例。
9. **两套规则同时活着**：pack 的 `IF/VP` 与 workspace 的 `STR/SYR/IFR`；"旧规则怎么共存/退出"是任何新方案都要处理的问题。
10. **OpenSpec 不含我们的 ID**：`openspec validate` 不校验；若要有检查器覆盖两套世界，它需要同时读 OpenSpec 树和非 OpenSpec 文档。
11. **present 不可由 pack 否决**（当前）：pack 只观察 presented；要真门禁，需 DSH 钩子或包装；这是可行性未知项。
12. **研究边界**：现在不实现、不迁移、不改盘面；所有选项都只是纸面。
