# 需求编号：Claude 的推荐（给人看的版本）

> 作者：claude。状态：**推荐 + 待验证假设**，不是决定。下面的倾向在 V1 盲测、V4 负例跑完之前都可以推翻。
> 依据：本目录的 evidence（盘面事实与路径）、candidates（假说 H1–H8）、validation（V1–V16，目前都还没跑）。
> 下文的 `REQ-001`、`IF-001`、`TBD-IF-022` 等例子是为了说明规则而编的，不是项目里的真实条目。

## 一、这件事在解决什么

项目里有好几层需求文档。从上往下是：

```
MRD（市场需求）→ PRD（产品需求）→ StRS（利益相关方需求）→ SyRS（系统需求）→ IRS（接口需求）
```

每层都要给条目编号。问题是，**编号本身读不出三件事**：

1. 这个 ID 是**定义**的，还是只是**引用**别人的？
2. 这个 ID 是**已经存在**的，还是只是**建议新增**的？
3. 它属于**哪一层**？

只要读不出来，人和 Agent 就会误读。下一节的三个事故都来自本机真实盘面（路径见 evidence 文件）。

## 二、三个真实事故

### 事故 1：21 条还是 23 条

v5 的系统架构文档（SA）写"接口 21 条，IF-001 到 IF-021"。同一动议的 SQA（系统质量）稿里有一句"补 2 条 IF：IF-022、IF-023"。

评审读到 `IF-022` 时，把它当成"已定义"，于是报"文档有 23 条，声称 21 条，不一致"。

实际上两边都没写错。SA 的 21 条是对的，SQA 的"建议补"也是对的。问题在于 `IF-022` 这种写法，**定义和建议长得一模一样**。编号唯一挡不住这种误读。

### 事故 2：Agent 自己编了一套编号

v4 的 SQA 稿在没有 PRD 时，自己编了 `VR-01` 到 `VR-15`，并且注明"临时编号，PRD 出来后回填"。PRD 一直没出来，这套临时编号从未回填，变成了事实上的正式编号。

缺上游时，Agent 不会空着，它会造一个看起来合法的编号空间。

### 事故 3：收口检查空过

收口审计有 10 条判据，全部 PASS。但它只检查"文件在不在、接线对不对"，没有要求 MRD 和 PRD 存在。v5 目录里没有 `mrd.md` 和 `prd.md`，收口仍然通过。

检查器只能看见它被设计去看的东西。对象缺失时，它可能直接空过。

## 三、推荐方案 A（我的倾向）

### 3.1 规则一句话版

| 规则 | 做法 | 例子 |
|---|---|---|
| ID 只编**种类** | `REQ`（需求）、`IF`（接口）、`TC`（测试用例）；`AC`（验收条件）、`MR`（市场需求）从属父条目 | `REQ-001`、`IF-001`、`TC-001` |
| **层**归文档 | 一份文档只属于一层，层不写进 ID | `syrs.md` 里的 `REQ-001` 就是 SyRS 层 |
| 定义点用**标题行** | 定义条目时把 ID 放进标题，机器可直接抓取 | `### REQ-001 告警需在 200 ms 内输出` |
| 引用用**裸 ID** | 本文档内直接写 ID；跨文档加项目键限定 | 本文档 `REQ-001`；跨文档 `PRD:REQ-001` |
| 建议新增用**保留标记** | 未定义、只是提议的，前缀 `TBD-`，机器一眼可辨 | `TBD-IF-022`（待 SA 确认） |
| 缺层**判红** | 应有层文档缺失时直接报红，不许写"不适用"跳过 | 缺 `mrd.md` → 红 |

### 3.2 一份文档长什么样

下面是假想的 SyRS 片段，用来看人读起来是什么感觉：

```markdown
# SyRS：过载检测系统需求（层 = SyRS，文件 = syrs.md）

### REQ-001 过载检测需在 200 ms 内输出告警
- 上游：MR-002
- 验收条件：AC-001-1、AC-001-2
- owner：SA

### REQ-002 告警需同时写入日志
- 上游：MR-002
- 验收条件：AC-002-1
- owner：SA

### IF-001 检测模块 → 告警模块
- 两端 owner：SW-检测、SW-告警
- 验证：TC-001

### TBD-IF-022 温度回读接口（建议新增，未定义）
- 来源：SQA 评审建议
- 状态：待 SA 确认；确认前不计入接口总数

### TC-001 注入过载信号，测告警延迟
- 覆盖：IF-001、REQ-001
```

**读法**：出现 `### REQ-001` 这种标题行 = 定义；正文里出现 `REQ-001` = 引用；`TBD-` 开头 = 提议，不计入已定义总数；文件名 `syrs.md` = 这一层是 SyRS。

### 3.3 这套规则怎么消掉三个事故

| 事故 | 方案 A 下会怎样 |
|---|---|
| 21 vs 23 | SQA 那句改成 `TBD-IF-022`，检查器数"已定义"时自动排除，21 = 21，不再误报 |
| 自造 `VR-01…` | 没有上游文档时检查器报红"缺 PRD"，Agent 不能靠自造编号绕过 |
| 收口空过 | 收口检查加上"MRD/PRD/StRS/SyRS/IRS 应存在"，缺一个就红 |

## 四、备选方案 B（有条件启用）

**方案 B**：ID 带层，例如 `SYS-REQ-001`（系统层需求）。

- **启用条件**：V1 盲测显示 Agent 看到裸 `REQ-001` 会跨层误认（比如把 PRD 的 REQ 当成 SyRS 的 REQ）。
- **代价**：ID 更长、表格更宽、多一个判断维度；而且和"前缀别再加"的约束有张力，**需要你明确放行**。

V1 没跑之前，我不建议先上 B。

## 五、为什么不选 H2（只编层：`STR / SYR / IFR`）

1. **先验弱**：`STR` 容易被读成 `string`，`IFR` 也没有明显含义。
2. **双号诱惑**：同一需求在 StRS 是 `STR-005`，在 SyRS 拆成 `SYR-012`，两个号指同一件事，容易混。
3. **和 lab 旧产物冲突**：`runtime/lifecycle-lab` 已有一整套 `STR/SYR/IFR` 产物，换规则要连旧产物一起迁移。

## 六、和你已拍约束的对照

| 约束 | 方案 A | 说明 |
|---|---|---|
| 编号必须有 | 满足 | 每个条目都有 ID |
| 一件东西一个编号 | 满足 | 层不进 ID，同一需求不会有两个号 |
| 专业域（HW/ME/FW/SW）不作前缀 | 满足 | 专业域放附录 |
| 前缀别再加 | 满足 | 只用 `REQ/IF/TC`，都是现有 token |
| 多层文档是前提 | 满足 | 每层一份文档 |

**一处需要你确认**：`TBD-` 是否算"新前缀"。我的理解它是状态标记、不是种类，所以不算违规；若你认为它也算前缀，就改用文档内的状态列表达。

## 八、需要你确认的三件事

1. **是否认可方案 A 的大方向**：ID 只编种类、层归文档、建议用 `TBD-` 标记。
2. **`TBD-` 算不算前缀**：影响"前缀别再加"怎么解释。
3. **缺层是否判红**：这会让现在没有 MRD/PRD 的动议收口直接变红，你是否接受。

另外，`2026-11-07-current-brief.md` §8.5 的 14 条"未说清"假设仍需你逐条确认或标记为假设。
