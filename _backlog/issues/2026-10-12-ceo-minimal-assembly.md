# 推敲：单域动议的最小在屋组队判断（CEO 不全员铺开）

> 立卡：2026-10-12 ｜ 状态：推敲中 ｜ 类型：Feature ｜ 毕业：未定 ｜ 可关闭：否

**问题与期望结果：** 用户 2026-10-12 在 `ai-coding-security-2026` 跑完后的现场裁定（原话）：
「这一启动，其实说白了应该就是 engineering VP 处理就行了，他为什么一定要把所有人都抓起来呢？
这个判断力他得有啊」「你不能什么事儿到都让底下人都要掺和一脚，这个就有问题了」。
期望结果：**单域动议**（安全/技术/合规诊断这类"一个域就能回答"的问题）CEO 默认**最小在屋起步**——
单 owner（如 VP-Eng）处理，其余职能不进屋；扩容靠**证据触发**（核心 owner 的稿显示真需要该域再叫）；
「一步全员」只在用户显式点名时走。该判断力要写进 CEO 的组队技能（显性化、可验收），
且要配一条**能红的验收手段**——没有红通道的判断条款管不住执行（本卡的直接教训，见当前情况③）。

**当前情况：**
1. **负例（live 真跑）**：`deliverables/2026-10-12-ai-coding-security-2026/`（AI coding 安全诊断）——
   任务书「在屋四职」+ 8 条派活行 + 3 条互审链。⚠ 事实更正（2026-10-12 晚）：立卡时快照为
   「仅 coo/vp-sales 出稿、核心 T1/T2 未落地」，此后运行未停——四职稿与两份互审稿已陆续出稿
   （vp-eng/cfo/cfo-review/coo-review 在盘；CFO 取证文件落 sources/），final 未出、meta 未闭。
   负例核心**不是动议停摆，而是组队判断本身**：单域安全诊断默认全员 + 外围与核心同步开工
   （T5 依赖：无），人事成本与陪跑在动议成立时就已发生。
2. **技能文本已有「少叫」条款但被合法绕开**：`presets/ceo/skills/assembling-the-team/SKILL.md`
   已写「列不出对应问题的职能不进」「拿不准时少叫」「纯为全面/稳妥陪跑的职能一律不叫」——
   现场仍四职入屋。绕开路径有二：a) 用户在选项里选了含多域的范围（范围 C 含交付面敞口盘点）；
   b) **验收字段设计**（每条控制带 owner/成本/落地日）在写任务书时就把 CFO/COO 结构化预订进屋。
   → 条款强度不够，缺一条**结构性硬测试**（在屋数 ≤ 问题域数、字段≠入屋理由、最小起步+扩容触发）。
3. **探针未复现红**：`probes/session-context/ceo-assembly-probe.mjs`（本轮新建的诊断器具）
   两轮形状（轮 1 裸问法给思路 / 轮 2 三项裁定+开工写任务书）在排练场对**旧 skill** 各跑一场，
   均 **0 spawn_teammate、0 subagent、路由 VP-Eng**——红未复现。红证据 = 上述 live 负例本身；
   失败形状依赖真人多轮范围裁定交互（证据 JSON 在 runtime/harness-home/probe-evidence/，gitignored）。

**未决问题：**
- **修复落点**：三候选——① assembling-the-team 加结构性硬条款（最小在屋起步/扩容触发/字段≠入屋理由/

## 方案与取舍

- **候选 ①（倾向）**：assembling-the-team 第 2 步加结构性硬测试。利 = 组队判断的单一 owner 面、
  与既有「少叫」条款同处；弊 = skill 文本已经有一次「少叫」没拦住，纯加字可能再次被绕开
  → 硬条款必须带**结构测试**（在屋数、字段归属）而非又一句态度话。
- **候选 ②**：persona 加一句第一响应原则。利 = 常驻注入、每动议必见；弊 = persona 管身份不管方法
  （role-content-plan §0 分工），方法进 persona 违背既有分工。
- **候选 ③**：手册加条。利 = 角色侧也能看见；弊 = 组队是 CEO 职权，写进全员手册等于让全员监督 CEO，
  分层不对。倾向 = ①（±③ 的一句路由提示），②不采。
