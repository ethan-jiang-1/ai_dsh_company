# 复盘：为什么 0.5.0 会坐歪

> 服务卡：[插件即产品 v3](../../settled_issues/2026-11-01-plugin-as-product-v3.md)。
> 性质：失败复盘，不是追责；目的是把「上次为什么会这样」变成「这次怎么不再这样」。
> 证据：当前代码/文档（C）、上一轮研究/卡（C）、FAQ 26 最新文本（C）、前轮真跑过的探针/冒烟（T，引用既往记录）。

## 0. 一句话

**不是某个文件写错了，是决策顺序反了：先用实现约束定产品形状，再用测试证明这个形状能跑，最后用文档把它写成合同。**

具体说：为了让「启动时问 workspace / 首启 seed / 一次安装」在当时的实现能力内跑起来，先造了 launcher，再把 registrar 放进 profile patch，再为了账本不串而限制一 home 一 workspace，最后为了手册能注入而复制骨架。每一步都在解决上一步的副作用，复杂度越长越像「产品深度」，但产品单位、入口、workspace 语义和内容边界从一开始就错了。

## 1. 用户要的 vs 0.5.0 给的

| 用户原话 | 0.5.0 实际 | 偏差性质 |
|---|---|---|
| 插件有独立启动 profile，启动后可在用户项目/指定 workspace 做事 | 产品入口是 bin/dsh-company（历史，已删除） / `pnpm company`；`company` profile 只是被 launcher 建出来的 | **入口单位错**：把 launcher 当产品 |
| 启动时知道 workspace，或启动过程中问 | launcher TTY 问 / `--workspace`；Host 没有启动器就只告警停写 | **询问位置错**：在终端、在 boot 前、阻塞式 |
| 插件内容全部在插件内部 | pack 的 `workspace/` 骨架被复制到用户 workspace | **内容边界错**：只读产品内容变成 run bundle 副本 |
| 生产状态/最终 artifacts（run bundle）在用户 workspace | 部分对了（v2 身份/业务产物在 workspace），但 home 仍绑定一个 workspace；换项目要新 home | **workspace 绑定错**：装一次不能指向多个项目 |
| 插件能力施加到用户指定 workspace | 应用内 Plugins 页装包不会跑 launcher；默认安装路径上 registrar/seed 不发生 | **默认路径错**：测试只证了侧门 |
| README、`_dist`、整个 repo 都要调整 | 文档确实改了，但改成了 launcher/一 home 一 workspace/骨架 copy 的合同 | **文档方向错**：描述了 workaround，不是用户要的产品 |

## 2. 症状 → 直接原因 → 根因

| 症状 | 直接原因 | 根因 |
|---|---|---|
| package bin / 第二层 launcher | 想要「启动前问 workspace / 建 profile / 装包 / seed 确认」，这些在 DSH 里没有现成 launcher 位置；就自己造了一个 | 把「启动体验」当成进程外编排，而不是 bundle 内 host/client 的职责；没有先问「DSH 支持的入口是什么」 |
| profile patch registrar | 应用内安装没有 launcher 写 profile patch；为了让 registrar 在 launcher 路径生效，把它放 profile patch | 产品行为没有随 bundle 交付；用「本机 profile 状态」补「bundle 缺行」，正好撞上 FAQ 17 的 home 不能供货 |
| 一 home 一 workspace | presented 账本单表按相对路径存，多个 workspace 会撞；为了不撞，禁止第二个 workspace | 用缩小产品范围来回避数据建模问题；没有先做账本分区 |
| 骨架 copy | `agent-instructions` 只认同目录文件名，不能指 pack 路径；为了让手册注入，复制到 workspace | 用复制绕开注入机制；复制后又长出 consent、哈希升级、v2 manifest、rebind 等一串补丁 |
| 默认安装路径没验证 | `company-entry-smoke` 测 launcher；`release-smoke` 预置 profile patch + seed-consent | 证据只验证自己造的那条路；没有把「Plugins 页装 + 直接 dsh --profile」当第一验收路径 |
| 文档写成 workaround 合同 | 文档在代码之后写，按「现在能跑什么」描述 | 没有把 README/手册当**设计约束和验收**；没有在写代码前先写「用户会怎么装、怎么起、数据在哪」 |
| 复杂度越来越高 | 每个 workaround 都需要新机制来兜底（consent、rebind、doctor、manifest 升级、一 workspace 约束） | 没有「workaround 登记 + 退出计划」；把补丁的复杂度误当成产品成熟度 |

## 3. 五层根因

### 3.1 决策顺序：实现先行，合同后置

上一轮先看「现有代码能怎么改」，再定产品形状；正确顺序是先定**产品合同**：

```text
产品单位（bundle / profile / launcher？）
安装（谁装、装到哪、默认路径？）
启动（谁启动、workspace 从哪来？）
内容（什么是插件内容，什么是 run bundle？）
数据（身份/治理/账本归谁？）
→ 然后才是代码、测试、文档
```

0.5.0 把顺序倒过来：先有 launcher，再定义「产品入口」；先有骨架 copy，再定义「run bundle」；先有一 home 一 workspace，再定义「一次安装」。产品合同成了实现的副产品。

### 3.2 产品单位：把 repo/dev harness 当成了产品

本仓的 dev 形状是 `pnpm company --workspace company-workspace`、`packages/company-pack/content/AGENTS.md` 符号链接、`runtime/harness-home`。这些是维护者便利，不是用户产品。0.5.0 把它们产品化：

- `pnpm company` → bin/dsh-company（历史，已删除）；
- `packages/company-pack/content/AGENTS.md` 符号链接 → 安装形态的骨架 copy；
- dev home → 产品 home + 一 home 一 workspace。

**教训**：dev harness 只能服务开发；产品形状必须从「收件人拿到 tarball 后怎么装、怎么起」倒推。任何 dev 便利进入 `_dist` 前都要重新论证。

### 3.3 平台约定：没有先尊重 DSH 的生命周期

DSH 的约定很清楚：named profile 是唯一受支持的 Node 启动；bundle 是安装/组合单位；应用内 Plugins 页是默认跨面安装；启动体验在 bundle 的 host/client 层；首启是 token 门，产品自己回答首屏。0.5.0 把其中四项都绕开了：

- 自建 launcher（绕过 named profile）；
- 自写 profile patch（绕过 bundle 自带行）；
- TTY 问 workspace（绕过 client 首启）；
- 一 home 一 workspace（绕过 DSH workspace 的多目录能力）。

这不是「机制不可用」，是「没有按约定用」。FAQ 37 的生命周期四阶段本来是验收骨架，上一轮只把它当参考资料。

### 3.4 证据：测试证明的是 workaround，不是用户路径

这是最危险的一层。上一轮的绿是「launcher 路径绿」：

- `company-entry-smoke` 调 `pnpm company`；
- `release-smoke` 预置 `company-workspace-register` profile patch 和 `.seed-consent`；
- `handbook-smoke` 读 workspace 里的 `AGENTS.md` 副本。

这些测试都通过，但它们验证的是我们自己造的那条路。**默认路径（Plugins 页装 + 直接 `dsh --profile`）没有被第一验收**。当测试只覆盖实现选择时，绿会制造虚假信心。

**教训**：第一验收必须走收件人的默认路径；侧门测试只能作为补充。每条「绿」要写清它证明了哪条路径，不能把「launcher 能跑」写成「产品能装」。

### 3.5 治理：把「按推荐」当成了产品语义的确认

上一轮的 Q1–Q7 是 agent 写的推荐，用户授权「按你的推荐推进、静默自主执行」。这在执行上没问题，但**产品语义的硬选择不能用「按推荐」代替用户确认**：

- 一安装一 workspace vs 多 workspace；
- 专用公司盘 vs 任意项目；
- 手册 copy vs 注入；
- 启动器 vs named profile。

这些不是实现细节，是产品承诺。上一轮把它们写进「裁决」表，等于把 agent 的偏好升格成用户决定；用户现在说「坐歪了」，本质是这些承诺没有被显式 review。

**教训**：自主执行适用于「已确认合同内的实现」；产品单位/入口/数据边界这类硬选择，必须显式列出选项、推荐、代价，等用户点头。授权「按推荐」只覆盖执行方式，不覆盖产品语义。

### 3.6 复杂度：用补丁掩盖边界错误

骨架 copy 之后，必须解决：

- 已有 `AGENTS.md` 怎么办（碰撞 seed `COMPANY.md`）；
- 升级怎么判定用户改没改（哈希/manifest v2）；
- 新 workspace 什么时候 seed（consent）；
- 换 workspace 怎么处理旧身份（rebind）；
- 一 home 多盘怎么不串（禁止第二盘）。

这些机制本身都做得不差，但它们全是在维护一个错误边界。**复杂度不是深度；如果边界错了，越精致越难改。**

## 4. 本可避免的路径（counterfactual）

如果上一轮按下面顺序做，会早发现歪：

1. **先写一页产品合同**：单位、安装、启动、workspace、内容/run bundle、数据 owner；让用户确认硬选择。写不出来 = 还没想清。
2. **先跑默认路径**：干净 home → Plugins 页/CLI 装 → 直接 `dsh --profile company` → workspace。没有 launcher 也要能跑；跑不通就停下来问，不造第二入口。
3. **先证注入，再决定 copy**：handbook 能否用 `systemPrompt.section`？templates 能否用 pack 路径/变量？能就不 copy；不能就把限制写清楚再问。
4. **先证账本分区，再决定 workspace 范围**：per-workspace ledger 是数据建模问题，不是禁止第二盘的理由。
5. **先写 README/手册草稿当验收**：如果安装说明必须写 node_modules/.bin/dsh-company --workspace（历史，已删除），说明产品入口已经错了；如果手册要教「换项目新建 home」，说明 workspace 语义错了。
6. **红队 review**：拿用户原话和 DSH architecture/FAQ 37 逐条对照，问「这条如果错了，最可能错在哪」；上一轮的 review 只查了内部一致性，没查产品/平台保真。

## 5. 本轮的过程守卫

| 守卫 | 具体做法 | 失败信号 |
|---|---|---|
| **合同先行** | P0 先出一页产品合同；D1–D6 显式列选项/推荐/代价；用户确认后才写代码 | 合同里还有「先这样，以后再说」的关键项 |
| **默认路径第一** | 每个能力先在「Plugins 页/CLI 装 + 直接 `dsh --profile`」路径跑；launcher/dev wrapper 只作补充 | 测试必须先起 launcher 才能绿 |
| **无第二入口** | package 无 bin；不新增 profile 写者；startup 行在 bundle patch | 需要写 profile patch 才能工作 |
| **内容不 copy** | 手册/模板只读内容住 `content/`；用注入/变量/override；run bundle 只放状态/产物 | 新 workspace 出现 `AGENTS.md`/`templates/` 副本 |
| **账本先分区** | 多 workspace 前先做 ledger v2；不允许用「一 workspace」回避 | 第二个 workspace 的 present 会改第一个的账本 |
| **文档即验收** | README/手册草稿在 P0/P1 先写；P5 定稿；docs 同 diff | 手册教 launcher/`--workspace`/新 home |
| **workaround 登记** | 任何临时绕行必须写「为什么、何时删、谁负责」；不能进 `_dist` 合同 | 绕行变成永久「产品特性」 |
| **红队 review** | P0 和 P5 各一次；按用户原话 + DSH 37 逐条问「哪条会证伪」 | review 只查代码风格/内部一致 |

## 6. 这次要特别盯住的「容易再歪」点

1. **又想造薄 launcher**：FAQ 40 允许「薄 bootstrap」，但产品默认安装是 Plugins 页；本产品不需要。dev wrapper 只能叫 dev，不能进 tarball、不能写 profile。
2. **又想靠 profile patch 补 startup**：应用内装不会写 profile patch；startup 必须在 bundle。client tier 冲突用 host-only 包/主 apply 解，不用 profile patch。
3. **又想 copy 模板**：模板/手册是只读产品内容；用 pack 路径/变量/override。章程/org/company 是状态，可以 seed，但要分类清楚。
4. **又想用「一 workspace」回避账本**：先做 per-workspace 账本；并发多 workspace 可以后置，顺序多 workspace 不能后置。
5. **又只测侧门**：release-smoke 必须从「干净 home + tarball + 无 launcher + 无 profile patch」开始；如果测试需要预置，就说明产品还不自包含。
6. **又让文档追代码**：README/手册先写；写完发现要 launcher/新 home，就回头改设计，不是改文档措辞。

## 7. 一句话教训

- **先定产品合同，再定实现；先跑默认路径，再谈体验；先证边界，再写补丁；先让用户 review 硬选择，再自主执行。**
- **DSH 的约定不是限制，是产品的地基；绕开它省下的每一步，后面都要用更多补丁还。**
- **测试如果只证明你造的那条路，它证明的是你的实现，不是用户的产品。**
