### 1.3 它是什么（README + SPEC 逐字原句）

来源：`https://raw.githubusercontent.com/GoogleCloudPlatform/open-knowledge-format/main/README.md` 与 `.../main/SPEC.md`（全文已读，获取 2026-11-12）。

**定位（SPEC 开头，L5-13）**：

> OKF is an open, human- and agent-friendly format for representing *knowledge*: the metadata, context, and curated insight that surrounds data and systems. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both.
>
> The format is intentionally minimal: a directory of markdown files with YAML frontmatter. There is no schema registry, no central authority, and no required tooling. If you can `cat` a file, you can read OKF; if you can `git clone` a repo, you can ship it.

**vendor-neutral（README）**：

> OKF is a **universal, vendor-neutral format** for representing knowledge as plain markdown files with YAML frontmatter. It is **not tied to any particular agent, framework, model provider, or serving system**.
>
> - **Anyone can produce** OKF — humans authoring by hand, agents built on any framework (Google ADK, LangChain, custom), export pipelines from existing catalogs (Dataplex, Unity Catalog, Collibra, …), or scripts walking a database.
> - **Anyone can serve and consume** OKF — a static file server, a knowledge-management UI (Obsidian, Notion, MkDocs), an LLM loading files into context, a search index, or a graph viewer like the one bundled in this repo.

**动机 = agent 持续维护的知识语料（SPEC §1）**：

> Increasingly, a knowledge corpus is not authored once and then read: it is **continuously written and maintained by agents**. When most concepts are machine-generated, a consumer needs answers that a plain markdown-plus-frontmatter convention does not make first-class:
>
> 1. What was this created from, and how was it verified? (**provenance**)
> 2. How much should I trust it? (**trust**)
> 3. Is it still true? (**freshness**)
> 4. Is it the current version? (**lifecycle**)
> 5. Was this number produced the way we said it must be? (**attestation**)

**Non-goals（SPEC §1）**：不定义固定概念类型分类法；不规定存储/服务/查询基础设施；不替代领域 schema（Avro/Protobuf/OpenAPI——"OKF *references* them; it does not subsume them"）；不规定执行器打包标准（"OKF fixes the interface, not the packaging"）。

### 1.4 它标准化什么（结构逐条，SPEC 一手）

1. **Bundle = 目录树**（§3）：markdown 文件树，目录组织由 producer 自定；分发单位 = git repo（推荐）/ tarball / 大仓内子目录。**保留文件名**（§3.1）：`index.md`（目录清单）与 `log.md`（更新史）在任意层级有定义含义，不得用作概念文档。
2. **Concept = 一个 markdown 文件**（§4）：YAML frontmatter + 自由正文。**唯一必需键 = `type`**（短字符串，无中央注册，consumer 必须容忍未知 type）；推荐 `title` / `description`（一句话摘要，供 index 生成器/搜索 snippet 用）/ `resource`（底层资产 URI）/ `tags`。任意扩展键合法，consumer "MUST NOT reject documents with unrecognized fields"。
3. **互链成图**（§6）：标准 markdown 链接，推荐 bundle 根相对路径（`/tables/customers.md`）；链接 = 无类型有向边，语义由周边散文表达；**"Consumers MUST tolerate broken links: ... it may simply represent not-yet-written knowledge."**（断链 = 尚未写出的知识，不是错误——与 wiki 生长模式直接对口）。`references/` 子目录约定镜像外部材料/代码。
4. **index.md = progressive disclosure**（§8，与 AK wiki 的 index 先行同构）：

   > An `index.md` file MAY appear in any directory, including the bundle root. It enumerates the directory's contents to support **progressive disclosure**: letting a human or agent see what is available before opening individual documents.

   格式 = 分节标题 + `* [Title](relative-url) - short description` 列表；条目 SHOULD 带概念 frontmatter 的 description；可自动生成，consumer 也可在无 index 时现场合成。**每层目录都可有自己的 index**（比 AK 单 index 更细的层级导航）。
5. **log.md = 变更史**（§9）：日期分组、最新在前，日期标题 MUST 用 ISO 8601 `YYYY-MM-DD`；条目散文体，`**Update**`/`**Creation**`/`**Deprecation**` 粗体前缀是约定非强制。（对比 AK gist 的 `## [2026-04-02] ingest | Title` 前缀——同思路不同排版。）
6. **信任/溯源/生命周期 frontmatter 族（v0.2 核心增量，§5）**：
   - `sources`：溯源列表，每条 `resource`（必需，URL/bundle 路径/范围描述符）+ 可选 `id`/`title` + **客观可信度信号** `author`、`usage_count`（配 `usage_window`）、`last_modified`。**"It does not store a credibility score: a score is subjective, unportable across consumers, and goes stale."**——存信号不存评分，trust 由 consumer 推断。逐断言归因 = markdown 脚注 `[^source-id]` 键入 sources（不用位置索引，因为 "agents constantly rewrite these documents"）。
   - `generated: { by, at }`：谁/何时写的；`verified: [{ by, at }]`：谁/何时确认的（写者 ≠ 确认者，两者独立）。
   - **Trust tiers（§5.3）**：无 verified ⇒ unverified；仅非 human 验证 ⇒ machine-confirmed；有 `human:<id>` 验证 ⇒ human-reviewed。**"Trust tiers are advisory signals, not access control."**
   - `status: draft | stable | deprecated`（缺省 stable）；`stale_after`（绝对时刻，`now >= stale_after` 即过期——不用相对 TTL，"keeps the staleness decision a plain comparison"）。
   - **Actor 约定（§7）**：`<producer>/<version>`（agent/工具）、`human:<id>`（人）、`process:<id>`（自动过程）。
7. **Attested Computation（§10，v0.2 新概念类型）**：把「 sanctioned 计算」本身做成概念——`runtime`（bigquery/postgres/dbt/python/Looker）+ `parameters`（类型化参数洞）+ `computation`（内联 `# Computation` 围栏或文件路径）+ `executor`（运行指令 + receipt 字段声明）+ `attester`（**确定性无 LLM 代码**，consumer 侧运行，检查 receipt 返回 verdict）。**"The agent MAY only supply *values* for the declared `parameters`; it MUST NOT author or edit the computation."**——agent 只能填参数不能改计算，attester 机械比对「实际跑的 ==  sanctioned 计算绑定参数」，防 agent 即兴 SQL。verification（定义层、慢、存 bundle）与 attestation（单次运行层、不存 bundle）分离。
8. **Conformance 极宽（§11）**：合规 bundle 只需 ① 每个非保留 .md 有可解析 frontmatter ② 每个 frontmatter 有非空 `type` ③ index/log 若存在则遵循 §8/§9。consumer **MUST NOT** 因缺可选字段/未知 type/未知键/断链/缺 index 而拒绝 bundle。
9. **版本声明（§12）**：bundle 根 index.md 的 frontmatter 可带 `okf_version: "0.2"`（index 唯一允许 frontmatter 之处）；minor = 向后兼容增量，major = 可破坏。

### 1.6 与「LLM 更好搜索知识」的关系

**【事实】** SPEC/README 直接回答这个问题的原句：

- index 先行（README）："**Progressive disclosure built in.** Auto-generated `index.md` files let an agent or human navigate the hierarchy one level at a time instead of loading the entire bundle into context."
- 图状互链（README）："**Graph-shaped, not just tree-shaped.** Concepts link to each other via normal markdown links, expressing relationships richer than the parent/child implied by the directory layout."
- LLM 直接吃（README）："**Human- and agent-readable.** No SDK or query language stands between a reader and the content. An engineer can `cat` a concept; an LLM can ingest it verbatim into context."
- git 原生（README）："**Version-controllable out of the box.** Bundles live in git. Pull requests, line-by-line diffs, blame, and review workflows just work — knowledge curation becomes a normal software-engineering activity."
- 无锁定（README）："**Portable and lock-in free.** A bundle is a directory. ... No proprietary API stands between you and your metadata."
- 与既有工具复合（README）："**Composes with existing tooling.** Many knowledge tools — Notion, Obsidian, MkDocs, Hugo, Jekyll — already speak markdown plus YAML frontmatter."

**【事实】OKF 与 AK llm-wiki 的关系 = 官方明示的「规范化」**：v0.1 公告原句 "an open specification that **formalizes the LLM-wiki pattern** into a portable, interoperable format"，并逐字引用 Karpathy gist（§1.7）。AK gist（2026-04，idea file，刻意抽象）给出 raw/wiki/schema 三层 + index/log + ingest/query/lint 三操作；OKF（2026-06 v0.1 / 2026-07 v0.2）把其中「wiki 层」的文件格式标准化（frontmatter 键、index/log 形状、链接语义、合规判据），并超出 AK 的部分 = **信任/溯源/保鲜的机器可查字段**（AK 靠 lint 散文纪律，OKF 靠 frontmatter 结构）与 **attested computation**（AK 没有的「数字必须按 sanctioned 方式算出来」保证）。两者都反 RAG 重基础设施、都主张 LLM 维护、都纯文件零运行时依赖。**【推论】** 对知识地图项目：AK gist 给「为什么/怎么运转」，OKF 给「文件长什么样才 interoperable」——两者互补，不冲突。

## 2. 候选逐个一手核验（景观澄清 + 边界划定）

> OKF 正主已确证（§1），本节候选不再是「用户记混的猜测」而是「相邻标准/易混项的边界」。§2 由父会话在子代理中断后接手补全（获取均 2026-11-12，bash curl + 浏览器 UA）。

### 2.1 Open Knowledge Foundation（OKF/OKFN）——缩写撞车，非 Google

**【事实】** https://okfn.org/en/ 首页标题逐字："Open Knowledge Foundation – For a fair, sustainable and open future"；项目清单含 Data Package v2、Open Data Editor (ODE)、Open Data Day、Open Knowledge Network 等。**【推论】** 这是倡导开放数据的非营利组织（及其 Frictionless Data 系规范），与 Google Cloud 的 Open Knowledge Format 只是缩写撞车；用户说的「Google 出的规范」按归属排除它。

### 2.2 llms.txt——Answer.AI/Jeremy Howard，非 Google

**【事实】** 姊妹材料 §2.1 已一手考证（llmstxt.org，署名 Jeremy Howard，v2）。**【推论】** 边界：llms.txt 标准化的是**网站给 LLM 的入口索引**（web 尺度），OKF 标准化的是**知识 bundle 的文件格式**（目录尺度）；两者同属 index-first 家族但层次不同，可复合（wiki 对外发布时可加 llms.txt 入口）。

### 2.3 Google A2A（Agent2Agent）——Google 系但管 agent 互操作，不管知识表示

**【事实】** https://raw.githubusercontent.com/a2aproject/A2A/main/README.md 定义句逐字："**An open protocol enabling communication and interoperability between opaque agentic applications.**"；"The Agent2Agent (A2A) protocol addresses a critical challenge in the AI landscape: enabling gen AI agents, built on diverse frameworks by different companies running on separate servers, to communicate and collaborate effectively - as agents, not just as tools."；Apache-2.0；README 头部逐字 "Part of the [Agentic AI Foundation](https://aaif.io/)"（站点博客同步公告 "A2A joins the Agentic AI Foundation"）。Google 发起为通行背景知识（本轮未取发起公告一手文本，标注为上下文）。**【推论】** A2A 管「agent 之间怎么说话/发现彼此」（Agent Card 是它的发现面），不管「知识文件长什么样」——与 OKF 正交，不是用户所指。

### 2.4 schema.org——Google 联合创始，但管网页结构化数据

**【事实】** https://schema.org/docs/about.html 逐字："Schema.org is a collaborative, community activity with a mission to create, maintain, and promote schemas for structured data on the Internet. In addition to people from the founding companies (**Google, Microsoft, Yahoo and Yandex**), there is substantial participation by the larger Web community..."；首页并述编码形式 "RDFa, Microdata and JSON-LD"。**【推论】** 2011 年起的网页结构化数据词汇表（搜索引擎富摘要用），不是 LLM 知识格式；但它是 NLWeb 的语义底座（§2.6），与 OKF 同属「机器可读语义」大家族。

### 2.5 Google-Extended——robots.txt 抓取控制 token，不是知识格式

**【事实】** https://developers.google.com/search/docs/crawling-indexing/google-common-crawlers （需 -L 跟随 301）逐字："Google-Extended doesn't have a separate HTTP request user agent string. Crawling is done with existing Google user agent strings; the robots.txt user-agent token is used in a control capacity." 与 "Google-Extended is a standalone product token that web publishers can use to manage whether content Google crawls from their sites may be [used for AI training, 句尾提取截断]"。**【推论】** 这是站长控制「抓走的内容能否用于 Google AI 训练」的开关，与知识表示无关——排除。

### 2.6 NLWeb（Microsoft）/ AGENTS.md——归属澄清

**【事实】** https://raw.githubusercontent.com/microsoft/NLWeb/main/README.md 逐字："**NLWeb** simplifies the process of building conversational interfaces for websites. It natively supports MCP (Model Context Protocol), allowing the same natural language APIs to serve both humans and AI agents." 与 "Schema.org and related semi-structured formats like RSS — used by over 100 million websites — have become not just de facto syndication mechanisms, but also a semantic layer for the web. NLWeb leverages these..."。**【推论】** Microsoft 项目（repo org 一手），把网站变成对话/MCP 端点，不是 Google 规范。AGENTS.md = 开放格式非 Google 专属（姊妹材料 §2.3 一手），OKF SPEC 的 schema 层思想与它同族（§1.6 博客已点名 AGENTS.md/CLAUDE.md 家族）。

### 2.7 Google 产品类（不是规范，排除「产品 ≠ 规范」）

**【事实/登记】** Data Commons（datacommons.org，首页标题 "Home - Data Commons" 已取；repo API 本轮返回空，未深核）= Google 的开放知识图谱数据项目；DataGemma / NotebookLM / Gemini Deep Research / AI Mode = 产品能力，均非文件格式规范（本节目的 = 排除，未逐个深核，标注为产品级登记）。**【事实】** 与 OKF 直接相关的产品 = **Knowledge Catalog（前身 Dataplex）**：v0.1/v0.2 博客一手（§1.7）——"We have also updated Google Cloud's Knowledge Catalog to be able to ingest Open Knowledge Format and serve it to our agents."

### 2.8 2025–2026 新规范/生态扫描

- **【事实】** OKF 第三方工具链已出现：PyPI `okf-toolkit` 0.1.2，summary 逐字 "CLI toolkit for working with Google's Open Knowledge Format (OKF)"（https://pypi.org/pypi/okf-toolkit/json ，获取 2026-11-12）。npm `okf-toolset` 与 UCP（Universal Commerce Protocol）关联线索仍待核（§1.5 登记，非关键）。
- **【事实】** MCP resources 侧：DSH 已内置 `list_mcp_resources` / `list_mcp_resource_templates` / `read_mcp_resource` 三工具（家底材料 §2.1 代码一手）——「外部知识以 MCP resource 形式接入」的通道现成。
- **【推论】** llms.txt v2（2026-08 修订，姊妹材料 §2.1）与 OKF v0.2（2026-07）是同年演进的姊妹运动：前者管 web 入口，后者管知识 bundle；SEO 社区已把两者关联（§1.7 二手标题线索）。

## 3. 候选排名与判定（定稿）

**【事实→推论】排名第 1（确证，不再是猜测）：OKF = Google Cloud Open Knowledge Format。** 用户说的「Google 出的规范叫 OKF」逐字成立：Google（GoogleCloudPlatform org + cloud.google.com 官方博客）、规范（SPEC.md v0.2）、名字（OKF）。证据强度 = 最高（官方仓库 + 规范全文 + 官方博客）。其余候选降为「相邻标准/易混项」，排名意义从「猜用户指什么」变为「划清 OKF 与它们的边界」。

**【推论】边界一览**（逐个一手核验见 §2）：

| 候选 | 归属 | 管什么 | 与 OKF 的关系 |
|---|---|---|---|
| OKFN（Open Knowledge Foundation） | 非营利组织，非 Google | 开放数据倡导/Data Package | 仅缩写撞车 |
| llms.txt | Answer.AI（Jeremy Howard） | 网站给 LLM 的入口索引 | 同家族不同层次（web 入口 vs bundle 格式），可复合 |
| A2A / Agent Card | Google 发起 → Agentic AI Foundation | agent 间通信与发现 | 正交（互操作 ≠ 知识表示） |
| schema.org | Google/Microsoft/Yahoo/Yandex 联合创始 | 网页结构化数据词汇 | 语义层前辈；NLWeb 的底座 |
| Google-Extended | Google | robots.txt AI 训练抓取控制 | 无关（抓取开关 ≠ 格式） |
| NLWeb | Microsoft | 网站对话化/MCP 端点 | 相邻运动（AI Web 语义层） |
| AGENTS.md | 开放格式（非 Google 专属） | agent 仓库说明书 | OKF 博客点名的同族约定 |
| Data Commons / NotebookLM 等 | Google 产品 | 知识图谱数据/产品能力 | 产品 ≠ 规范；Knowledge Catalog 是 OKF 的产品消费端 |

## 4. 对知识地图项目的含义（定稿）

**【建议】核心**：AK gist 给「为什么/怎么运转」（idea），OKF 给「文件长什么样才 interoperable」（spec）——**两者叠加 = 本仓 wiki 内容层的现成设计依据，零新依赖**（OKF 是纯文件约定；参考 agent 的 BigQuery/Gemini 依赖是 PoC 的依赖不是格式的依赖，README 明言）。具体借鉴清单：

1. **frontmatter 最小集 + 信任族**：`type` 必需（唯一硬键）+ `description` 一句话 + `sources`/`generated`/`verified`/`status`/`stale_after` 按需渐进（v0.2 全部 opt-in，"adds vocabulary, not rules"）。合规极宽（§1.4.8）→ 可先只写 type+description，信任字段后补，不破坏兼容。
2. **frontmatter = 读正文前的廉价决策面**（v0.2 博客原句，§1.7）："Trust becomes something you can filter on before you commit to reading."——**与搜索阶梯直接复合**：L1 自建 FTS 可把 frontmatter 字段（type/tags/description）一并索引做过滤；agent 扫 index 时先看 frontmatter 信号决定钻不钻页，省 token。这是「靠 LLM 更好搜索」的标准化抓手。
3. **每层目录 index.md + log.md**（OKF §8/§9）：比 AK 单 index 更细的层级导航；与本仓 kb guide「一眼看懂」表先例同构（主材料 §4.2）。log 日期标题 ISO 8601、最新在前。
4. **断链容忍**（SPEC §6 原句）："it may simply represent not-yet-written knowledge"——与「动态增长、加不完」的诉求直接对口：wiki 可以先有链接后有页。
5. **trust tiers 对应公司审核闸**：unverified / machine-confirmed / human-reviewed 三档（§1.4.6）与培养回路「提案-人采纳」同构——agent 写的页 = machine-confirmed 以下，人审过的页 = human-reviewed；**advisory 不是访问控制**，不改变沙箱边界。
6. **ingest 工作流参照**：reference agent 的 web pass = "runs the LLM as its own crawler"（种子 URL + fetch_url + 自主判断出链 + max-pages/allowed-hosts 硬上限，§1.5）——DSH 侧对应物 = web_fetch/bash curl + workflow 编排（载体材料 §2），上限纪律照抄。
7. **人浏览层参照**：visualize 单文件自包含 HTML 图（Cytoscape.js，无后端，§1.5）——client 浏览面板或静态导出都可借鉴此形状；Quartz 是现成开源替代（oss-search-landscape §5）。
8. **attested computation 暂不需要**：公司知识地图无「sanctioned 数字计算」场景；留作可选升级（若将来政策数字要可复核计算，此模式 = 现成参照）。

**【推论】** 标准化红利：wiki 若按 OKF 形状长，将来可被任何 OKF 消费端读（Knowledge Catalog、okf-toolkit、第三方图谱工具），也可随时换生产端——BYOAI/File-over-app 四原则（主材料 §1.1）的规范化保障。
