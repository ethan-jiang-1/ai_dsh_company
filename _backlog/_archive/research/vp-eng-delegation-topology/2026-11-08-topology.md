# 委派拓扑：workflow 控流程、subagent 保信噪比

> 本文是研究材料，不是合同。结论候选在第 4、6 节；未定性前不写进题名页 `> 结论：`。
> 三条边界沿用题目：不发明第二套编排、不把 workflow 子代当 SA/SQA、本轮不改任何 preset/合同。
> 用户 2026-11-08 的口径：**角色按判据自主用 workflow，用户强制也行**；本轮只做 keyless。

## 0. 一句话

`workflow` 买的是**流程的确定性**（步骤完整、并发、结构化证据、失败即停），买不到**判断的独立性**；
`subagent` 买的是**上下文防火墙**（子代理的细节留在子代理），买不到**流程的确定性**。
两者不是替代关系：workflow 是「把一件事拆成可并行的多件、再把结果压回一个 JSON」的流程编译器，
subagent 是「把一件细节活交出去、只收回结论」的信噪比工具；命名专家与 team 各自补上「独立人格」与「多轮协作」。
这不是纸面推演：2026-10-12 有一次真实自主使用（CFO teammate 的四路取证，§1.3），也有一次因沙箱失败的探针。

## 1. 机制事实（先钉死，再谈取舍）

### 1.1 通道能力表

| 通道 | 子代人格 | 父上下文收到什么 | 并发 | 持久/可续 | 失败语义 |
|---|---|---|---|---|---|
| 自己做 | — | 全部 | — | — | — |
| `subagent`（spawn） | 继承调用者组合 | 回执 + 完成通知（子代最终文本） | 同轮多调用 | 可续（控制行） | 子失败进通知，父不中断 |
| `subagent_fork` | 调用者组合 + 已完成轮前缀 | 同上 | 同上 | 可续 | 同上 |
| `workflow` 的 `agent()` | 继承调用者组合，**无 agentPreset**；fresh 上下文（无父历史） | 前台：脚本返回的 JSON（渲染 ≤50000 字符）；后台：job id + 完成通知 | 脚本内 `parallel`/`pipeline` | 外壳不给续驶；持久化部署下子代进 catalog、可 cold resume（工具不暴露该操作） | 子失败→`null`；fatal 默认为整轮 error（脚本可 catch 吞掉） |
| 命名专家 | 真 preset（SA/SQA/CMO） | 回执 + 完成通知 | 同轮多调用 | 可续 | 子失败进通知 |
| `spawn_teammate` | 继承 Lead 组合 | 成员消息逐条进历史 | 成员并行 | 持久、冷恢复 | 成员失败不自动释放任务 |

### 1.2 六条会改变判断的事实

**F1｜`agent()` 没有 `agentPreset`，也没有 `maxDepth` 与工具过滤。**
选项集合 = `label / phase / schema / provider / model`（`vendor/dsh/packages/workflow/workflow-ptc/src/runtime.ts`
的 `SUPPORTED_AGENT_OPTIONS`；`effort / isolation / agentType` 被显式列为 deferred 并拒绝）。
host 调 `ctx.subagents.startActivation` 时不传 `agentPreset`（`workflow-ptc/src/host.ts` 的 `startChild`）⇒
子代加入调用者当前的 preset revision：**同一人格、同一工具面、同一 cwd 的克隆线程**，不是另一个角色。
但它是 **spawn 的 fresh 上下文**，不 seed 父对话（`subagent/subagent/README.md`：spawn = fresh state，
fork = completed-turn seed）——脚本里每个 `agent()` 的 prompt 必须自包含，别指望子代「看到上文」。

**F2｜父代只收最终 JSON，不收子代消息。**
`delivery: 'caller'`，且 workflow 引擎自己收集结果、不向父模型发 settlement notice；local 子代仍可在父会话的
subagent catalog 里被发现（`list_agents`），但父模型看不到中间消息，运行结束即 dispose。
工具结果的渲染上限 = `maxResultChars`（默认 `50000`），超出截断并加提示（`tool-workflow/src/index.ts`）。
后台档（`run_in_background: true`）走另一条路：立即返回 job id，返回值随 job 完成通知到达，可用 `job_output` 读。
证据质量备注：`workflow-ptc/README.md` 的结果段写「不进父 catalog」，与实现/测试（会进）矛盾；以代码与测试为准。

**F3｜`schema` 是「结构化证据」的硬通道。**
`agent(prompt, { schema })` 的 schema 是 object-rooted 的受限子集；子代没交出合规结构（`structured === undefined`）
时该次调用折成 `null`（`workflow-ptc/src/runtime.ts` 的 `agent()`）。这给了脚本一个可判定的「证据不齐」信号，
而不是一段可信度未知的散文。

**F4｜run 级没有 partial success，但「数据级 partial」与「吞错」都合法。**
子代非 `completed` ⇒ 该次 `agent()` 返回 `null`；hook 误用、超帽、取消 ⇒ 抛出 fatal，**脚本不 catch 时**整个 run
以 `error`/`cancelled` 结束（`workflow` 子系统文档的 failure discipline）。两个口子：
① 脚本可以把 per-item `null` 当数据返回（`{supported, missing: 3}`）——run 是 `completed`，内容却是 partial；
② runtime 只抛 promise rejection，没有强制终止，脚本 `try/catch` 可以吞掉 fatal 继续跑。
所以「失败即停」是**默认**不是**强制**：模板必须写「不要 catch fatal；`missing > 0` 就自己 throw」，
否则质量门只是建议。

**F5｜组合形状已有先例，公司只是把 seam 空着。**
vendor 的 `standard/ptc/cordis` 三个 preset 在**同一个** `isolate.workflowEngine` 组里同时声明：

```yaml
- id: workflow-ptc
  name: '@deepseek-ai/dsh-workflow-ptc'
  config: { provider: spawn }
- id: tool-workflow
  name: '@deepseek-ai/dsh-tool-workflow'
```

base 另有 `ptc-runtime` 行（`@deepseek-ai/dsh-ptc-runtime-node`），web-app 把 `workflow-ptc` / `tool-workflow`
两行 `disabled: true`，由 preset 重新挂。公司五个角色 preset 目前只有 `isolate.workflowEngine: true`
（`presets/vp-eng/agent.cordis.yml` 的 `delegation` 组），没有这两行 ⇒ **空 seam，不是能力**。

**F6｜历史不是「0.8.0 一刀切退役」，而是「CEO 试点 → 升 pin 掉行 → 两周后清 peer」。**
git 历史（`git log -S`）给出三段：

1. **2026-09-30（0.2.0 harvest 批4）**：CEO preset 加过 `workflow-ptc` + `tool-workflow`，persona 写
   「并行编排多路活…它是编排面不是分工面」；VP/COO/CFO 没给（编排位归 CEO 的组织语义）。
2. **2026-10-19（升 pin 0.2.1）**：preset 重写时两行被撤，提交说明没有给 workflow 专属理由；同日 persona
   删掉 workflow 句。**VP-Eng 从来没有过这条通道。**
3. **2026-11-03（0.8.0）**：peer 清账，`notes/implemented/2026-11-03-d4-semantic-drift.md` 的「输掉的方案」
   写「没有使用场景，恢复只会把死行带回来」。

而且 §1.3 的 2026-10-12 真跑直接反证了「没有使用场景」——那次 CFO 四路取证就是真实使用。
所以本次不是「恢复旧能力」，而是「把用过的能力装回目标角色」；当年 `architecture.md` 的否决理由仍成立且要保留：
workflow 是「一次 run，不常驻组织」——本材料因此只把它当**单个复杂包的一次性流程工具**，不当组织通道。
另有两处历史叙述要顺手校正：`architecture.md` §3 写「worker-thread 引擎」，实际当年挂的是 `workflow-ptc`
（同 standard preset）；`guides/budget-and-ops.md` §2 仍把「workflow 冲刺」当现行成本项（与三处「已退役」矛盾）。

### 1.3 真实先例（2026-10-12）：CEO 团队里的 CFO 四路取证

证据 = dev home 的会话 `77cc8c50-…`（`runtime/harness-home/sessions/--Users-bowhead-ai_dsh_company-company-workspace--/`；
gitignored 的本地证据，不随仓分发）。会话头：`agentPreset: ceo`、`origin: subagent`、`delegationDepth: 1`、
`parentSession: 6cce7fb4…`——即 CEO 团队里的 teammate `cfo`，因为 teammate 继承 Lead 组合而拿到了当时 CEO preset 上的
`workflow` 两行。

| 项 | 值 |
|---|---|
| 任务 | T4「AI coding 安全」成本与合规闸门：控制项成本表 + 预算闸门 + 数据/许可合规 |
| 用法 | `parallel` 四路：密钥扫描 / SAST 依赖 / AI 助手数据条款 / 许可与 IP；每路 `agent(..., {schema})` |
| 约束 | 只写 `drafts/sources/`、文件名 `cfo-` 前缀；不许写 `.md`、`kb/`、别人的文件；只写实读到的原文 |
| 结果 | 4/4 `completed`；run 371s（2026-10-12 12:27:58 CST 起） |
| 返回 | 4 路 × ~20 行 JSON；渲染 58.8k 字符，另有 66.2k 字符溢出到 spill 文件；父代理 grep 溢出件后写 `cfo.md`（302 行） |
| 沙箱 | `danger-full-access`（delegation） |

读法（都受「单样本」限制）：

- **支持 H1**：真实使用是「同身份扇出取证」，不是「替代独立人格」；`schema` 与写盘范围都是模型自己写的。
- **支持 H2 的一半**：4 路并行 371s；但这是**前台** run，teammate 被阻塞约 6 分钟，Lead 的 T8 消息在 run 结束后才投递
  （`agent/inbox/spliced` 在 `run-end` 之后）——墙钟省了，协作延迟付了。
- **H4 仍成立**：四路都是 CFO 人格的克隆线程，出的是证据，不是签字。
- **反证「没有使用场景」**：`d4-semantic-drift` 的「没有使用场景」被这条真跑直接推翻。行是 2026-10-19 升 pin 时掉的，
  peer 是 2026-11-03 清的；复装不是「恢复死行」，是「把用过的能力装回目标角色」。
- **沙箱是硬前提**：同期的 depth probe（2026-10-10，`workspace-write`）以
  `sandbox-unavailable: sandbox-exec: sandbox_apply: Operation not permitted` 失败；真跑能成是因为
  `danger-full-access`。**workflow-ptc 在默认 `workspace-write` 下能否起，是落地的第一道部署门。**

限制：单样本；角色是 CEO teammate（继承 CEO 组合），不是 VP-Eng；结果大到触发 cap + spill，模板应返回聚合/异常而不是全量 rows。
同窗口（9/29–10/20）的 185 个会话目录里，`workflow` 作为工具名出现在 148 个（多数是开发/探针会话，工具可见），
实际调用只有 2 次——可见 ≠ 会用；但真实工作里的那 1 次正是我们要的形态。

## 2. workflow 到底能控什么（质量边界）

### 2.1 买得到的五种保证

| # | 保证 | 机制 | 对 VP-Eng 的意义 |
|---|---|---|---|
| G1 | 步骤完整 | 脚本是固定程序，循环/顺序/重试不靠模型「记得」 | 五层链、逐份核对这类流程不会中途漏步 |
| G2 | 扇出与并发 | `parallel` / `pipeline`；引擎默认按 CPU 并行度 | 多源调研、多文件审计的墙钟从串行等待变并行 |
| G3 | 结构化证据 | `schema`；缺结构→`null` | 每条结论带 `claim/evidence/source/confidence`，主代理不用读散文 |
| G4 | 默认失败即停 | fatal 抛 rejection；脚本不 catch 时整轮 error | 默认不会「总结成基本完成」；但脚本可 catch 或返回 `missing` 字段，门要自己写 |
| G5 | 可观察/可审计 | `phase()` / `log()`、run 记录、后台 job 输出 | 收口时能给出「跑了哪些分支、各什么结局」的过程证据 |

### 2.2 买不到的五件事

| # | 买不到 | 原因 | 替代 |
|---|---|---|---|
| L1 | 独立人格/签字 | `agent()` 无 `agentPreset` | 命名专家（`system_architect` / `system_qa` / `vp_cmo`） |
| L2 | 判断独立性 | 同模型、同人格、同工具面；P5 的口径是「判断类复核 = 同模异线程 ⇒ 独立性有限」 | 机械全量重算可算独立；判断类仍要命名专家或人审 |
| L3 | 写盘互斥 | 子代继承写工具、共享 cwd；脚本没有文件锁/合并 | 一分支一文件 + 父代理单写者；或分支只读 |
| L4 | 跨轮协作 | workflow 外壳不给续驶界面（run 不把 child id 交回父模型），也没有消息/任务板；子代本身在持久化部署下仍可 cold resume，但那是 `list_agents` + 控制行的旁路，不是 workflow 的设计面 | team（持久成员）或再委派一次 |
| L5 | 子代不再向下委托 | **装上 workflow 两行之后**，子代继承完整工具面：VP-Eng 根（depth 0）时子代 depth 1，`system_architect` maxDepth 2 放行 ⇒ 子代可再命名 SA；VP-Eng 作为 CEO 子代（depth 1）时 SA 需 depth 3 > 2 被拒。**workflow 本身没有深度闸**：子代若继承 `tool-workflow` 可再开 run（嵌套），只受 per-run caps 与共享 `maxActiveSubagents`（默认 8）限制 | 软约束（任务书写「只调研、不委托」）或工具过滤（vendor 未提供）；嵌套 run 的治理要单列 |

### 2.3 与 P5 独立性口径对齐

P5 / 手册的分层是「机械全量重算（独立性成立）」与「判断类复核（同模异线程 ⇒ 独立性有限）」。
workflow 正好落在前者的延伸上：**同一份机械判据在多个分支上各算一遍，可以算独立复核**；
但**「这份设计是否可接受」这种判断**，workflow 出的结论仍只是「同模异线程」，不能替代 SQA 的签字。
这也解释了为什么 H4（workflow 出的验证结论不能算独立复核）要拆成两半看：机械的一半成立，判断的一半不成立。

## 3. 信噪比：让主代理只看见决策差异

### 3.1 上下文账本

| 事件 | 进父上下文？ | 量级 | 可控性 |
|---|---|---|---|
| `subagent` 的调用 prompt + 回执 | 是 | 父代理自己写的 brief + 一行 ack | 父代理可控 |
| `subagent` 的完成通知 | 是 | 子代最终文本，**无契约上限** | 只能靠 brief 约定；兜底是 pruner/compaction |
| 子代主动消息 | 是 | 每条一条 user 消息 | 少用；非必要不让子代回报 |
| `workflow` 的脚本 + args | 是 | 脚本本身可能很长 | 父代理可控；但一次写死所有 prompt |
| `workflow` 的返回 JSON | 是 | ≤ `maxResultChars`（默认 50k 字符） | 脚本可只回聚合/异常 |
| team 成员消息 | 是 | 每条一条消息 | 任务板记录不进模型历史，消息进 |
| workflow 子代的上下文 | **否**（fresh，不 seed 父对话） | 父代理必须把上下文写进脚本 prompt | 写全的成本在脚本里，不在子代对话里 |

### 3.2 四个压缩杠杆 + 一个兜底（按效果排序）

1. **源头契约**：brief 里写死返回形状（`只回 JSON：{claim, evidence_path, confidence}` / `≤10 行` / `只回不通过项`）。
   子代写多长，父代就吃多长；在源头压最便宜。
2. **N→1 聚合**（workflow）：N 个分支 → 一个 JSON。父代不再收 N 条完成通知。
3. **细节落盘 + 指针**（artifact handoff）：子代把全文写进 `drafts/<name>.md`，只回「路径 + 5 行摘要 + 关键差异」；
   父代按需再读。细节不占常驻上下文，证据仍可追溯。
4. **异常优先**：脚本只返回非 OK 项（`{failures: [...], counts: {...}}`）。主代理的注意力只花在差异上。
5. 机械兜底：`tool-result-pruner`（`thresholdChars: 8192` / `headChars: 4096` / `tailChars: 1024`）与
   `compaction-basic` 是安全网，不是设计——被它们裁掉的信息，主代理已经看不到了。

### 3.3 反模式（噪声就是这么来的）

- 「帮我研究一下 X」不写返回形状 → 子代交一篇长文，父代被淹没。
- 轮询 `list_agents` 等结果 → 每次轮询都是一条消息；正确姿势是结束本轮，等完成通知。
- 1–2 件小事也用 workflow → 脚本本身的长度超过省下的通知，净亏。
- 用 `subagent_fork` 替代 fresh → 子代复制父代前缀（子代成本），父代并没有更干净。
- 用 team 做一次性扇出 → 任务板、成员消息、共享组合，全是额外噪声与额外面。

## 4. 判据：什么时候用哪条

### 4.1 「复杂」的五维定义

| 维 | 取值 | 为什么重要 |
|---|---|---|
| N 产物/分支数 | 1 / 2–3 / ≥4（阈值按 A 调） | 决定扇出是否值得编排 |
| I 独立性 | 无 / 机械重算 / 判断 / 人格签字 | 唯一能一票否决 workflow 的维度 |
| A 聚合度 | 无 / 需要合并 / 需要交叉核对或异常聚合 | 决定是否需要脚本做 reduce |
| R 轮次 | 一次 / 多轮追加意见 | 决定是否要 team 的持久面 |
| W 写面 | 只读 / 各写各的 / 共享文件 | 决定能否并行写 |

「复杂」= **N≥3 且（A≥合并 或 I=人格签字）**，或 **R≥2 且有共享任务板**。
只有 N 大、A 小、I 无的活（例如 10 个独立文件各查一个事实）也算「大」，但它是扇出题，不是复杂包。

### 4.2 通道选择表

| 条件 | 通道 | 备注 |
|---|---|---|
| N=1，A=无，I=无，R=1 | 自己做 | 别为一件小事付编排成本 |
| N≤2，A≤合并，I=无，R=1 | `subagent`（fresh） | 要继承上下文才用 `subagent_fork` |
| N≥3，I∈{无, 机械}，R=1，且（A≥合并/交叉核对 或 纯扇出且 N≥4） | `workflow` | 结构化返回 + 异常优先 |
| I=人格签字（SA/SQA/CMO） | 命名专家 | 任何 N 都走这条；改稿=再委派一次 |
| R≥2，共享任务板/互审 | team（`spawn_teammate`） | 成员继承 Lead 组合，不冒充角色 |
| W=共享文件 | 单写者 | workflow 分支只读或一分支一文件 |

### 4.3 组合拓扑：一个复杂研发包

```
VP-Eng 根（Lead）
├─ workflow：证据扇出 / 覆盖审计 / 交叉核对   ← 只读或各写各的，返回 JSON
├─ 命名专家：system_architect（SyRS/IRS）、system_qa（V&V） ← 独立人格，单写者
├─ team（可选）：多轮实现/互审，任务板 + writeScopes
└─ VP-Eng 自己：合稿、写 PRD、署名判断（单写者）
```

顺序上建议：workflow 先出证据 → VP-Eng 写稿 → 命名专家评审 → VP-Eng 改稿（可再用 workflow 做覆盖审计）。
**不要**让 workflow 分支写正式交付物，也不要让它替代任何一次签字。

## 5. 三个可复用的 workflow 模板

模板纪律（三条，先于模板本身）：

1. **prompt 自包含**：子代是 fresh 上下文，看不到父对话；把「背景 + 要查什么 + 返回形状」全写进 `agent()` 的 prompt。
2. **不要 catch fatal**：让 hook 误用/超帽/取消杀掉整轮；catch 只会把失败伪装成 completed。
3. **门自己写**：run 的 `completed` 不等于内容完整；`missing > 0`、`failures.length > 0` 时脚本自己 `throw`。

### T1 证据扇出（研究/调研）

```js
const items = args.questions
const rows = await pipeline(items,
  q => agent(`只查证这个问题，返回 JSON：{claim,evidence,source,confidence}\n${q}`,
             { schema: EVIDENCE, phase: '取证' }),
  r => r === null ? null : agent(`复核这条证据是否支持结论：${JSON.stringify(r)}`,
             { schema: VERDICT, phase: '复核' }))
const missing = rows.filter(r => r === null).length
if (missing > 0) throw new Error(`证据不齐：${missing} 条`)
return { supported: rows.filter(r => r?.ok), disputed: rows.filter(r => r && !r.ok) }
```

质量点：每条结论有 source；复核不通过的单列；缺证据的显式计数。
边界：复核仍是同模异线程，不能写成「独立评审」。

### T2 交叉复核（高 stakes 内部审）

两路独立取景（「找支持」/「找反例」）→ 一个 judge 按 rubric 出 `{verdict, blockers}`。
用途：VP-Eng 自己的评估稿在交 SA/SQA 之前先自检。
边界：judge 与两路同人格；结论只能叫「内部交叉核对」，不能叫「独立复核」。

### T3 覆盖审计（提交前）

items = 产物/需求清单；每支返回 `{id, ok, problems}`；脚本只回 `failures` 与计数。
用途：PRD 的 REQ/AC 覆盖、五层链完整性、编号/追溯的机械核对。
边界：机械全量重算可以算独立；判断类（「这条 AC 是否可验收」）不算。
纪律：脚本返回 `failures` 时，父代理必须读它才能宣称覆盖；若这道门必须硬红，模板改成 `failures.length > 0` 就 `throw`。

### T4 切片实现（可选，风险最高）

一分支一文件、prompt 里写死路径与验收；脚本汇总 `{file, status}`；父代理 review diff。
只在文件互不重叠时用；不要指望脚本做合并或冲突解决。

## 6. 采用成本与风险

### 6.1 要动的面（实施时）

1. `presets/vp-eng/agent.cordis.yml` 的 `delegation` 组内加 `workflow-ptc` + `tool-workflow` 两行（同组，否则
   `tool-workflow` 看不到组内 isolate 的 engine）。
2. `packages/company-pack/package.json` 的 `peerDependencies` 加 `@deepseek-ai/dsh-tool-workflow` /
   `@deepseek-ai/dsh-workflow-ptc`（`preset-row-deps` 门禁会查）。
3. `docs/delegation.md` §4 的「workflow 第三通道已于 0.8.0 退役」必须改；`docs/presets.md` 的两行「已退役」
   工具面表补一行；`design/architecture.md` §2.3/§3 的「通道 D 已退役」同 diff 改。
   顺带对齐一处既有漂移：`guides/budget-and-ops.md` §2 仍把「workflow 冲刺」列为脉冲成本，与上面三处
   「已退役」矛盾——无论本次定性做不做，这处都该改。
4. `eng-teaming` 的四档决策树加一行「2.5 并行扇出（workflow）」；`eng-workflow` 第 3 步「深挖」点名 workflow 的适用判据。
5. 验证：`preset-smoke`（真挂载，keyless ~30s）+ `pnpm test` + `pnpm verify`；真模型行为判据另立。

### 6.2 固定税

- `workflow` 的 tool schema 在 catalog 里 **4311 字符**（同口径 `subagent` 段 3026、`subagent-control` 段 2716），
  每次请求都在；再加一条约 300 字符的 prompt section。
- 对 VP-Eng 这种长会话，这是**每轮**的常驻成本，不是「用的时候才付」。这也是先只开一个角色试点的理由。

### 6.3 三个真实风险

**R1｜工具自带的反向提示。** `tool-workflow` 注册的 prompt section 原文：
「Use the `<toolName>` tool **ONLY when the user explicitly asks** for a workflow or for large multi-agent orchestration…」
用户要的是「角色按判据自主用」。可用的解释路径有三条，按可靠性排序：
① 句子本身有第二个分支「large multi-agent orchestration」——角色 skill 把判据写成可自检的「这属于大型多代理编排」；
② 公司 preset / skill 是用户写的常驻指令，构成「standing explicit ask」；
③ skill 在对话中后加载（tool 结果），比 system prompt 的 ONLY 段更靠近当前决策。
残余风险仍在：模型可能保守不调用。验收时要有行为判据（给定 N≥3 的题，是否真的用 workflow），不能只看挂载。
若真跑证明 ONLY 段稳定压过 skill，备选是自写一个薄 consumer（复用 `ctx.workflowEngine`，带公司自己的 guidance）——
但那是新插件、新维护面，违背「优先现成载体」，只作为兜底，不在第一版。

**R2｜写盘冲突。** workflow 子代继承写工具与同一 cwd；脚本没有锁。规则：分支只读，或一分支一文件；
正式交付物只由父代理写。团队侧的 `writeScopes` 只告警不阻塞，不能当锁用。

**R3｜假独立。** 用 workflow 出「验证结论」再署 SQA 的名，会把 E/V 分家破坏掉。规则：workflow 只能出
「机械重算 / 证据核对」；判断类结论仍由命名专家出，原样保留。

**R4｜沙箱前提。** workflow-ptc 在 `workspace-write` 下曾以 `sandbox-unavailable` 失败（2026-10-10 depth probe），
真跑能成是因为 `danger-full-access`。落地前必须在 VP-Eng 的默认沙箱里跑一次最小 workflow；失败就先解决沙箱，
别先改两行。这条是**第一道部署门**，比 peer/文档都靠前。

**R5｜前台阻塞与结果溢出。** 真实先例 371s 前台 run 阻塞 teammate 约 6 分钟，Lead 消息排队；结果 ~125k 字符触发
50k 渲染上限 + spill，父代理还要 grep 溢出件。规则：团队会话里的长 run 用 `run_in_background`（或先告知 Lead）；
脚本返回聚合/异常，别回全量 rows。

### 6.4 候选措辞（给 eng-teaming / delegation，不实施）

`eng-teaming` 四档表加一行（编号可叫 2.5，避免把「命名专家」挤成 4）：

> **2.5 并行扇出（workflow）** | ≥3 个同构分支、要合并/交叉核对/只回异常，且不需要独立人格 | 写脚本：
> `pipeline`/`parallel` + `schema` + 异常优先；分支只读或一分支一文件；返回 JSON | 父代理合稿署名

`eng-workflow` 第 3 步「深挖」改为：

> 1–2 件用 `subagent`（brief 写死返回形状）；≥3 件同构且要聚合用 `workflow`（证据扇出 / 覆盖审计）；
> 要独立结论（SA/SQA/CMO）仍走命名专家。用户点名要 workflow 时直接照办。

`docs/delegation.md` §4 第 2 条改为：

> **要自定义组合/多角色编排** ⇒ 四个职能角色的 `subagent_fork` + 命名委托；`workflow` 是 vp-eng 的
> **同身份并行扇出**通道（不能带 `agentPreset`，不能替代 SA/SQA 的独立结论）；CEO 的编排面仍是 team + 命名委托。

### 6.5 建议的落地顺序（若定性为「做」）

0. **最小两行 + 立刻验沙箱**：只改 `vp-eng` preset（两行 + 两 peer），先跑 `preset-smoke`（挂载），再在
   `vp-eng` 会话（默认 `workspace-write`）里跑一次最小 workflow（一条 prompt，约 1–2 分钟）。任一步红就**回滚两行**、
   停在 `sandbox-unavailable` 上，不进后续。这一步不是 keyless，是一次性部署验证。
1. 绿了再补 `pnpm test`、`eng-teaming` 2.5、`eng-workflow` 第 3 步、四处文档与 Note。
2. `eng-teaming` 加判据与模板；`eng-workflow` 第 3 步点名；`docs/delegation.md` 同 diff 改退役叙述。
3. 真模型行为判据（另立卡）：给一个 N≥3、无独立人格需求的题，看是否选 workflow；给一个需要 SQA 的题，
   看是否仍走 `system_qa`。两条都过，才谈扩到其他角色。
4. 观察一个迭代：VP-Eng 会话里 workflow 的实际调用次数与 token 账；没有使用就回滚（维持 0.8.0 的结论）。

若定性为「做」，产出的卡建议 = **VP-Eng workflow 通道接入**：两行 + 两 peer + `eng-teaming` 判据 +
`docs/delegation.md` 退役叙述同 diff；验收 = `preset-smoke` 真挂载 + 真模型行为两条（N≥3 会用 workflow；
需要 SQA 时仍走 `system_qa`）。
