## 背景 / 触发

多用户 BDD 加工收口时的诚实边界（2026-10-04）：**单进程 team 内**的并发同步已全部观察固化
（C1–C7 六 probe，含崩溃恢复）；**跨进程**（多个真人各开各的 `$DSH_HOME` 实例 + 外部编辑器，
写同一共享盘）内建机制管不到——E2 实测同版本守卫写 ×20 = 20/20 静默互踩。用户指认「没解决的
跨进程……我们也要解决这个」，令立卡推敲。

## 已知与未决

**已知（带出处）**：
- E2：跨进程同版本守卫写 ×20 双双成功互踩——守卫检查与发布间**无跨进程原子性**（fs-local 守卫
  管新鲜度不管独占；原子发布管完整不管丢失更新——后写者基于旧读的合法重写 = 内容静默丢）。
- 规矩层已闭合（审计面，非预防面）：slug 唯一（S1）、占位=认领（S3）、双 home 审计拼图（S5）、
  署名行（authorship-audit）。
- 前序毕业卡 [writing-collab-locks-redis](../_done/_closed_plans/2026-09-29-writing-collab-locks-redis.md)：
  R0 四条原生协作已落地；**R1（互斥需求成立即上）与 R2（单机 redis 实验，双触发条件：真多人动议
  撞上 R0 罩不住的具体失败）的实验位已在案**——本卡是它们的接续盘，不重复推敲 R0。
- redis 判定树（C 系卡）：单进程不需要；跨进程先规矩层 → dsh-atomic-write → redis 最后手段。
- **`dsh-atomic-write` 形状未复核**：multi-human.md 指名它是跨进程互斥"正解"（维护者/脚本侧），
  但钉住的 vendor 树内**未见独立原语**（grep 仅 fs-local 进程内 staging）——是 upstream 工具、
  模式名、还是本仓需自建 = 第一项待答。

**未决（四问）**：
- 该不该：用户已表"要解决"；但解决的成本阶梯（规矩强化 → 原语采纳 → 锁基建 → redis）未选。
- 何时：触发条件候选 = 多真人开门常态化 / 首例真实丢失更新事故（内容丢，非被拒）/ 第二贡献者
  日常使用。
- 次序：dsh-atomic-write 复核 → 候选选型 → RFC → 实施。
- 放弃：单真人/单实例阶段本卡自然休眠（不销——机制债真实存在）。
